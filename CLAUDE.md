# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## 🚫 GOLDEN RULE — No runtime AI/LLM calls (non-negotiable)

This app must **never** call any external AI/LLM API (OpenAI, Anthropic, Google, etc.) during operational runtime. All running-sheet logic, intelligence processing, tagging, search, and analysis must be implemented as **deterministic, testable code that runs fully offline** — this is a legal/evidentiary system and behavior must be reproducible, not probabilistic.

- AI/LLM assistance (i.e. Claude Code, this session) is permitted **only at development time**, to write/review code. It must never leave a runtime dependency behind.
- Never add a network AI call as a "fallback" or "enhancement" to a feature, even if it seems like the easy way to solve something — not even silently, not even behind a flag.
- If a feature genuinely seems to need NLP/AI-style capability (e.g. entity extraction, classification, summarization), **flag it and propose a rule-based / deterministic / on-device approach instead.** Do not silently reach for an API call.
- Current state (audited when this rule was added): `server/_core/llm.ts` (`invokeLLM`), `server/_core/imageGeneration.ts`, and `server/_core/voiceTranscription.ts` are template scaffolding **left over from the Manus platform bootstrap and are not wired into any live route** — no router in `server/routers.ts` imports or calls them. `client/src/components/AIChatBox.tsx` likewise is only rendered on `client/src/pages/ComponentShowcase.tsx` (a component demo page), not in any real workflow. The existing entity extraction in `server/db.ts` (`extractEntitiesFromText`, used by the Intelligence module) is rule-based/regex, **not** an LLM call — that's the correct pattern to keep extending.
- Treat any future PR/diff that adds a call to `invokeLLM`, `generateImage`, `transcribeAudio`, or any other external AI SDK from a request-serving code path as a rule violation to reject, not a style nit.
- **Technically enforced, not just documented**: `.claude/settings.json` denies WebFetch/curl/wget to known AI API hosts (including `forge.manus.im`, the actual host `server/_core/llm.ts` posts to — not a generic OpenAI/Anthropic domain) and wires up `.claude/hooks/check-no-runtime-ai.sh`, which blocks any Write/Edit introducing a banned AI SDK/host/helper pattern outside `dev-tools/`, `scripts/dev/`, or a `_core` directory. `scripts/check-no-runtime-ai.sh` re-runs the same scan (text files only — `grep -I` skips binary test fixtures) as the authoritative gate in CI (`.github/workflows/no-runtime-ai.yml`, on every push/PR). The banned-pattern list matches literal SDK/package/host strings (`openai`, `anthropic`, `forge.manus.im`, ...) **and** the dead `_core` helper call sites (`invokeLLM(`, `generateImage(`, `transcribeAudio(`) — so importing one of them into a live route outside `_core` now trips both the hook and CI. If you extend this list, keep it in sync across both scripts (both enforcement scripts, `.claude/settings.json`, and this file are self-exempted by path in the hook, since they must contain these strings as declared blocklist/documentation data, not as calls).

## What this app is

RunLog is a surveillance/HUMINT "running sheet" logging system for a police operational team. Officers (identified by a **CIN** — a unique officer identifier, not a login username) log timestamped observations against **Operations**, which contain one or more **Running Sheets** (a per-day/per-shift log), which contain **Rows** (a timestamped observation with a list of CIN "members" present). Rows must be **certified** by every CIN listed on them before the row locks. Related modules: a global **Target Registry** (surveillance subjects, linkable to multiple operations), an **Intelligence** module that mines observation text for entities (people/vehicles/addresses/locations) and renders an association map, a **Governance** to-do/compliance tracker, an **Operation Manager** weekly tasking board, and a **Court** section that generates Word documents (statements, witness lists, and WIPC — Witness Identity Protection Certificate — requests).

## Versioning — bump on every merge to `main` (non-negotiable)

**Every PR merged into `main` must bump the version number**, in both places, kept in sync:

- `package.json`'s `"version"` field
- `shared/const.ts`'s `export const APP_VERSION`

This applies to all merges to `main` — features, fixes, docs, refactors — not just user-facing changes. There is no size/significance exception: every merge gets at least a patch bump. Do the bump as part of the same PR being merged (or as a final standalone "Bump version to X.Y.Z" commit immediately before merging), not as a follow-up. Before merging any branch into `main`, check whether the version has already been bumped on that branch; if not, bump it before merging.

**Which digit to bump — categorize it, don't default to patch every time:**

- **PATCH** (`1.0.X`) — the default. Bug fixes, corrections to existing behavior, copy/UI tweaks, refactors, dependency bumps, doc/CLAUDE.md changes — anything that doesn't add a capability an officer didn't already have.
- **MINOR** (`1.X.0`, resets patch to 0) — a new, backward-compatible feature or capability: a new chip/shortcut type on the running sheet, a new autocomplete, a new report/export, a new module or section, a new field on an existing form. If the change description would honestly use "add" for something genuinely new an officer can now do, it's minor, not patch.
- **MAJOR** (`X.0.0`, resets minor and patch to 0) — a breaking or structural change: a non-backward-compatible schema change, an auth/session model change, replacing how a whole module works, or anything that would require officers to be retrained or old running sheets reinterpreted differently. Expect this to almost never fire in normal feature work.

When a single PR bundles multiple changes (e.g. a new feature plus incidental fixes along the way), bump for the **highest** category present — one new feature alongside three bug fixes is a minor bump, not three separate patches.

## Architecture

**Stack:** Express + tRPC (v11) server, React 19 + Vite client, Drizzle ORM over MySQL, wouter for client routing, TanStack Query via `@trpc/react-query`, Tailwind v4 + shadcn/radix components, PWA (workbox) with an IndexedDB offline draft layer.

**Monorepo layout, one process:** `server/` (API), `client/src/` (SPA), `shared/` (types/constants used by both). Path aliases: `@/*` → `client/src/*`, `@shared/*` → `shared/*` (defined in `tsconfig.json`, `vite.config.ts`, `vitest.config.ts` — keep all three in sync if aliases change). In dev, `server/_core/index.ts` mounts Vite as Express middleware; in production it serves the built static client (`server/_core/vite.ts`).

### `_core` directories are template/platform plumbing

`server/_core/`, `client/src/_core/`, and `shared/_core/` hold **generic platform integration code** (auth/OAuth, LLM calls, image generation, voice transcription, maps proxy, file storage, notifications, cron/heartbeat, tRPC context/middleware setup). This app was bootstrapped from a "Manus" platform template — treat `_core` as scaffolding: read `references/*.md` before touching any of these integrations (OAuth redirect handling, maps/storage helpers, owner notifications, periodic/cron jobs). Notably `references/periodic-updates.md` forbids `setInterval`/`node-cron` for scheduled work — use the platform's heartbeat/agent cron endpoints instead. App-specific domain logic (everything else) lives outside `_core`. **Exception: `llm.ts`, `imageGeneration.ts`, `voiceTranscription.ts` are dead scaffolding — see the Golden Rule above, do not wire these into any live route.**

**Auth is now local, not OAuth:** despite the `_core`/Manus OAuth scaffolding still being present (and used as a fallback), day-to-day auth is username/password against the `users` table (`bcryptjs` hashing, see `auth.login`/`auth.logout` in `server/routers.ts` and `server/_core/sdk.ts#authenticateRequest`). Session state is a cookie (`COOKIE_NAME` in `shared/const.ts`), 12-hour expiry (`SESSION_EXPIRY_MS`). `users.role` is `observer | member | admin`; `adminProcedure` in `server/_core/trpc.ts` gates admin-only endpoints, `protectedProcedure` gates any logged-in user.

### Server (`server/`)

- `routers.ts` (~2800 lines) — the single tRPC `appRouter`, namespaced by domain (`auth`, `operation`, `sheet`, `row`, `member`, `certification`, `auditLog`, `target`, `targetShortcuts`, `intelligence`, `governance`, `calendar`, `statement`, `witnessList`, `wipc`, `recycleBin`, `customMarker`, `rsMapping`, `sidebar`, `reports`, `opManager`, `admin`, `adminUtils`, `users`, `export`, plus `system` from `_core/systemRouter.ts`). Add new endpoints inside the matching namespace rather than creating new top-level routers.
- `db.ts` (~4600 lines) — every DB query/mutation as a plain exported async function, organized by `// ─── Section ───` comment headers (Users, Operations, Running Sheets, Targets, Intelligence, Governance, WIPC, Recycle Bin, Op Manager, etc.). `routers.ts` imports these functions rather than querying Drizzle directly. Follow this split when adding features: query logic in `db.ts`, request/response shape + auth checks in `routers.ts`.
- `*Generator.ts` (`statDecGenerator.ts`, `wipcRequestGenerator.ts`, `witnessListGenerator.ts`, `statementGenerator.ts`) — build `.docx` files with the `docx` package for court output.
- `wipcVault.ts` — encrypt/decrypt helpers for sensitive WIPC member data at rest.
- `storage.ts` — file storage helper (see `references/file-storage.md`); don't hand-roll upload/URL logic.

### Data model conventions (`drizzle/schema.ts`)

- **Soft delete, not hard delete**, for `operations`, `runningSheets`, `targets`, `customMapMarkers`: a nullable `deletedAt` (bigint ms timestamp) + `deletedByCIN`. Always filter live queries with `isNull(table.deletedAt)`; there's a Recycle Bin (`recycleBin` router / `getRecycleBinItems`) to reinstate or the record purges after expiry (`purgeExpiredRecycleBinItems`).
- **Audit trail**: significant mutations call `createAuditLog` (see `auditLogs` table / `auditLog` router) — follow this pattern for new mutating endpoints that touch operational data.
- **CIN, not user id, is the human-facing identity** stored on rows/certifications/audit entries (`memberName`, `certifiedByCIN`, `deletedByCIN`, etc.) so history reads correctly even if a user record changes.
- Timestamps are inconsistently typed across the schema — some columns are Drizzle `timestamp` (`createdAt`/`updatedAt`), others are `bigint` ms epoch (`deletedAt`, `closedAt`, `certifiedAt`). Check the column type before formatting/comparing.
- **Street types are always written in full** — "Street", "Road", "Avenue", never "St", "Rd", "Ave" — in everything the app writes or shows: Quick Entry addresses and their bracket short forms, card/chip sentences, known-address suggestions, map and Intelligence labels. `shared/streetTypes.ts` (`fullStreetTypes`) is the single rule (only expands the last word of a number-led street or an intersection, so "St Kilda"/"Dr Smith" are safe); apply it at the point text is produced, don't hand-roll abbreviations. Rows officers already typed are never rewritten — Check Sheet flags an abbreviation (`street-type-abbreviated`) with a one-tap fix. Place matching (`samePlace`) treats short and long forms as the same place.
- Server timezone is forced to `Australia/Perth` at the top of `server/_core/index.ts` — this must stay the very first executable line (before any `Date`-touching code runs) since running sheets are time-sensitive legal records.
- Migrations: `drizzle/*.sql` are numbered, auto-named by drizzle-kit (e.g. `0036_long_gertrude_yorkes.sql`). Never hand-edit an already-applied migration; run `pnpm db:push` to generate + apply a new one after changing `drizzle/schema.ts`.

### Client (`client/src/`)

- Routing is `wouter` (`App.tsx`), not React Router. Most routes render inside `DashboardLayout`; sidebar order is user-configurable and persisted server-side (`sidebar` router).
- Data fetching goes through the tRPC React Query client (`lib/trpc.ts`) — don't add a second fetch layer.
- **Offline-first draft mode**: `lib/offlineStore.ts` (IndexedDB via `idb`) persists draft operations/targets/sheets/rows with local UUIDs when offline, and `lib/offlineSync.ts` replays a queue against the server on reconnect, remapping local IDs to server IDs as it goes (`OfflineContext`, `useOfflineMutations`, `DraftModeBanner`, `DraftHubPage`/`DraftSheetPage`). If you touch sheet/row creation, check whether the offline draft path also needs updating — it duplicates the shape of the equivalent server mutations.
- `pages/Intelligence*` and `pages/RSMapping*`/`IntelligenceMapping.tsx` are large (`IntelligenceMapping.tsx` is 4000+ lines) map/entity-extraction views; `lib/markerSvgs.ts` and `components/Map.tsx` back the map rendering (Google Maps via the platform's maps proxy — see `references/maps-integration.md`, never request API keys from users or use a third-party map library).
- **Resolved — `AdvancedMarkerElement` positioning drift, migrated to `OverlayView`**: `google.maps.marker.AdvancedMarkerElement` had a confirmed, reproducible positioning-drift bug — its on-screen position visibly separated from its true lat/lng the further the map was zoomed from wherever it was last drawn, correcting back to accurate near that original zoom level. Confirmed present under both a real vector Map ID and a real raster Map ID (see `components/Map.tsx`'s `MAP_ID_VECTOR`/`MAP_ID_RASTER`), so it wasn't a rendering-mode/Map-ID issue. Not fixable from outside the class: forcing a fresh `.position` assignment, or even a full detach/reattach (`.map = null` then `.map = map`) on the map's `idle` event, didn't stop it — `AdvancedMarkerElement` recalculates its position continuously as part of the map's own render loop during a gesture, not once at the end, so any one-shot correction got overwritten by the very next frame. **Fixed** by migrating all five overlay call sites (custom map markers, shape note-labels, live team member pins, intel pins, and the address search pin) in `IntelligenceMapping.tsx` to a shared `DivIconOverlay` class (`lib/divIconOverlay.ts`), built on `google.maps.OverlayView` — the same overlay mechanism `Circle`/`Rectangle`/`Polygon`/`Polyline` shapes use, which is why shapes never drifted. It recomputes its pixel position from the map's live projection on every redraw instead of trusting cached internal state. `DivIconOverlay` mirrors `AdvancedMarkerElement`'s API shape closely (`.map`/`.position`/`.content`/`.zIndex`/`.title`/`.gmpDraggable` get/set properties, `.addListener(...)` inherited from `google.maps.MVCObject` — do not replace it with a custom shim) and hand-rolls the two behaviours `OverlayView` doesn't provide natively: drag-to-move (via pointer events + `projection.fromDivPixelToLatLng`) and an `anchor: "center" | "none"` option (`"none"` for shape note-labels, whose pill content sets its own offset transform directly rather than being centred on its anchor point). The previous `AdvancedMarkerElement` implementation stays intact in git history (see the commits migrating each overlay type, prior to this note being updated), so reverting to it is a reasonable option to revisit if it's ever needed (e.g. a future Google Maps JS API release changing this trade-off) — not a rewrite from scratch.

**Vehicle lists (v1.193.0)** — vehicles written one after another in an observation are punctuated as a list: two get "and" (`A and B`), three or more get commas with "and" before the last and no comma before it (`A, B and C`). The pure rule is `shared/vehicleList.ts` (tested in `server/vehicleList.test.ts`): a vehicle ends at its `(Vehicle REGO)` bracket and what sits between two brackets must look like the next vehicle's description (a bare rego, "…, bearing WA registration …", or empty — narrative, a new line or sentence punctuation between them leaves it alone, and a gap that opens with a body-type word like "station sedan" is the previous vehicle's own description). A list with any unpunctuated link is rewritten in full, so one that grew a vehicle at a time becomes `A, B and C`. **Articles (v1.194.0):** every *described* vehicle in a list also gets `a` / `an` in front (a capital `A` / `An` when it opens a sentence or the observation; a vehicle that is just a rego gets none; an existing article is kept; the colour is lower-cased) — `A white Lexus …, a white Toyota … and a silver Ford …`. The first vehicle's description start is found by looking back in its sentence for a colour-led run of plain words up to `, bearing …`, so narrative before it is left alone. A list that is already fully right is never touched. Applied live on Space right after a vehicle bracket and when the field loses focus — in `ObservationCell` (`SheetDetail.tsx`) and the RS Quick Entry textarea (`IntelligenceMapping.tsx`, also at submit) — and again at save time in `normalizeObservationPunctuation` (`server/db.ts`), whose Rule 1 (comma after every `(Vehicle …)` bracket) skips the bracket in front of a list's final "and". Check Sheet flags older rows (`vehicle-list-unpunctuated`, one finding per list, one-tap fix) via `checkVehicleLists` in `server/sheetCheck.ts`. Locked rows are never changed.

**Observation tidy-up (v1.195.0)** — one pass over text an officer *typed*, doing what they'd otherwise fix by hand: a capital at the start, after each full stop and at the start of each line; one space between words; a space after a comma that has none (`1,000` untouched); and a full stop at the end (only on click-out, and only for 2+ words). The pure rule is `shared/observationTidy.ts` (`tidyObservation`, `tidyObservationAtCaret`, `justTypedSpaceAfterBracket`; tested in `server/observationTidy.test.ts`); it runs `joinVehicleLists` first so vehicle lists and tidy-up agree. It never lower-cases or rewrites wording and leaves alone: a bare "tv", a sentence opening with a colour phrase, a rego/number or inner-capital token (iPhone), text after abbreviations (etc, cnr, st…) or a single-capital initial, and anything inside brackets. **Chips, shortcuts, pre-typed sentences and Target Logger text are never changed**: it runs only on typing — `ObservationCell` (`SheetDetail.tsx`) tidies on blur only if the draft differs from the saved value, and the RS Quick Entry textarea only if `rsInlineTypedRef` (set in the textarea `onChange`, reset on close) is true, otherwise just `joinVehicleLists` as before. Triggers: Space after a `)` and click-out. Deliberately **not** added to the server's `normalizeObservationPunctuation`. Considered and not built: tagging each chip with a phrase kind (sentence / noun phrase / name) so back-to-back chips could be joined — it would alter chip output.

**Joining words between pieces (v1.196.0)** — part of the observation tidy-up, automatic, same triggers (Space after a bracket, click-out) and same "only text that was edited" guard. The pure rule is `shared/sentenceJoin.ts` (`sentenceJoinEdits`, `wholeSentenceChips`; tests in `server/sentenceJoin.test.ts`), run by `tidyObservation` / `tidyObservationAtCaret` after the vehicle lists and before the capitals/spacing rules; `joinObservationPieces` is the joining without the capitals/full-stop fixes, used for Quick Entry text made only from chips. It only ever fills the **gap** between two pieces and never rewrites, removes or re-cases a word: (1) a **full stop** between two whole sentences — a whole-sentence phrase (built-ins: Surveillance commenced / Surveillance ceased / Out of sight / Continued out of sight / PHOTOGRAPH/S TAKEN, plus any shortcut expansion that is plain capitalised words, 2–6 words, not ending on a joining word, no brackets/commas/digits/[blanks]) followed by a capitalised word that isn't a joining word (after "Surveillance commenced/ceased" only if the next word plainly opens a sentence, since a place may follow); (2) **"at"** between "Surveillance commenced/ceased" and a street address (digit-led, full street type); (3) **"and" / commas** between people introduced back to back as `Given SURNAME (SURNAME)` — `A and B`, `A, B and C` — a capitalised sentence opener (Seen, Then, Vehicle…) is never taken for a given name. The comma after a `(Vehicle …)` bracket already happens at save (`normalizeObservationPunctuation`), so it is not repeated here. Target Logger buttons make whole new rows and are never joined; `[route]`-style blanks are never touched. The shortcuts the main sheet and Quick Entry pass in (`sentenceChips`) come from the Shortcuts page. To add a rule, add it to `sentenceJoinEdits` with a test, and keep it to filling a gap. **Fourth rule (v1.200.1):** "continued out of sight" straight after the place someone entered (`enteredPlaceEdits`) — "entered Crooked Spire Coffee & Art House Midland continued out of sight" → "… Midland **and** continued out of sight" (a capitalised "Continued out of sight" gets a full stop instead). It only fires when everything between the last "entered" in the sentence and the phrase is plainly a place (capitalised words, numbers, "&", an optional leading "the" and a bracketed short form) — "entered the car park", "SANTOS continued out of sight" and anything already joined are left alone; the comma in "…the car park, entered" is not touched. **Fifth rule (v1.200.4):** "A" / "An" before a single full vehicle that opens its sentence (`vehicleArticleEdits`) — "white Lexus NX350h station sedan, bearing WA registration 1TDM414 (Vehicle 1TDM414), parked…" → "A white Lexus …". It needs the same shape the list rule looks for (a colour-led description running up to ", bearing … (Vehicle …)") at the very start of the sentence, observation or line; a description with an article already, one with narrative before it ("Seen leaving in white Lexus…", "Observed …") or no colour is left alone, a capitalised colour is lower-cased, and a vehicle that is part of a list is left to the list rule (no double article). Check Sheet does not flag older rows for this. **Entity extraction (v1.196.1):** the joining does not change what `extractEntitiesFromText` finds (same people, vehicles and places before and after — tested in `server/sentenceJoin.test.ts`); the only effect was a joining word or comma leaking to the front of a person's `fullDescription` ("and Karim Elias NAJJAR"), which extraction now strips for persons (this also fixed hand-typed lists).

## Commands (regions), sharing and Region Search

Five fixed **Commands** — Western, Northern, Eastern, Southern, Central (`shared/commands.ts`, colours in `client/src/lib/commandStyle.ts`: gold / maroon / sky blue / dark blue / red). `operations.command` says which Command owns an operation; `users.command` is a person's home Command (the Add User "Unit — Command" dropdown replaces the old free-text Unit; only an all-region admin can put someone in another Command); `users.allRegions` marks an **all-region admin** (sees every Command, can open restricted operations). Everything existing landed in `WESTERN` on migration, so a single-Command deployment behaves exactly as before. Merged to `main` at v1.188.x.

**The access rule — one place** (`shared/operationAccess.ts`): your own Command's operations are fully yours (your role still limits what you can DO); another Command's operation is reachable only if an admin of the **owning Command** shared it with you **by name** (`operation_shares`: one operation, or every operation that Command owns) at the same levels as the usual access — **Investigator** (the Mapping page only; stored as share level `investigator`, numeric level 0 so the normal guard opens nothing, picked up by `mapOnlyOperationIds` and only the `MAP_VIEW_PATHS` reads + `operation.listForMap`) / **Observer** (`view`, read) / **Full Access** (`log`, also add rows, certify) / **Full Access + User Management** (`manage`, also edit the operation — it does not grant user management). An Observer is held to View. Shares are made on Access Management (`admin.createShares`/`revokeShare`/`listShares`/`userShares`, `components/admin/*`: team groups, Visiting access, Share with + searchable person picker, "Shared access" card on a profile). Only an admin of the owning Command (or an all-region admin) may share/revoke; an admin manages only their own Command's people.

**Enforcement** (`server/operationAccess.ts`, run from the `requireUser` middleware in `server/_core/trpc.ts` on every signed-in procedure): a single operation / sheet / row / member / attachment id the person can't reach → FORBIDDEN (queries need View, mutations Log, `operation.update/delete` Manage); lists (`operationIds`, `sheetIds`) are trimmed; map-style lists with no operations named are filled with "what I can reach". The operation lists, sheet list, to-do lists, deep search and Target Registry are filtered. **Intelligence has two scopes** (per-request `AsyncLocalStorage`, `server/intelScope.ts`, honoured by `getAllIntelligenceEntities()`): *browsing* (the Intelligence Folder lists, maps, reports — every procedure except the four below) shows only the entities of operations you can reach, so a Command's Folder is its own plus anything shared with it; *opening one entity's profile* (`intelligence.targetProfile/associateProfile/vehicleProfile/locationProfile` — what Region Search's "Open in Intelligence" does) is more open: any operation except another Command's **Restricted** one. Region Search itself asks for the unscoped set (`{ unscoped: true }`). Anyone who can reach everything skips all of it. **Coverage audit (v1.176.3)** — every procedure was reviewed against the guard. *Guarded by id*: operation, sheet, row, member, attachment (and its entity links), SMEAC/UCO briefings, map markers and shapes, Recycle Bin items (by type), `export.sheetData`, and **targets** — a target belongs to the operations it is linked to (readable if it has none or any is open in the profile scope; changing one needs Log on one of its operations) — with associates and target shortcuts following their target. *Filtered lists*: operations, sheets, to-dos, deep search, Target Registry, calendar, briefings, audit log (sheet entries by operation; system entries admin-only), incomplete-sheets / weekly-activity / outstanding-to-do reports, Recycle Bin, attachment counts, photos by entity, live team locations and their history (one stricter rule, `canSeeLivePin` in `shared/operationAccess.ts`: your own Command's people, visitors your Command hosts, and people who genuinely reach the same operation — no all-region exemption, and the operations a pin is tagged with only count if its owner really belongs on them), entity merges, pin overrides, WIPC members (by the Command of the admin who created them). System-wide `adminUtils.*` need an all-region admin. **Still Command-agnostic by design, needs a decision before relying on it**: `users.listForCin` (names and CINs of everyone, so officers can be added to rows), and the Add Target "possible duplicate" prompt (searches the whole Target Registry, like Region Search). If the guard's database read fails the request fails (fail-closed).

**CTO Roster and the Op Manager weekly tasking board are per-Command (v1.186.0, migration 0120).** Each Command has its own roster (teams, members, shifts, secondments, drafts, saved rosters, Outlook minimums, audit log) and its own tasking board (priority rows, tasking grid, supervisor contacts, posted weeks) and Weekly Tasking Report; Eastern's can't be seen or changed by Western. `command` (default `WESTERN`, so everything that existed landed there) is on the root tables: `cto_roster_teams` (name unique per Command), `cto_roster_members` (a person has at most one place per Command's roster — unique on `(command, cin)`; **a visitor** from another Command, i.e. someone it shared an operation with by name or put in one of its teams (`visitorUserIdsOf` in `db.ts`), can be on that host Command's roster as well as their own, via `ctoRoster.members.candidates` / `addCtoRosterMember`'s eligibility check, and "My Shifts" merges every roster they are on; anyone else from another Command is refused with a message pointing at Share with), `cto_roster_drafts`, `cto_roster_saved_rosters`, `cto_roster_audit_log`, `cto_roster_outlook_settings` (one row per Command) and the four `op_manager_*` tables; shifts and secondments follow their member, draft/saved-roster children follow their parent. `shared/rosterCommand.ts` resolves which Command a request works on: the person's own, except an **all-region admin** may pick another via the `x-runlog-roster-command` header (the picker bar `RosterCommandBar` on the CTO Roster / Op Manager / Weekly Tasking pages stores the pick in `localStorage` and reloads). Two layers, both in `server/rosterContext.ts` / `server/rosterScope.ts`: the tRPC `rosterScopeMiddleware` runs every request inside a per-request scope that `server/ctoRoster.ts` and the Op Manager functions in `db.ts` read (`rosterCommand()` filters lists, `rosterCommandForWrite()` stamps new rows; no request = internal call, unfiltered), and `enforceRosterAccess` refuses any roster id from another Command (`ROSTER_ID_REFS`: path → input fields; `server/rosterScope.test.ts` fails if a new `ctoRoster.*` procedure takes a member/team/draft/saved-roster id and isn't listed). **Adding a roster/tasking endpoint: filter by `rosterCommand()` in the data function and add its id fields to `ROSTER_ID_REFS`.** The generic operation guard no longer reads a `ctoRoster.*` `memberId` as a running-sheet row member. Deliberately still shared: the EA compliance **rules** (company-wide settings) and `opManager.listUsers` (SMEAC/UCO briefings use it for recipients, which can cross Commands).

**Command features — per-Command on/off switches (v1.188.0, migration 0122).** The owner (`COMMAND_FEATURES_OWNER_CIN` = `"459"`, and role admin — `isFeatureOwner` in `shared/commandFeatures.ts`; nobody else sees or changes them, server included) switches **CTO Weekly Tasking** (`tasking`), **CTO Roster** (`roster`), **Import Target** (`import`) and **Vehicle Crash** (`crash`) on or off for each Command from the **Command features** card at the bottom of Access Management (`components/admin/CommandFeaturesCard.tsx`, `commandFeatures.all/set`). `command_features` stores only what was changed (no row = on; unique per Command + feature); changes write a `command_feature_changed` audit entry. A Command's own people get their switches with `auth.me` (`features`, `isFeatureOwner`; `useCommandFeatures` / `useCommandFeature` in `lib/commandFeatures.ts`); an **all-region admin always keeps every feature**. Enforced twice: the tRPC `rosterScopeMiddleware` calls `enforceFeatureAccess` (`server/commandFeatures.ts`, 2-second cache) using `featureForPath` (`ctoRoster.*` → roster; `opManager.*` except `opManager.listUsers` and `reports.weeklyTasking` → tasking; `target.registry.parseDocument` → import) and answers FORBIDDEN; the screens hide the menu entries (both sidebar renderings in `DashboardLayout.tsx`), show "isn't turned on" for the page (`gatedByFeature` in `App.tsx`), and hide the Import Target button. Vehicle Crash makes no server calls, so it is hidden on screen only. Nothing is deleted when a feature is off. **Adding a switchable feature: add its key to `FEATURES`/`FEATURE_KEYS`, map its procedures in `featureForPath`, then hide its menu entries and gate its route.**

**Region Search** (small button in the Intelligence Folder header, where Merge Entities used to be; `client/src/components/RegionSearch.tsx`, `intelligence.regionSearch`, pure logic in `shared/regionSearch.ts`): finds a person/vehicle/address across every Command. Everyone signed in sees the same matches and details (role, operations, "Contact <Command>" — plain text). The only difference is **Open in Intelligence**: an operation marked **Restricted** (`operations.restricted`, admin-only to set; tick on New/Edit Operation) can only be opened from its own Command, by an all-region admin, or by someone it was shared with. Deterministic matching — no AI.

**Teams are per-Command records** (`teams` table: `command`, `name`, `colour`, `aiPhones` JSON, `sortOrder`; `users.teamId` points at one — migration 0115 turned the old fixed TEAM1/TEAM2/PTT enum into Western's three teams and carried everyone across; the old `users.team` column is kept as `legacyTeam` for rollback only and is never read or written). An admin manages their own Command's teams from the **+ Team** button on Access Management (`admin.createTeam/updateTeam/deleteTeam`; deleting a team moves its members to "No team"; a person can only be given a team of their own Command, and moving Command clears it). `users.listTeams` returns the caller's Command's teams (all-region admins: every Command's); `client/src/lib/teams.ts` (`useTeams`, `useMyTeams`) is the single client reader. Screens that follow teams: Access Management groups, Add/Edit User, the roster "Add team" buttons on sheets and operations, the Incomplete Sheets "by team" report, the Mapping page's live-team pin colours and team list, and the Crash Helper's Assumed Identity phones. **Visiting from Commands** (Access Management, collapsed section under Teams: **Share** — give people in other Commands operations — and **Members**) also lets the hosting Command put each visitor in one of *its own* teams (`visitor_team_assignments`: userId + hosting Command → teamId, migration 0116; `admin.setVisitorTeam`/`listVisitorTeams`, the "+ New team…" option makes a team and assigns it in one step). `users.teamId` is never touched, so the visitor keeps their home team and the hosting Command sees them in theirs; the assignment goes when the team is deleted or the last share from that Command is revoked. `visitorTeamMap(command)` in `db.ts` is the single "effective team" lookup, used by `users.listForCin` (roster "Add team" buttons), the Incomplete Sheets / Outstanding Actions reports and the live-map team pins — use it for any new screen that groups by team on the hosting Command's side. **Map Settings → Teams (v1.183.0)**: each team has `mapVisibility` (`always` — Team 1, Team 2, PTT, Capability and any temporary team an admin adds, shown until deleted — or `online`, shown only while someone in it is logged in) and `forceShare` (members' Show & Share switches on at login and is locked on; the server also ignores a switch-off). Both are set in the Team dialog; migration 0118 set Admin/Administration to online and Investigators to online + forceShare by name. The rule is `shared/teamMap.ts`: "logged in" = active within `ONLINE_WINDOW_MS` (15 min — `users.lastSignedIn` is stamped on every signed-in request), read through `users.teamsWithOnlineMembers`; `auth.me` carries `mustShareLocation` (map-only Investigator accounts can't list teams), `ForcedLocationSharing` keeps the flag on app-wide, and the Map page locks the switch. **Deliberately separate for now (will be linked later):** the CTO Roster's own teams (`cto_roster_teams`) and Op Manager's typed role names.

## Zeroing the data (go-live reset)

`scripts/ops/zero-data.mjs` empties the operational data so every Command starts at zero. Run it from the app folder (e.g. `/opt/runlog`) with the app **stopped**: `node scripts/ops/zero-data.mjs` is a dry run (row counts only); `--execute` takes a `mysqldump` backup into `backups/` (aborts if the backup fails), asks you to type the database name, truncates the tables (numbering restarts at 1), moves the on-disk `uploads/` folder aside to `uploads.pre-zero-<time>/` (remote storage is left alone), then checks every cleared table is empty and every kept table is unchanged. **Kept:** users, teams, Command features, shortcuts, style guides, sidebar orders, WIPC officer profiles and the vault key check, and the **whole CTO Roster** (all `cto_roster_*` tables). **Cleared:** operations, sheets, rows, attachments, targets and associates, intelligence data, map data, WIPC members, briefings, the Op Manager tasking board, notifications and the audit log. `scripts/ops/zero-data-tables.mjs` classifies every table; the script refuses to run when a table is in neither list, and `server/zeroDataTables.test.ts` fails when a table added to `drizzle/schema.ts` isn't classified — **a new table must be added to KEEP_TABLES or CLEAR_TABLES.**

**Confirmed direction, not yet scheduled: this is intended to eventually be wrapped in a native shell (Capacitor or equivalent) to support hands-free wake-word activation** — browsers don't allow background microphone access or an always-listening keyword spotter while the app isn't foregrounded, so that mode is a separate, later, native-app-only project (App Store/MDM distribution, a custom native keyword-spotter plugin, background-audio entitlements). The web-only tap-to-talk build should not assume or block on this — build it as a normal PWA feature — but don't reach for a browser-only voice API or library that would need to be thrown away when the native wrap happens; prefer approaches that would still work (or port cleanly) inside a Capacitor WebView.
