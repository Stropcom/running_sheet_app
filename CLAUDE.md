# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## 🚫 GOLDEN RULE — No runtime AI/LLM calls (non-negotiable)

This app must **never** call any external AI/LLM API (OpenAI, Anthropic, Google, etc.) during operational runtime. All running-sheet logic, intelligence processing, tagging, search, and analysis must be implemented as **deterministic, testable code that runs fully offline** — this is a legal/evidentiary system and behavior must be reproducible, not probabilistic.

- AI/LLM assistance (i.e. Claude Code, this session) is permitted **only at development time**, to write/review code. It must never leave a runtime dependency behind.
- Never add a network AI call as a "fallback" or "enhancement" to a feature, even if it seems like the easy way to solve something — not even silently, not even behind a flag.
- If a feature genuinely seems to need NLP/AI-style capability (e.g. entity extraction, classification, summarization), **flag it and propose a rule-based / deterministic / on-device approach instead.** Do not silently reach for an API call.
- Current state (audited when this rule was added): `server/_core/llm.ts` (`invokeLLM`), `server/_core/imageGeneration.ts`, and `server/_core/voiceTranscription.ts` are template scaffolding **left over from the Manus platform bootstrap and are not wired into any live route** — no router in `server/routers.ts` imports or calls them. `client/src/components/AIChatBox.tsx` likewise is only rendered on `client/src/pages/ComponentShowcase.tsx` (a component demo page), not in any real workflow. The existing entity extraction in `server/db.ts` (`extractEntitiesFromText`, used by the Intelligence module) is rule-based/regex, **not** an LLM call — that's the correct pattern to keep extending.
- Treat any future PR/diff that adds a call to `invokeLLM`, `generateImage`, `transcribeAudio`, or any other external AI SDK from a request-serving code path as a rule violation to reject, not a style nit.
- **Technically enforced, not just documented**: `.claude/settings.json` denies WebFetch/curl/wget to known AI API hosts (including `forge.manus.im`, the actual host `server/_core/llm.ts` posts to — not a generic OpenAI/Anthropic domain) and wires up `.claude/hooks/check-no-runtime-ai.sh`, which blocks any Write/Edit introducing a banned AI SDK/host/helper pattern outside `dev-tools/`, `scripts/dev/`, or a `_core` directory. `scripts/check-no-runtime-ai.sh` re-runs the same scan (text files only — `grep -I` skips binary test fixtures) as the authoritative gate in CI (`.github/workflows/no-runtime-ai.yml`, on every push/PR). The banned-pattern list matches literal SDK/package/host strings (`openai`, `anthropic`, `forge.manus.im`, ...) **and** the dead `_core` helper call sites (`invokeLLM(`, `generateImage(`, `transcribeAudio(`) — so importing one of them into a live route outside `_core` now trips both the hook and CI. If you extend this list, keep it in sync across both scripts (both enforcement scripts, `.claude/settings.json`, and this file are self-exempted by path in the hook, since they must contain these strings as declared blocklist/documentation data, not as calls).

## What this app is

RunLog is a surveillance/HUMINT "running sheet" logging system for a police operational team. Officers (identified by a **CIN** — a unique officer identifier, not a login username) log timestamped observations against **Operations**, which contain one or more **Running Sheets** (a per-day/per-shift log), which contain **Rows** (a timestamped observation with a list of CIN "members" present). Rows must be **certified** by every CIN listed on them before the row locks. Related modules: a global **Target Registry** (surveillance subjects, linkable to multiple operations), an **Intelligence** module that mines observation text for entities (people/vehicles/addresses/locations) and renders an association map, a **Governance** to-do/compliance tracker, an **Operation Manager** weekly tasking board, and a **Court** section that generates Word documents (statements, witness lists, and WIPC — Witness Identity Protection Certificate — requests).

## Versioning — bump on every merge to `main` (non-negotiable)

**Every PR merged into `main` must bump the version number**, in both places, kept in sync:

- `package.json`'s `"version"` field
- `shared/const.ts`'s `export const APP_VERSION`

This applies to all merges to `main` — features, fixes, docs, refactors — not just user-facing changes. There is no size/significance exception: every merge gets at least a patch bump. Do the bump as part of the same PR being merged (or as a final standalone "Bump version to X.Y.Z" commit immediately before merging), not as a follow-up. Before merging any branch into `main`, check whether the version has already been bumped on that branch; if not, bump it before merging.

**Which digit to bump — categorize it, don't default to patch every time:**

- **PATCH** (`1.0.X`) — the default. Bug fixes, corrections to existing behavior, copy/UI tweaks, refactors, dependency bumps, doc/CLAUDE.md changes — anything that doesn't add a capability an officer didn't already have.
- **MINOR** (`1.X.0`, resets patch to 0) — a new, backward-compatible feature or capability: a new chip/shortcut type on the running sheet, a new autocomplete, a new report/export, a new module or section, a new field on an existing form. If the change description would honestly use "add" for something genuinely new an officer can now do, it's minor, not patch.
- **MAJOR** (`X.0.0`, resets minor and patch to 0) — a breaking or structural change: a non-backward-compatible schema change, an auth/session model change, replacing how a whole module works, or anything that would require officers to be retrained or old running sheets reinterpreted differently. Expect this to almost never fire in normal feature work.

When a single PR bundles multiple changes (e.g. a new feature plus incidental fixes along the way), bump for the **highest** category present — one new feature alongside three bug fixes is a minor bump, not three separate patches.

## Architecture

**Stack:** Express + tRPC (v11) server, React 19 + Vite client, Drizzle ORM over MySQL, wouter for client routing, TanStack Query via `@trpc/react-query`, Tailwind v4 + shadcn/radix components, PWA (workbox) with an IndexedDB offline draft layer.

**Monorepo layout, one process:** `server/` (API), `client/src/` (SPA), `shared/` (types/constants used by both). Path aliases: `@/*` → `client/src/*`, `@shared/*` → `shared/*` (defined in `tsconfig.json`, `vite.config.ts`, `vitest.config.ts` — keep all three in sync if aliases change). In dev, `server/_core/index.ts` mounts Vite as Express middleware; in production it serves the built static client (`server/_core/vite.ts`).

### `_core` directories are template/platform plumbing

`server/_core/`, `client/src/_core/`, and `shared/_core/` hold **generic platform integration code** (auth/OAuth, LLM calls, image generation, voice transcription, maps proxy, file storage, notifications, cron/heartbeat, tRPC context/middleware setup). This app was bootstrapped from a "Manus" platform template — treat `_core` as scaffolding: read `references/*.md` before touching any of these integrations (OAuth redirect handling, maps/storage helpers, owner notifications, periodic/cron jobs). Notably `references/periodic-updates.md` forbids `setInterval`/`node-cron` for scheduled work — use the platform's heartbeat/agent cron endpoints instead. App-specific domain logic (everything else) lives outside `_core`. **Exception: `llm.ts`, `imageGeneration.ts`, `voiceTranscription.ts` are dead scaffolding — see the Golden Rule above, do not wire these into any live route.**

**Auth is now local, not OAuth:** despite the `_core`/Manus OAuth scaffolding still being present (and used as a fallback), day-to-day auth is username/password against the `users` table (`bcryptjs` hashing, see `auth.login`/`auth.logout` in `server/routers.ts` and `server/_core/sdk.ts#authenticateRequest`). Session state is a cookie (`COOKIE_NAME` in `shared/const.ts`), 12-hour expiry (`SESSION_EXPIRY_MS`). `users.role` is `observer | member | admin`; `adminProcedure` in `server/_core/trpc.ts` gates admin-only endpoints, `protectedProcedure` gates any logged-in user.

Add new endpoints inside the matching namespace rather than creating new top-level routers.
- `db.ts` (~4600 lines) — every DB query/mutation as a plain exported async function, organized by `// ─── Section ───` comment headers (Users, Operations, Running Sheets, Targets, Intelligence, Governance, WIPC, Recycle Bin, Op Manager, etc.). `routers.ts` imports these functions rather than querying Drizzle directly. Follow this split when adding features: query logic in `db.ts`, request/response shape + auth checks in `routers.ts`.
- `*Generator.ts` (`statDecGenerator.ts`, `wipcRequestGenerator.ts`, `witnessListGenerator.ts`, `statementGenerator.ts`) — build `.docx` files with the `docx` package for court output.

- `storage.ts` — file storage helper (see `references/file-storage.md`); don't hand-roll upload/URL logic.

### Data model conventions (`drizzle/schema.ts`)

- **Soft delete, not hard delete**, for `operations`, `runningSheets`, `targets`, `customMapMarkers`: a nullable `deletedAt` (bigint ms timestamp) + `deletedByCIN`. Always filter live queries with `isNull(table.deletedAt)`; there's a Recycle Bin (`recycleBin` router / `getRecycleBinItems`) to reinstate or the record purges after expiry (`purgeExpiredRecycleBinItems`).
- **Audit trail**: significant mutations call `createAuditLog` (see `auditLogs` table / `auditLog` router) — follow this pattern for new mutating endpoints that touch operational data.
- **CIN, not user id, is the human-facing identity** stored on rows/certifications/audit entries (`memberName`, `certifiedByCIN`, `deletedByCIN`, etc.) so history reads correctly even if a user record changes.
- Timestamps are inconsistently typed across the schema — some columns are Drizzle `timestamp` (`createdAt`/`updatedAt`), others are `bigint` ms epoch (`deletedAt`, `closedAt`, `certifiedAt`). Check the column type before formatting/comparing.
- **Street types are always written in full** — "Street", "Road", "Avenue", never "St", "Rd", "Ave" — in everything the app writes or shows: Quick Entry addresses and their bracket short forms, card/chip sentences, known-address suggestions, map and Intelligence labels. `shared/streetTypes.ts` (`fullStreetTypes`) is the single rule (only expands the last word of a number-led street or an intersection, so "St Kilda"/"Dr Smith" are safe); apply it at the point text is produced, don't hand-roll abbreviations. Rows officers already typed are never rewritten — Check Sheet flags an abbreviation (`street-type-abbreviated`) with a one-tap fix. Place matching (`samePlace`) treats short and long forms as the same place.
- Server timezone is forced to `Australia/Perth` at the top of `server/_core/index.ts` — this must stay the very first executable line (before any `Date`-touching code runs) since running sheets are time-sensitive legal records.
- Migrations: `drizzle/*.sql` are numbered, auto-named by drizzle-kit (e.g. `0036_long_gertrude_yorkes.sql`). Never hand-edit an already-applied migration; run `pnpm db:push` to generate + apply a new one after changing `drizzle/schema.ts`.

### Client (`client/src/`)

- Routing is `wouter` (`App.tsx`), not React Router. Most routes render inside `DashboardLayout`; sidebar order is user-configurable and persisted server-side (`sidebar` router).
- Data fetching goes through the tRPC React Query client (`lib/trpc.ts`) — don't add a second fetch layer.
- **Offline-first draft mode**: `lib/offlineStore.ts` (IndexedDB via `idb`) persists draft operations/targets/sheets/rows with local UUIDs when offline, and `lib/offlineSync.ts` replays a queue against the server on reconnect, remapping local IDs to server IDs as it goes (`OfflineContext`, `useOfflineMutations`, `DraftModeBanner`, `DraftHubPage`/`DraftSheetPage`). If you touch sheet/row creation, check whether the offline draft path also needs updating — it duplicates the shape of the equivalent server mutations.
- `pages/Intelligence*` and `pages/RSMapping*`/`IntelligenceMapping.tsx` are large (`IntelligenceMapping.tsx` is 4000+ lines) map/entity-extraction views; `lib/markerSvgs.ts` and `components/Map.tsx` back the map rendering (Google Maps via the platform's maps proxy — see `references/maps-integration.md`, never request API keys from users or use a third-party map library).
- **Resolved — `AdvancedMarkerElement` positioning drift, migrated to `OverlayView`**: `google.maps.marker.AdvancedMarkerElement` had a confirmed, reproducible positioning-drift bug — its on-screen position visibly separated from its true lat/lng the further the map was zoomed from wherever it was last drawn, correcting back to accurate near that original zoom level. Confirmed present under both a real vector Map ID and a real raster Map ID (see `components/Map.tsx`'s `MAP_ID_VECTOR`/`MAP_ID_RASTER`), so it wasn't a rendering-mode/Map-ID issue. Not fixable from outside the class: forcing a fresh `.position` assignment, or even a full detach/reattach (`.map = null` then `.map = map`) on the map's `idle` event, didn't stop it — `AdvancedMarkerElement` recalculates its position continuously as part of the map's own render loop during a gesture, not once at the end, so any one-shot correction got overwritten by the very next frame. **Fixed** by migrating all five overlay call sites (custom map markers, shape note-labels, live team member pins, intel pins, and the address search pin) in `IntelligenceMapping.tsx` to a shared `DivIconOverlay` class (`lib/divIconOverlay.ts`), built on `google.maps.OverlayView` — the same overlay mechanism `Circle`/`Rectangle`/`Polygon`/`Polyline` shapes use, which is why shapes never drifted. It recomputes its pixel position from the map's live projection on every redraw instead of trusting cached internal state. `DivIconOverlay` mirrors `AdvancedMarkerElement`'s API shape closely (`.map`/`.position`/`.content`/`.zIndex`/`.title`/`.gmpDraggable` get/set properties, `.addListener(...)` inherited from `google.maps.MVCObject` — do not replace it with a custom shim) and hand-rolls the two behaviours `OverlayView` doesn't provide natively: drag-to-move (via pointer events + `projection.fromDivPixelToLatLng`) and an `anchor: "center" | "none"` option (`"none"` for shape note-labels, whose pill content sets its own offset transform directly rather than being centred on its anchor point). The previous `AdvancedMarkerElement` implementation stays intact in git history (see the commits migrating each overlay type, prior to this note being updated), so reverting to it is a reasonable option to revisit if it's ever needed (e.g. a future Google Maps JS API release changing this trade-off) — not a rewrite from scratch.

**Vehicle lists (v1.193.0)** — vehicles written one after another in an observation are punctuated as a list: two get "and" (`A and B`), three or more get commas with "and" before the last and no comma before it (`A, B and C`). A list with any unpunctuated link is rewritten in full, so one that grew a vehicle at a time becomes `A, B and C`. **Articles (v1.194.0):** every *described* vehicle in a list also gets `a` / `an` in front (a capital `A` / `An` when it opens a sentence or the observation; a vehicle that is just a rego gets none; an existing article is kept; the colour is lower-cased) — `A white Lexus …, a white Toyota … and a silver Ford …`. The first vehicle's description start is found by looking back in its sentence for a colour-led run of plain words up to `, bearing …`, so narrative before it is left alone. A list that is already fully right is never touched. Applied live on Space right after a vehicle bracket and when the field loses focus — in `ObservationCell` (`SheetDetail.tsx`) and the RS Quick Entry textarea (`IntelligenceMapping.tsx`, also at submit) — and again at save time in `normalizeObservationPunctuation` (`server/db.ts`), whose Rule 1 (comma after every `(Vehicle …)` bracket) skips the bracket in front of a list's final "and". Check Sheet flags older rows (`vehicle-list-unpunctuated`, one finding per list, one-tap fix) via `checkVehicleLists` in `server/sheetCheck.ts`. Locked rows are never changed.

**Observation tidy-up (v1.195.0)** — one pass over text an officer *typed*, doing what they'd otherwise fix by hand: a capital at the start, after each full stop and at the start of each line; one space between words; a space after a comma that has none (`1,000` untouched); and a full stop at the end (only on click-out, and only for 2+ words). The pure rule is `shared/observationTidy.ts` (`tidyObservation`, `tidyObservationAtCaret`, `justTypedSpaceAfterBracket`; tested in `server/observationTidy.test.ts`); it runs `joinVehicleLists` first so vehicle lists and tidy-up agree. **Typing slips are repaired (v1.206.7)** — part of the observation tidy-up (`repairEdits` / `repairObservation` / `repairObservationAtCaret` in `shared/observationTidy.ts`, run first by `tidyObservation` and `tidyObservationAtCaret`, so same triggers and same "only text that was typed" guard; tests in `server/observationTidy.test.ts`). It fixes what a Quick Entry sentence edited by hand looked like — "CORNELL exited the vehicle, entered. 64 Sewell Streetand and continued out of sight." → "… entered 64 Sewell Street and continued out of sight.": (1) a **doubled function word** (`and|the|a|an|of|to|at|with|for|from|or|but`, case-insensitive, any run of repeats) keeps the first and drops the rest — words that can legitimately repeat ("that that", "had had") are not on the list; (2) a **doubled comma** (`,,` or `, ,`) becomes one; (3) a **full stop in the middle of a sentence** is removed only when it is clearly a slip: straight after a joining word (`and the of to at with for from or but into towards via onto`) when a number or lower-case word follows, and straight after "entered" only when an address follows (number then a capitalised word) — "HOGAN entered. SANTOS walked off." and "entered. 2 males exited." are left alone; (4) a **street type glued to "and"/"then"** ("Streetand") gets its space. **Joining words between pieces (v1.196.0)** — part of the observation tidy-up, automatic, same triggers (Space after a bracket, click-out) and same "only text that was edited" guard. The pure rule is `shared/sentenceJoin.ts` (`sentenceJoinEdits`, `wholeSentenceChips`; tests in `server/sentenceJoin.test.ts`), run by `tidyObservation` / `tidyObservationAtCaret` after the vehicle lists and before the capitals/spacing rules; `joinObservationPieces` is the joining without the capitals/full-stop fixes, used for Quick Entry text made only from chips. It only ever fills the **gap** between two pieces and never rewrites, removes or re-cases a word: (1) a **full stop** between two whole sentences — a whole-sentence phrase (built-ins: Surveillance commenced / Surveillance ceased / Out of sight / Continued out of sight / PHOTOGRAPH/S TAKEN, plus any shortcut expansion that is plain capitalised words, 2–6 words, not ending on a joining word, no brackets/commas/digits/[blanks]) followed by a capitalised word that isn't a joining word (after "Surveillance commenced/ceased" only if the next word plainly opens a sentence, since a place may follow); (2) **"at"** between "Surveillance commenced/ceased" and a street address (digit-led, full street type); (3) **"and" / commas** between people introduced back to back as `Given SURNAME (SURNAME)` — `A and B`, `A, B and C` — a capitalised sentence opener (Seen, Then, Vehicle…) is never taken for a given name. Target Logger buttons make whole new rows and are never joined; `[route]`-style blanks are never touched. The shortcuts the main sheet and Quick Entry pass in (`sentenceChips`) come from the Shortcuts page. It only fires when everything between the last "entered" in the sentence and the phrase is plainly a place (capitalised words, numbers, "&", an optional leading "the" and a bracketed short form) — "entered the car park", "SANTOS continued out of sight" and anything already joined are left alone; the comma in "…the car park, entered" is not touched. **Fifth rule (v1.200.4):** "A" / "An" before a single full vehicle that opens its sentence (`vehicleArticleEdits`) — "white Lexus NX350h station sedan, bearing WA registration 1TDM414 (Vehicle 1TDM414), parked…" → "A white Lexus …". It needs the same shape the list rule looks for (a colour-led description running up to ", bearing … (Vehicle …)") at the very start of the sentence, observation or line; a description with an article already, one with narrative before it ("Seen leaving in white Lexus…", "Observed …") or no colour is left alone, a capitalised colour is lower-cased, and a vehicle that is part of a list is left to the list rule (no double article). **The access rule — one place** (`shared/operationAccess.ts`): your own Command's operations are fully yours (your role still limits what you can DO); another Command's operation is reachable only if an admin of the **owning Command** shared it with you **by name** (`operation_shares`: one operation, or every operation that Command owns) at the same levels as the usual access — **Investigator** (the Mapping page only; stored as share level `investigator`, numeric level 0 so the normal guard opens nothing, picked up by `mapOnlyOperationIds` and only the `MAP_VIEW_PATHS` reads + `operation.listForMap`) / **Observer** (`view`, read) / **Full Access** (`log`, also add rows, certify) / **Full Access + User Management** (`manage`, also edit the operation — it does not grant user management). ## Zeroing the data (go-live reset)

`scripts/ops/zero-data.mjs` empties the operational data so every Command starts at zero (there is now also an in-app version for the owner, below). Run it from the app folder (e.g. `/opt/runlog`) with the app **stopped**: `node scripts/ops/zero-data.mjs` is a dry run (row counts only); `--execute` takes a `mysqldump` backup into `backups/` (aborts if the backup fails), asks you to type the database name, truncates the tables (numbering restarts at 1), moves the on-disk `uploads/` folder aside to `uploads.pre-zero-<time>/` (remote storage is left alone), then checks every cleared table is empty and every kept table is unchanged. **Kept:** users, teams, Command features, shortcuts, style guides, sidebar orders, WIPC officer profiles and the vault key check, and the **whole CTO Roster** (all `cto_roster_*` tables). **Cleared:** operations, sheets, rows, attachments, targets and associates, intelligence data, map data, WIPC members, briefings, the Op Manager tasking board, notifications and the audit log. `scripts/ops/zero-data-tables.mjs` classifies every table; the script refuses to run when a table is in neither list, and `server/zeroDataTables.test.ts` fails when a table added to `drizzle/schema.ts` isn't classified — **a new table must be added to KEEP_TABLES or CLEAR_TABLES.**

**Tables from other branches (v1.204.2)** — the one database is shared by every branch, so migrations from an unmerged branch (the external integrations work, `claude/ext-integrations-*`) leave tables that this branch's schema doesn't have, and Zero data refuses to run on a table it doesn't know ("Can't run yet…"). ## Target Logger: a vehicle seen on the move names who is in it (v1.204.4)

A departure with unseen occupants ("Vehicle 1FAT001, unseen occupant/s, departed 27 Olding Way and continued via:") is often followed by a row that identifies the target in the vehicle ("Vehicle 1FAT001, HOGAN driver and sole occupant, travelled on Leach Highway, FREMANTLE and continued via:"). That shape — `VEHICLE_SIGHTING_PATTERN` / `matchVehicleSighting` in `shared/vehicleEventPatterns.ts`: "Vehicle REGO", the occupants, a comma, then `travelled|travelling|driving|drove` + `on|along|down|up|via|through` + the route, and **no** departure or arrival verb (those keep their own rules) — is now read as a move: (1) `computePendingVehicleDepartures` (`server/db.ts`) gives that pending departure the identified occupants (when the row names someone; "unseen" is kept when it doesn't) and `via` / `viaRowId` (where it is now); (2) `scanWalkEvents` places those people **in the vehicle** (`ScannedPlacement.via`) and takes them out of the place they were last logged inside, so the "Inside 27 Olding Way" card goes; (3) `isReadAsMovement` is true for it, so the tracker no longer warns that a later row "wasn't read as a move". On the sheet's Target Logger and the RS Quick Entry card the departed vehicle now shows the person (HOGAN · In 1FAT001) and "Travelling on Leach Highway, FREMANTLE · 10:55 AM — from 27 Olding Way · 10:50 AM", and its "Vehicle arriving" chip carries the identified occupants. It ends, as before, when the vehicle arrives. `extractOccupantNames` moved to `shared/occupantNames.ts` (still re-exported from `lib/mentionAutocomplete.ts`) so the server rules can use it. Tests: `server/vehicleSighting.test.ts`. Not yet looked at in a browser against a real sheet.

**Target Logger: a sighting row keeps the place they entered (v1.206.4)** — "HOGAN and CORNELL inside Flight Club Fremantle playing darts and drinking beers." used to be read as being inside **"Flight Club Fremantle playing darts"** — a different place from the one they had entered, so the logger moved them there and the map's target flag (which needs a place it can locate) disappeared. `presencePlace` in `shared/walkEventPatterns.ts` now runs the text after "inside" through `cutAtDescription`: a place name is written in capitals / digits, so it keeps the leading run of name words and stops at the first lower-case word that isn't a name connector (`PLACE_NAME_CONNECTOR_RE`: and, of, the, de, la, le, du, del, von, van, on, at, in, by, near, upon — kept only when a capitalised word follows, so "Melville Fish and Chips", "Hotel de Ville" and "Kinky Lizard Cafe on Mews" stay whole while "Gino's at the bar", "Bull Creek Tavern for lunch" and "… playing darts" are cut). The existing cuts (with / while / who / as / when, "and" + lower case) still apply first. Tests: `server/walkScan.test.ts` ("a presence row's place stops where the description starts"). Only the "inside <Place>" sighting rows are changed; other walk-in phrasings are as before.

**Target Logger: a departure that names its occupants moves them out of "inside" (v1.206.6)** — "HOGAN and CORNELL entered DRIVO Carpark…" followed by "Vehicle 1FAT001, HOGAN driver, CORNELL front passenger, departed DRIVO Carpark and continued via:" used to show both "Inside DRIVO Carpark" and the departed vehicle (and the map's "inside" flag). A person can only be in one place and the latest row wins, so `scanWalkEvents` now treats a `VEHICLE_DEPART_PATTERN` row that names occupants like the v1.204.4 sighting: they are placed in that vehicle, taken out of every place they were inside, and no longer heading anywhere. Unseen and "unidentified …" occupants name nobody registered and change nothing (an unseen-occupant departure still leaves the walk-in). A later row placing them elsewhere overrides as before. Tests: `server/vehicleSighting.test.ts`.

**Target Logger: boats and vessels (v1.207.0)** — a row where someone gets onto a boat puts them **on a vessel** until a later row puts them somewhere else (latest row wins, same as everything else in the logger). The pure rules are `shared/vesselPatterns.ts` (`matchVesselBoarding`, `matchVesselDisembark`; tests in `server/vessel.test.ts`): boarding = boarded / embarked (on, onto) / entered / climbed or stepped or got aboard, onto, into / went aboard / jumped aboard + a craft ("a vessel", "the white yacht", "a 10 metre catamaran" — vessel, boat, yacht, ship, ferry, dinghy, jet ski, catamaran, cruiser, speedboat, sailboat, trawler, tinny, skiff, houseboat, runabout, kayak, canoe); leaving = disembarked (from) / alighted / got off / stepped off / climbed off / jumped off / exited / left / walked off + a craft, or "disembarked" / "alighted" alone. A craft word that is part of a place ("boat ramp", "boat shed", "Fremantle Boat Pens", "marina", "jetty", "dock") is never read as a vessel, and "Vehicle <rego>" sentences are never boardings. `scanWalkEvents` places the people with `placements[].vessel` (rego `""`, so they are not in a vehicle), takes them out of any place they were inside and stops them heading anywhere; a boarding row returns early (so "entered a vessel" is no longer read as being *inside* "a vessel"), a leaving row puts them back on foot and the rest of the sentence ("… and walked along the jetty") is still read. `locateTarget` gives the new state `vessel` (flag emoji 🛥️, label "on a vessel", `TARGET_EMOJI`), placed at where they were last logged, else at the newest vehicle arrival that named them, always marked `placeIsEstimate` — the row says where the boat is only in words ("at the end of the jetty"), which can't be geocoded. Both the running sheet panel (`SheetDetail.tsx`) and RS Quick Entry (`IntelligenceMapping.tsx`) show an **On a vessel** card (key `vsl-…`) with a **Disembarked** chip ("HOGAN disembarked from a vessel and walked [route] towards [location]."), and `isReadAsMovement` counts boarding / leaving so the "wasn't read as a move" warning stays quiet. **Not built:** tracking the vessel itself as an entity (a named boat, its own profile, a boat target) or a "vessel departing" chip; vessels are only where the people are. Not yet looked at in a browser.

**Target flag: when several markers share an address (v2.0.1)** — a parked car and a boat can both resolve to "15 Riverside Road", and the flag used to go on whichever matching marker came first (the boat), so "HOGAN · departed on foot" sat on the boat instead of the car he got out of. The pure rule is `shared/flagMarker.ts` (`chooseFlagMarker`, `markerKind`; tests `server/flagMarker.test.ts`) — **the flag goes on the most specific marker the sheet points at:** (1) **the marker of the vehicle he got out of / is in** (label holds the rego, `findVehicleMarker`; a rego marker of another operation is never used) — a "departed on foot" position now carries that vehicle's `rego` (`locateTarget`'s walking branch, from the newest arrival that named him) and the map uses its marker wherever its address is; (2) **a boat marker when he is on a vessel**; (3) otherwise a marker of the right *kind* for the state — vehicle marker for vehicle / moving / out of sight, place marker (house, point of interest) for inside / on foot, boat for vessel (`markerKind` reads the icon: boat / vessel / yacht / ship / ferry… = boat; sedan / car / police / motorbike / truck / van… = vehicle; a rego-only label with no icon is a vehicle; anything else is a place); (4) still more than one of that kind → the **newest** (markers arrive newest first), and the Target location status line says "N markers share this address, so the flag is on the newest <kind> marker" instead of picking silently. Only custom markers that *carry* the place (own address, linked intel label, or a merged location) are weighed; a single carrier is used as before. **To stop it recurring: label a vehicle's marker with its rego** — that is the only thing that ties a marker to a specific vehicle; boats have no equivalent tie yet (a boat marker is found by its icon, so two boats at one address fall to rule 4). Wired in the flag effect in `IntelligenceMapping.tsx` (`findPin`).

**Target Logger: "last seen at" follows arrivals and departures (v2.0.2)** — the logger's "last place logged" for a person (`lastAt` in `scanWalkEvents`, shown as "Last seen at …" on the On-a-vessel and in-vehicle cards and used as the place for the boat flag and for a vehicle with no arrival row) was only updated by walk-in / walk-out rows, so after "Vehicle 1FAT001, HOGAN driver, arrived at 15 Riverside Road…" it still said **DRIVO Carpark** from several rows earlier, and the boat flag was drawn there ("HOGAN · on the boat" on a car park). It is now also set by **a vehicle arrival with named occupants** (the arrival address, short form) and by **a departure with named occupants** (the address they left from), in row order, so the newest logged place wins. Unseen occupants set nothing. Tests: `server/vessel.test.ts` ("where the vessel is: the latest place logged, not an older one").

**Getting off a boat reads short (v2.0.3)** — "HOGAN disembarked from the boat and walked [route] towards [location]." used to make the on-foot card and flag read "HOGAN disembarked from the boat and · departed on foot" (the whole front of the sentence was taken as the walker's name). `scanWalkEvents` now cuts the getting-off clause out of the row text (`stripVesselLeave`, `shared/vesselPatterns.ts`: "disembarked (from) / got off / stepped off / exited … the boat (and)", or a bare "disembarked / alighted (and)") before the walking rules read it, so the walker is just **HOGAN**. The heading it produces carries `fromVessel` ("the boat", or "the vessel" when the row only says "disembarked") — `ScannedHeadingTo` / `PendingHeadingTo.fromVessel`, set per row from `disembarkRows` — and **the flag reads "HOGAN · disembarked, on foot"** (`locateTarget`, label `disembarked, on foot`) while the Target Logger card (sheet and RS Quick Entry) shows the pill **Disembarked**, "On foot", "Left the boat · since …". A boat is never a place someone is "inside", and a getting-off row without a walk still just puts them back on foot. Tests: `server/vessel.test.ts` ("getting off a boat and walking: short wording").

## Passkey (device-bound) login (v2.0.0, migration 0126) — built, OFF by default

**Status: built and merged to `runlogtest`, but switched OFF — the application is still in testing, so nothing changes for anyone until the owner ticks "Require a passkey for all users".** Off, `decidePasswordSignIn` always answers `allow`, the banner / Profile card / sign-in button / admin card are all invisible (only the owner sees the Access Management card, so they can switch it on), and the settings read fails *open* (no row, or a database error, means off). Do not widen what shows while it is off. A **major** bump because it adds a second authentication path to `auth.login` (the auth model).

**How it works.** WebAuthn via `@simplewebauthn/server` 14 / `@simplewebauthn/browser` 14 (on-device cryptography, no network call, no AI — Golden Rule safe). The server keeps only the **public key** of each approved device (`passkey_credentials`: credentialId, COSE public key, signature counter, transports, device name/kind, dates; never a fingerprint, face or IMEI). Pure rules are in `shared/passkeyRules.ts` (tests `server/passkeyRules.test.ts`): `decidePasswordSignIn` (allow / allow_warn with `left` / refuse_has_passkey / lock), `passkeyStatus` (pill text), `canAdministerPasskey` / `canSeePasskeyPerson`, code format. Server glue is `server/passkey.ts` (settings with a 2 s cache, relying party from `PASSKEY_RP_ID` / `PASSKEY_ORIGIN` or the request's host (`x-forwarded-host`/`-proto` behind nginx), in-memory single-use challenges (5 min), per-account attempt limiter (8 per 15 min on passkey sign-in and code redemption), device and code queries); the procedures are the `passkey` router in `server/routers.ts` and the changed `auth.login`.

**The rollout rule.** The owner (`isFeatureOwner`, CIN 459 + admin) ticks **Require a passkey for all users** in the **Passkey login** card at the bottom of Access Management (`components/admin/PasskeyAdminCard.tsx`; turning it ON asks for confirmation and **starts everyone's countdown from zero and clears every lock**, people already signed in are not signed out) and picks the allowance (2 / 3 / 5 password-only sign-ins, default 3). A person with no passkey then gets `allow_warn` on each correct-password sign-in (`users.passkeyPasswordSignIns` +1, counted **per person, not per device**) with a warning toast and the app-wide **`PasskeyBanner`** (in `DashboardLayout`, "N sign-ins left… Set up passkey"); the next sign-in after the allowance sets `users.passkeyLocked`, writes `passkey_locked` and `auth.login` returns `{ success: false, blocked: { kind: "locked" } }` — the login page then shows the lock message and an **"I have a one-time code"** box. Once a person has a registered device, a password alone is **refused** (`blocked.kind: "has_passkey"`, with the same code box) and the **Sign in with passkey** button signs them in (`passkey.loginOptions` / `passkey.login`). Registering a device (any route) clears the lock. `auth.login` now returns a union (`success: true` + `user` + optional `passkeyWarning`, or `success: false` + `blocked`) — `LoginPage.tsx` handles both. The sign-in page shows the passkey button only on a device where one was registered (`localStorage` `runlog_passkey_users`, `lib/passkeyClient.ts`) or once the server says the account needs one, so nobody else can tell the feature exists.

**Codes and region rules.** An admin in a person's **own Command** (`users.command`) can **Issue code** (the inline panel has only the tick "I have verified this is CIN …" — admins personally know the people they approve, so there is no "how did you check" field; 30 minutes, works once, tied to that user, only a SHA-256 hash is stored in `passkey_codes`) and see/remove that person's devices, **including other admins in the Command**; the owner and an all-region admin (`users.allRegions`) can do it for everyone; **nobody can approve themselves** and **nobody but the owner touches the owner**. An admin removing a person's **last** device locks their next password sign-in until a new code is issued. The person redeems a code on the sign-in page (`passkey.redeemOptions` → browser prompt → `passkey.redeem`, which registers the device, marks the code used, clears the lock and signs them in). A person with a device can also make a **5-minute add-device code** for another of their own devices from **Profile → My devices** (`components/PasskeyDevicesCard.tsx`, limit 5 devices; the card shows only when the requirement is on or they already have a device). The owner can mark an account **Exempt** (shared / map-only Investigator accounts, phones that can't do passkeys); exempt is never affected. Observers and Investigators can use the self-service procedures (added to `OBSERVER_ALLOWED_MUTATIONS` / `INVESTIGATOR_ALLOWED_PATHS` in `server/_core/trpc.ts`). Every step writes an audit entry (`passkey_registered`, `passkey_removed`, `passkey_login`, `passkey_code_issued`, `passkey_code_used`, `passkey_locked`, `passkey_settings_changed`).

**Not built / known limits.** (1) Turning the requirement on does **not** end sessions already signed in by password (the confirmation says so). (2) The owner's own recovery is a second registered device plus **server access** — `scripts/ops/passkey-reset.mjs` (`--status`; `--off --execute` switches the requirement off; `<username> --execute` clears that person's devices and codes, unlocks them and restarts their countdown; dry-run without `--execute`; written to the audit log). Printed recovery codes are not built. (3) Passkeys are tied to the site address (`rpID`): **settle the domain before switching it on**, and the site must be served over HTTPS (localhost works for testing). Changing the domain invalidates every registered passkey; set `PASSKEY_RP_ID` / `PASSKEY_ORIGIN` if the address the server sees differs from the public one. (4) Synced passkeys (iCloud / Google keychain) are not blocked — a device-bound-only policy is not built. (5) No "or N days" limit and no per-device counting. (6) Challenges and attempt counts are in memory, so one server process only. (7) **A new table must stay in the Zero data KEEP list** — `passkey_credentials`, `passkey_codes`, `passkey_settings` are kept (people and settings), see `scripts/ops/zero-data-tables.mjs`. Checked in a headless Chromium with a virtual authenticator against the dev database: owner switch, device registration, the 2/1/0-left warnings, the 4th-sign-in lock, an admin code redeemed by the locked officer, a reused code refused, a Western admin seeing only Western people (and refused for another Command), and with the switch off no banner, Profile card, passkey button or admin card for anyone but the owner. Interactive mock-ups and an ICT briefing (private artifacts from the session) exist: *Passkey Device Login*, *Passkey Placement*, *Passkey Rollout*, *Passkey Login Briefing*.
