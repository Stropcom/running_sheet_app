## Commands (regions), sharing and Region Search

Five fixed **Commands** — Western, Northern, Eastern, Southern, Central (`shared/commands.ts`, colours in `client/src/lib/commandStyle.ts`: gold / maroon / sky blue / dark blue / red). `operations.command` says which Command owns an operation; `users.command` is a person's home Command (the Add User "Unit — Command" dropdown replaces the old free-text Unit; only an all-region admin can put someone in another Command); `users.allRegions` marks an **all-region admin** (sees every Command, can open restricted operations). Everything existing landed in `WESTERN` on migration, so a single-Command deployment behaves exactly as before. Merged to `main` at v1.188.x.

**The access rule — one place** (`shared/operationAccess.ts`): your own Command's operations are fully yours (your role still limits what you can DO); another Command's operation is reachable only if an admin of the **owning Command** shared it with you **by name** (`operation_shares`: one operation, or every operation that Command owns) at the same levels as the usual access — **Investigator** (the Mapping page only; stored as share level `investigator`, numeric level 0 so the normal guard opens nothing, picked up by `mapOnlyOperationIds` and only the `MAP_VIEW_PATHS` reads + `operation.listForMap`) / **Observer** (`view`, read) / **Full Access** (`log`, also add rows, certify) / **Full Access + User Management** (`manage`, also edit the operation — it does not grant user management). An Observer is held to View. Shares are made on Access Management (`admin.createShares`/`revokeShare`/`listShares`/`userShares`, `components/admin/*`: team groups, Visiting access, Share with + searchable person picker, "Shared access" card on a profile). Only an admin of the owning Command (or an all-region admin) may share/revoke; an admin manages only their own Command's people.

**Enforcement** (`server/operationAccess.ts`, run from the `requireUser` middleware in `server/_core/trpc.ts` on every signed-in procedure): a single operation / sheet / row / member / attachment id the person can't reach → FORBIDDEN (queries need View, mutations Log, `operation.update/delete` Manage); lists (`operationIds`, `sheetIds`) are trimmed; map-style lists with no operations named are filled with "what I can reach". The operation lists, sheet list, to-do lists, deep search and Target Registry are filtered. **Intelligence has two scopes** (per-request `AsyncLocalStorage`, `server/intelScope.ts`, honoured by `getAllIntelligenceEntities()`): _browsing_ (the Intelligence Folder lists, maps, reports — every procedure except the four below) shows only the entities of operations you can reach, so a Command's Folder is its own plus anything shared with it; _opening one entity's profile_ (`intelligence.targetProfile/associateProfile/vehicleProfile/locationProfile` — what Region Search's "Open in Intelligence" does) is more open: any operation except another Command's **Restricted** one. Region Search itself asks for the unscoped set (`{ unscoped: true }`). Anyone who can reach everything skips all of it. **Coverage audit (v1.176.3)** — every procedure was reviewed against the guard. _Guarded by id_: operation, sheet, row, member, attachment (and its entity links), SMEAC/UCO briefings, map markers and shapes, Recycle Bin items (by type), `export.sheetData`, and **targets** — a target belongs to the operations it is linked to (readable if it has none or any is open in the profile scope; changing one needs Log on one of its operations) — with associates and target shortcuts following their target. _Filtered lists_: operations, sheets, to-dos, deep search, Target Registry, calendar, briefings, audit log (sheet entries by operation; system entries admin-only), incomplete-sheets / weekly-activity / outstanding-to-do reports, Recycle Bin, attachment counts, photos by entity, live team locations and their history (one stricter rule, `canSeeLivePin` in `shared/operationAccess.ts`: your own Command's people, visitors your Command hosts, and people who genuinely reach the same operation — no all-region exemption, and the operations a pin is tagged with only count if its owner really belongs on them), entity merges, pin overrides, WIPC members (by the Command of the admin who created them). System-wide `adminUtils.*` need an all-region admin. **Still Command-agnostic by design, needs a decision before relying on it**: `users.listForCin` (names and CINs of everyone, so officers can be added to rows), and the Add Target "possible duplicate" prompt (searches the whole Target Registry, like Region Search). If the guard's database read fails the request fails (fail-closed).

**CTO Roster and the Op Manager weekly tasking board are per-Command (v1.186.0, migration 0120).** Each Command has its own roster (teams, members, shifts, secondments, drafts, saved rosters, Outlook minimums, audit log) and its own tasking board (priority rows, tasking grid, supervisor contacts, posted weeks) and Weekly Tasking Report; Eastern's can't be seen or changed by Western. `command` (default `WESTERN`, so everything that existed landed there) is on the root tables: `cto_roster_teams` (name unique per Command), `cto_roster_members` (a person has at most one place per Command's roster — unique on `(command, cin)`; **a visitor** from another Command, i.e. someone it shared an operation with by name or put in one of its teams (`visitorUserIdsOf` in `db.ts`), can be on that host Command's roster as well as their own, via `ctoRoster.members.candidates` / `addCtoRosterMember`'s eligibility check, and "My Shifts" merges every roster they are on; anyone else from another Command is refused with a message pointing at Share with), `cto_roster_drafts`, `cto_roster_saved_rosters`, `cto_roster_audit_log`, `cto_roster_outlook_settings` (one row per Command) and the four `op_manager_*` tables; shifts and secondments follow their member, draft/saved-roster children follow their parent. `shared/rosterCommand.ts` resolves which Command a request works on: the person's own, except an **all-region admin** may pick another via the `x-runlog-roster-command` header (the picker bar `RosterCommandBar` on the CTO Roster / Op Manager / Weekly Tasking pages stores the pick in `localStorage` and reloads). Two layers, both in `server/rosterContext.ts` / `server/rosterScope.ts`: the tRPC `rosterScopeMiddleware` runs every request inside a per-request scope that `server/ctoRoster.ts` and the Op Manager functions in `db.ts` read (`rosterCommand()` filters lists, `rosterCommandForWrite()` stamps new rows; no request = internal call, unfiltered), and `enforceRosterAccess` refuses any roster id from another Command (`ROSTER_ID_REFS`: path → input fields; `server/rosterScope.test.ts` fails if a new `ctoRoster.*` procedure takes a member/team/draft/saved-roster id and isn't listed). **Adding a roster/tasking endpoint: filter by `rosterCommand()` in the data function and add its id fields to `ROSTER_ID_REFS`.** The generic operation guard no longer reads a `ctoRoster.*` `memberId` as a running-sheet row member. Deliberately still shared: the EA compliance **rules** (company-wide settings) and `opManager.listUsers` (SMEAC/UCO briefings use it for recipients, which can cross Commands).

**Command features — per-Command on/off switches (v1.188.0, migration 0122).** The owner (`COMMAND_FEATURES_OWNER_CIN` = `"459"`, and role admin — `isFeatureOwner` in `shared/commandFeatures.ts`; nobody else sees or changes them, server included) switches **CTO Weekly Tasking** (`tasking`), **CTO Roster** (`roster`), **Import Target** (`import`) and **Vehicle Crash** (`crash`) on or off for each Command from the **Command features** card at the bottom of Access Management (`components/admin/CommandFeaturesCard.tsx`, `commandFeatures.all/set`). `command_features` stores only what was changed (no row = on; unique per Command + feature); changes write a `command_feature_changed` audit entry. A Command's own people get their switches with `auth.me` (`features`, `isFeatureOwner`; `useCommandFeatures` / `useCommandFeature` in `lib/commandFeatures.ts`); an **all-region admin always keeps every feature**. Enforced twice: the tRPC `rosterScopeMiddleware` calls `enforceFeatureAccess` (`server/commandFeatures.ts`, 2-second cache) using `featureForPath` (`ctoRoster.*` → roster; `opManager.*` except `opManager.listUsers` and `reports.weeklyTasking` → tasking; `target.registry.parseDocument` → import) and answers FORBIDDEN; the screens hide the menu entries (both sidebar renderings in `DashboardLayout.tsx`), show "isn't turned on" for the page (`gatedByFeature` in `App.tsx`), and hide the Import Target button. Vehicle Crash makes no server calls, so it is hidden on screen only. Nothing is deleted when a feature is off. **v2.18.0: a fifth switch, Check Sheet (`sheetCheck`), starts OFF** (`DEFAULT_OFF_FEATURES` in `shared/commandFeatures.ts`: no saved setting means off, not on, and an all-region admin follows it too) — see `docs/features/dev-and-ops.md`. **Adding a switchable feature: add its key to `FEATURES`/`FEATURE_KEYS`, map its procedures in `featureForPath`, then hide its menu entries and gate its route.**

**Region Search** (small button in the Intelligence Folder header, where Merge Entities used to be; `client/src/components/RegionSearch.tsx`, `intelligence.regionSearch`, pure logic in `shared/regionSearch.ts`): finds a person/vehicle/address across every Command. Everyone signed in sees the same matches and details (role, operations, "Contact <Command>" — plain text). The only difference is **Open in Intelligence**: an operation marked **Restricted** (`operations.restricted`, admin-only to set; tick on New/Edit Operation) can only be opened from its own Command, by an all-region admin, or by someone it was shared with. Deterministic matching — no AI.

**Teams are per-Command records** (`teams` table: `command`, `name`, `colour`, `aiPhones` JSON, `sortOrder`; `users.teamId` points at one — migration 0115 turned the old fixed TEAM1/TEAM2/PTT enum into Western's three teams and carried everyone across; the old `users.team` column is kept as `legacyTeam` for rollback only and is never read or written). An admin manages their own Command's teams from the **+ Team** button on Access Management (`admin.createTeam/updateTeam/deleteTeam`; deleting a team moves its members to "No team"; a person can only be given a team of their own Command, and moving Command clears it). `users.listTeams` returns the caller's Command's teams (all-region admins: every Command's); `client/src/lib/teams.ts` (`useTeams`, `useMyTeams`) is the single client reader. Screens that follow teams: Access Management groups, Add/Edit User, the roster "Add team" buttons on sheets and operations, the Incomplete Sheets "by team" report, the Mapping page's live-team pin colours and team list, and the Crash Helper's Assumed Identity phones. **Visiting from Commands** (Access Management, collapsed section under Teams: **Share** — give people in other Commands operations — and **Members**) also lets the hosting Command put each visitor in one of _its own_ teams (`visitor_team_assignments`: userId + hosting Command → teamId, migration 0116; `admin.setVisitorTeam`/`listVisitorTeams`, the "+ New team…" option makes a team and assigns it in one step). `users.teamId` is never touched, so the visitor keeps their home team and the hosting Command sees them in theirs; the assignment goes when the team is deleted or the last share from that Command is revoked. `visitorTeamMap(command)` in `db.ts` is the single "effective team" lookup, used by `users.listForCin` (roster "Add team" buttons), the Incomplete Sheets / Outstanding Actions reports and the live-map team pins — use it for any new screen that groups by team on the hosting Command's side. **Map Settings → Teams (v1.183.0)**: each team has `mapVisibility` (`always` — Team 1, Team 2, PTT, Capability and any temporary team an admin adds, shown until deleted — or `online`, shown only while someone in it is logged in) and `forceShare` (members' Show & Share switches on at login and is locked on; the server also ignores a switch-off). Both are set in the Team dialog; migration 0118 set Admin/Administration to online and Investigators to online + forceShare by name. The rule is `shared/teamMap.ts`: "logged in" = active within `ONLINE_WINDOW_MS` (15 min — `users.lastSignedIn` is stamped on every signed-in request), read through `users.teamsWithOnlineMembers`; `auth.me` carries `mustShareLocation` (map-only Investigator accounts can't list teams), `ForcedLocationSharing` keeps the flag on app-wide, and the Map page locks the switch. **Deliberately separate for now (will be linked later):** the CTO Roster's own teams (`cto_roster_teams`) and Op Manager's typed role names.

## Zeroing the data (go-live reset)

`scripts/ops/zero-data.mjs` empties the operational data so every Command starts at zero (there is now also an in-app version for the owner, below). Run it from the app folder (e.g. `/opt/runlog`) with the app **stopped**: `node scripts/ops/zero-data.mjs` is a dry run (row counts only); `--execute` takes a `mysqldump` backup into `backups/` (aborts if the backup fails), asks you to type the database name, truncates the tables (numbering restarts at 1), moves the on-disk `uploads/` folder aside to `uploads.pre-zero-<time>/` (remote storage is left alone), then checks every cleared table is empty and every kept table is unchanged. **Kept:** users, teams, Command features, shortcuts, style guides, sidebar orders, WIPC officer profiles and the vault key check, and the **whole CTO Roster** (all `cto_roster_*` tables). **Cleared:** operations, sheets, rows, attachments, targets and associates, intelligence data, map data, WIPC members, briefings, the Op Manager tasking board, notifications and the audit log. `scripts/ops/zero-data-tables.mjs` classifies every table; the script refuses to run when a table is in neither list, and `server/zeroDataTables.test.ts` fails when a table added to `drizzle/schema.ts` isn't classified — **a new table must be added to KEEP_TABLES or CLEAR_TABLES.**

## Zero data — in the app (v1.204.0, migration 0125)

**Access Management → Zero data** (`components/admin/ZeroDataCard.tsx`, bottom of the page under Command features) empties the operational data from inside the app, for test data / go-live. **Owner only** — `isFeatureOwner` (CIN 459 + admin), checked on the screen and again in `zeroData.preview/run` (`server/routers.ts`). It lists the rows per area (`ZERO_AREAS` in `shared/zeroDataAreas.ts`, grouped for people; `server/zeroDataTables.test.ts` fails if a cleared table isn't in exactly one area) and what stays, then **Zero all data…** asks for the typed word `ZERO` and the owner's password again. **The table lists are the same ones the command-line script uses** — `scripts/ops/zero-data-tables.mjs` is the one source (typed for the server by `zero-data-tables.d.mts`); keep/clear rules are unchanged (users, teams, Command features, shortcuts, style guides, sidebar order, WIPC officer profiles and the whole CTO Roster stay; everything else, including targets, the Weekly Tasking board and the audit log, is cleared). `server/zeroData.ts` truncates on one dedicated connection (`withDedicatedConnection` in `db.ts`, FK checks off for the run), refuses if the database has a table neither list knows, verifies every cleared table is empty, **deletes everything inside the on-disk `uploads/` folder** (v1.204.1 — photos and uploaded documents, permanently; the folder itself stays; refuses before clearing anything if `uploads` is a link; the card shows the file count and size first; remote storage has no delete here, so those files stay and the card says so), drops the access and feature caches, then writes one `data_zeroed` audit entry (new value on the `audit_logs.action` enum — migration 0125 — so the log isn't empty). **There is no backup in the app** (the script `scripts/ops/zero-data.mjs` still takes a `mysqldump`, needs the app stopped, and moves `uploads/` aside rather than deleting it); the confirmation says so. **Offline drafts on other devices:** `auth.me` carries `dataEpoch` (time of the latest `data_zeroed` entry, `server/dataEpoch.ts`, 30-second cache); `AppearanceApplier` in `App.tsx` calls `applyDataEpoch` (`lib/dataEpoch.ts`): when it differs from the number the device last saw (`localStorage` `runlog_data_epoch`, default 0) it empties the offline store (`clearAllOfflineData`) and reloads once — never if the number can't be saved, so it can't loop. The device that did the zero clears its own store and remembers the number, then shows "Reload RunLog". Checked against the dev database: 46 tables cleared, users/shortcuts kept, uploads moved, epoch returned.

**Tables from other branches (v1.204.2)** — the one database is shared by every branch, so migrations from an unmerged branch (the external integrations work, `claude/ext-integrations-*`) leave tables that this branch's schema doesn't have, and Zero data refuses to run on a table it doesn't know ("Can't run yet…"). Those are listed in `scripts/ops/zero-data-tables.mjs` as `OTHER_BRANCH_KEEP_TABLES` (`connectors` — integration set-up, no operation ids) and `OTHER_BRANCH_CLEAR_TABLES` (`cameras`, `signal_sensors`, `signal_detections`, `tracked_assets`, `tracked_asset_positions`, `external_events`, `connector_audit_log` — cameras/sensors carry operation ids, which restart at 1 after a zero, so they must not survive); the script and the in-app card use the union (`ALL_KEEP_TABLES` / `ALL_CLEAR_TABLES`), a table that isn't in the database is skipped, and the card shows them as "Integrations (cameras, trackers, signals)". `server/zeroDataTables.test.ts` fails once one of these appears in `drizzle/schema.ts` — **when an integrations branch is merged, move its tables into `KEEP_TABLES` / `CLEAR_TABLES` and out of the OTHER_BRANCH lists.** Any other new table from another branch needs the same treatment.

**Live-trail points are deleted after 7 days (v1.204.3)** — `user_location_history` (the GPS breadcrumbs behind the map's Track line, one point every few seconds per person on the move while Show & Share is on) used to grow forever (24,804 rows in the Zero data count). `purgeOldLocationHistory` (`server/db.ts`, `LOCATION_HISTORY_MAX_AGE_MS` = 7 days) deletes anything older, in batches of 5,000, opportunistically like `purgeExpiredNotifications` — no timer: from `recordUserLocationHistory` at most once an hour (fire-and-forget, so a failed purge can't lose a position) and once at startup (`server/_core/index.ts`). Nothing reads older points: a trail only starts from the moment Track was switched on. The live positions table (`user_locations`, one row per device) is unaffected. Checked against the dev database: 12,000 old points removed in batches, 3 recent kept.

**Built files get long cache lifetimes (v2.2.2)** — `serveStatic` (`server/_core/vite.ts`) now sets `Cache-Control` through `staticCacheControl` (`server/staticCache.ts`, tested in `server/staticCache.test.ts`, including a real `express.static` round trip): the hashed files Vite writes to `/assets/` (name carries a content hash, so a new build is a new name) get `public, max-age=31536000, immutable`; `index.html` (and the catch-all that serves it for any unknown path — so a missing old chunk comes back as an uncached page, never as something cached for a year), `sw.js`, `workbox-*.js` and `manifest.webmanifest` get `no-cache` (keep a copy but ask first; a 304 when unchanged); everything else (icons, fonts, models, tactical markers) keeps Express's default (`max-age=0`, revalidate). **Never widen the long-cache rule beyond hashed `/assets/` files** — a long lifetime on `index.html` or `sw.js` would leave officers on an old version after a deploy. nginx passes these headers through; nothing to change there. **Compression is not done by Express** (no `compression` middleware), so gzip depends on nginx (`gzip on; gzip_types …` in the droplet-only `/etc/nginx/sites-available/runlog`): check with `curl -sI -H 'Accept-Encoding: gzip' https://<site>/assets/<main>.js | grep -i content-encoding`. Uncompressed the main bundle is 3.6 MB; gzipped about 0.85 MB. The PWA service worker precaches the app code, so these mostly help a first visit and the download after a deploy.

**Stored photos and documents need a sign-in (v2.2.3)** — `/local-uploads/…` (and the remote-store `/manus-storage/…` proxy) used to serve any file to whoever had its address, signed in or not, so an address from browser history, a screenshot, a copied link or a server log opened the evidence from any device, indefinitely. Both routes now go through `requireSignedIn` (`server/uploadAccess.ts`, tests `server/uploadAccess.test.ts`), which runs `sdk.authenticateRequest` — the same check the raw upload route uses — and answers `401 Sign in required` (`Cache-Control: no-store`; a file that doesn't exist answers the same, so nothing leaks about what exists). The browser sends the login cookie by itself with `<img>`, `<iframe>`, downloads and the export/print window (a `window.open("")` page with absolute photo URLs — checked), so no screen changed; server-side readers use `storageGetBytes` straight from disk and are unaffected. **This is "signed in", not "may see this operation"** — a signed-in officer of another Command who knows a file's address can still open it; mapping a file back to its attachment/operation for the Command rule is not built (the address is `row-attachments/sheet-N/row-N/<ms>_<8 hex>.jpeg`, not guessable in practice, but not a secret once seen). Files are still **never deleted** when a photo is removed in the app (only Zero data deletes them), so an address stays valid. Served files carry `Cache-Control: private, max-age=2592000, immutable` (`UPLOAD_CACHE_CONTROL`: names are unique — timestamp + random suffix — and a file is never rewritten, so a device may keep its copy; `private` keeps shared caches/proxies from holding evidence; 30 days so a copy on a lost device doesn't linger). A copy in a browser's own cache is not removed on sign-out (as before). **Anything outside RunLog that fetches these addresses without the login cookie (a script, a shared link) now gets 401** — that is the point.

**Passkey login card is a drop-down, closed by default (v2.3.4)** — the Passkey login card at the bottom of Access Management (`components/admin/PasskeyAdminCard.tsx`) is now a collapsible section: its titled band is a button (chevron, "Passkey login", the people count and the Off / Required status pill, all on one line at laptop and phone widths) and everything below it (the owner's switch and allowance, the people list, devices, codes) shows only when opened. **Closed every time the page opens** (`useState(false)`, deliberately not remembered, unlike the Visiting section) because the card is long and rarely needed; the setup dialog stays mounted outside the collapsed part. Closed it is a single 44 px band. Nothing about what the card does or who sees it changed.

**Every Access Management section is a drop-down (v2.12.1)** — Teams, Visiting from Commands, Passkey login, Command features, Document AI and Zero data each fold down to a single titled band, so the long page can be scrolled to the one wanted. The shared piece is `components/admin/CollapsibleSection.tsx` (the Passkey card's band: chevron, optional icon, title, count pill such as "4 people", and a status pill on the right — "Off" / "On" / "Only you"); the band is the toggle and everything below shows only while open. **Teams starts open** (it is the page's main job) and **the rest start closed**; each section's choice is **remembered per section on this device** (`localStorage` `runlog_admin_section_<id>`: `teams`, `visiting`, `document-ai`, `command-features`, `zero-data`), unlike the Passkey card, which still opens closed every time (v2.3.4). Controls that must work while folded sit outside the toggle — the **+ Team** button is in Teams' band (`actions`), not inside the toggle button. On a phone the owner pill reads "Only you" (the full "Only you can see this" from `sm` up). Also fixed: the Passkey card's toggle button stopped 32 px short of the card's right edge (a white strip beside "Off") — it is now the full width. Nothing about what any section does or who sees it changed.

## Passkey (device-bound) login (v2.0.0, migration 0126) — built, OFF by default

**Status: built and merged to `runlogtest`, but switched OFF — the application is still in testing, so nothing changes for anyone until the owner ticks "Require a passkey for all users".** Off, `decidePasswordSignIn` always answers `allow`, the banner / Profile card / sign-in button / admin card are all invisible (only the owner sees the Access Management card, so they can switch it on), and the settings read fails _open_ (no row, or a database error, means off). Do not widen what shows while it is off. A **major** bump because it adds a second authentication path to `auth.login` (the auth model).

**How it works.** WebAuthn via `@simplewebauthn/server` 14 / `@simplewebauthn/browser` 14 (on-device cryptography, no network call, no AI — Golden Rule safe). The server keeps only the **public key** of each approved device (`passkey_credentials`: credentialId, COSE public key, signature counter, transports, device name/kind, dates; never a fingerprint, face or IMEI). Pure rules are in `shared/passkeyRules.ts` (tests `server/passkeyRules.test.ts`): `decidePasswordSignIn` (allow / allow_warn with `left` / refuse_has_passkey / lock), `passkeyStatus` (pill text), `canAdministerPasskey` / `canSeePasskeyPerson`, code format. Server glue is `server/passkey.ts` (settings with a 2 s cache, relying party from `PASSKEY_RP_ID` / `PASSKEY_ORIGIN` or the request's host (`x-forwarded-host`/`-proto` behind nginx), in-memory single-use challenges (5 min), per-account attempt limiter (8 per 15 min on passkey sign-in and code redemption), device and code queries); the procedures are the `passkey` router in `server/routers.ts` and the changed `auth.login`.

**The rollout rule.** The owner (`isFeatureOwner`, CIN 459 + admin) ticks **Require a passkey for all users** in the **Passkey login** card at the bottom of Access Management (`components/admin/PasskeyAdminCard.tsx`; turning it ON asks for confirmation and **starts everyone's countdown from zero and clears every lock**, people already signed in are not signed out) and picks the allowance (2 / 3 / 5 password-only sign-ins, default 3). A person with no passkey then gets `allow_warn` on each correct-password sign-in (`users.passkeyPasswordSignIns` +1, counted **per person, not per device**) with a warning toast and the app-wide **`PasskeyBanner`** (in `DashboardLayout`, "N sign-ins left… Set up passkey"); the next sign-in after the allowance sets `users.passkeyLocked`, writes `passkey_locked` and `auth.login` returns `{ success: false, blocked: { kind: "locked" } }` — the login page then shows the lock message and an **"I have a one-time code"** box. Once a person has a registered device, a password alone is **refused** (`blocked.kind: "has_passkey"`, with the same code box) and the **Sign in with passkey** button signs them in (`passkey.loginOptions` / `passkey.login`). Registering a device (any route) clears the lock. `auth.login` now returns a union (`success: true` + `user` + optional `passkeyWarning`, or `success: false` + `blocked`) — `LoginPage.tsx` handles both. The sign-in page shows the passkey button only on a device where one was registered (`localStorage` `runlog_passkey_users`, `lib/passkeyClient.ts`) or once the server says the account needs one, so nobody else can tell the feature exists.

**Codes and region rules.** An admin in a person's **own Command** (`users.command`) can **Issue code** (the inline panel has only the tick "I have verified this is CIN …" — admins personally know the people they approve, so there is no "how did you check" field; 30 minutes, works once, tied to that user, only a SHA-256 hash is stored in `passkey_codes`) and see/remove that person's devices, **including other admins in the Command**; the owner and an all-region admin (`users.allRegions`) can do it for everyone; **nobody can approve themselves** and **nobody but the owner touches the owner**. An admin removing a person's **last** device locks their next password sign-in until a new code is issued. The person redeems a code on the sign-in page (`passkey.redeemOptions` → browser prompt → `passkey.redeem`, which registers the device, marks the code used, clears the lock and signs them in). A person with a device can also make a **5-minute add-device code** for another of their own devices from **Profile → My devices** (`components/PasskeyDevicesCard.tsx`, limit 5 devices; the card shows only when the requirement is on or they already have a device). The owner can mark an account **Exempt** (shared / map-only Investigator accounts, phones that can't do passkeys); exempt is never affected. Observers and Investigators can use the self-service procedures (added to `OBSERVER_ALLOWED_MUTATIONS` / `INVESTIGATOR_ALLOWED_PATHS` in `server/_core/trpc.ts`). Every step writes an audit entry (`passkey_registered`, `passkey_removed`, `passkey_login`, `passkey_code_issued`, `passkey_code_used`, `passkey_locked`, `passkey_settings_changed`).

**Not built / known limits.** (1) Turning the requirement on does **not** end sessions already signed in by password (the confirmation says so). (2) The owner's own recovery is a second registered device plus **server access** — `scripts/ops/passkey-reset.mjs` (`--status`; `--off --execute` switches the requirement off; `<username> --execute` clears that person's devices and codes, unlocks them and restarts their countdown; dry-run without `--execute`; written to the audit log). Printed recovery codes are not built. (3) Passkeys are tied to the site address (`rpID`): **settle the domain before switching it on**, and the site must be served over HTTPS (localhost works for testing). Changing the domain invalidates every registered passkey; set `PASSKEY_RP_ID` / `PASSKEY_ORIGIN` if the address the server sees differs from the public one. (4) Synced passkeys (iCloud / Google keychain) are not blocked — a device-bound-only policy is not built. (5) No "or N days" limit and no per-device counting. (6) Challenges and attempt counts are in memory, so one server process only. (7) **A new table must stay in the Zero data KEEP list** — `passkey_credentials`, `passkey_codes`, `passkey_settings` are kept (people and settings), see `scripts/ops/zero-data-tables.mjs`. Checked in a headless Chromium with a virtual authenticator against the dev database: owner switch, device registration, the 2/1/0-left warnings, the 4th-sign-in lock, an admin code redeemed by the locked officer, a reused code refused, a Western admin seeing only Western people (and refused for another Command), and with the switch off no banner, Profile card, passkey button or admin card for anyone but the owner. ## Day and Arvo shifts are 9 hours; Admin is 8 (v2.69.0)
