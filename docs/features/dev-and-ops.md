**CI runs the type check and the unit tests on every push and pull request (v2.17.11)** — `.github/workflows/ci.yml` (Node 22, pnpm from the `packageManager` field, `pnpm install --frozen-lockfile`, `pnpm check`, `pnpm test`; on pushes to `main`, `runlogtest` and `develop`, on every pull request, and by hand; a newer run on the same branch cancels the older one; 20-minute limit). The tests are offline (no database, network or AI), so the job needs no services. It sits alongside `no-runtime-ai.yml`, which is unchanged. **The six long-standing failures in `server/running_sheet.test.ts` were stale tests, not bugs, and are fixed** (so the suite is green and a red run means something): sheet creation by an Observer is refused (Observers have view and export access only), a Member creates a sheet on an active operation; `sheet.delete` needed `softDeleteSheet` in the `./db` mock; `row.update` needs an active sheet and operation; and a Member may only certify / unlock rows that carry their own CIN, so those tests now sign in as a member with a CIN and a row that has it. **If CI goes red, fix the test or the code — do not leave a known failure in the suite.** Not done: a branch-protection rule requiring the check before merge (a GitHub setting), browser smoke tests, and splitting `db.ts` / `routers.ts`.

**Browser smoke tests (v2.17.13)** — `e2e/` (Playwright, `pnpm test:e2e`, `e2e/README.md` has the setup) now drives the real app in Chromium: `auth.setup.ts` signs in once per run and saves the session (`e2e/.auth/user.json`, git-ignored — the login endpoint is limited to 20 attempts per 15 minutes per IP, so one sign-in per run, not per test); `smoke.spec.ts` (1) creates an operation and a running sheet, adds a row with an observation and the officer's own CIN, reloads to prove it was saved, clicks the CIN to certify and checks the row shows **Locked** and no longer opens an editor, and (2) opens every main page that doesn't need Google Maps and fails on the error screen ("An unexpected error occurred.") or any uncaught script error; `voice-offline.spec.ts` (the older Golden Rule check) was repaired — it had been failing since RS Quick Entry started requiring a selected running sheet and voice input was switched off (`VOICE_INPUT_DISABLED`), so it now makes a sheet, selects it in `runlog_map_settings` and asserts no request leaves the app's own origin while Quick Entry is open offline (it still exercises the Voice button if the feature is turned back on). **CI** — `.github/workflows/e2e.yml` (own workflow, so `ci.yml` stays fast and offline): MySQL 8 service, `drizzle-kit migrate`, `scripts/dev/create-admin-user.ts`, the app started with `NODE_ENV=development`, `playwright install --with-deps chromium`, then `pnpm test:e2e`; failure screenshots, traces and the app log are kept as an artifact for 7 days. **Things that cost time to find, so they are written down:** the server needs both `VITE_APP_ID` and `JWT_SECRET` or the session cookie is rejected ("Session payload missing required fields") and sign-in looks like it does nothing; a CIN added to a row is checked against registered users (green tick) and committed with the round **+** button — Enter alone doesn't add it; after adding, a CIN shows red until its owner clicks it, and a row locks (shows **Locked**) only when every CIN on it has certified; the CIN pill is an `<input>` while editing, so its text isn't in `innerText`. **Not covered yet:** Mapping / RS Mapping (Google Maps isn't reachable from CI), the Target Logger and Target Registry flows, Import Target, exports, and phone-width layouts. Checked against a local MariaDB 10.11 (all 132 migrations apply) with the full suite run repeatedly; the first run on GitHub (MySQL 8) is the check that matters for the workflow itself. Sheet-row tests add one operation and sheet per run (`Smoke <timestamp>`) and delete nothing, so only point them at a throwaway database.

**`routers.ts` split into one file per area (v2.17.14)** — `server/routers.ts` was 10,266 lines; it is now 93 lines that only put the areas together, and each of the 40 API areas is its own file in `server/routers/` (`profile`, `auth`, `passkey`, `operation`, `sheet`, `row`, `attachment`, `target`, `intelligence`, `ctoRoster`, `admin`, … — the same names and order as before, so every client call such as `trpc.sheet.create` is unchanged). The guards, shared input schemas and small shared helpers that used to sit at the top of the file are in `server/routers/_helpers.ts` (each now `export`ed; a router file imports only the ones it uses). **Pure move: no code inside any procedure changed** — only the file it lives in, its indentation, its import paths (`./x` → `../x`, including the dynamic `import()`s) and its imports (each file keeps only what it uses). Checked three ways: `pnpm check`; all 1,587 unit tests (the tests that mock `./db` still work because the new files import the same module); and a comparison of the old and new `appRouter` — 381 procedures each, no missing or extra, every one with the same type (query/mutation), input count and middleware count. **How the split was done, in case `db.ts` or another big file is next:** a throwaway script cut the file by its top-level `name: router({ … }),` entries and wrote one file each; TypeScript's own organise-imports removed the unused imports; Prettier formatted the result; the old and new routers were then compared. **Next:** `db.ts` — done in v2.17.15, below.

**`db.ts` split into one file per area (v2.17.15)** — `server/db.ts` was 19,199 lines (432 exports in 63 `// ─── Section ───` blocks); it is now a ~490-line file of re-exports and the code is in 16 files in `server/db/`: `core` (119 lines: pool, `getDb`, `withDedicatedConnection`), `accounts`, `notifications`, `operations`, `recycleBin`, `attachments`, `faces`, `targets`, `intelligence`, `crossOperation`, `targetLogger`, `reports`, `governance`, `court`, `mapping`, `opManager`. A section was never cut in half; the biggest files are `reports` (3,224 lines — it holds the 2,000-line Weekly Activity Report), `intelligence` (2,292), `targets` (2,110) and `crossOperation` (1,802) and can be split further the same way. **Pure move: no function body changed.** What changed is only which file a statement is in, its imports, and an `export` added to a name another file needs (a name used only inside its own file is still private). **`db.ts` re-exports exactly the names it exported before** (explicit lists, not `export *`, so the public surface did not grow — checked by comparing the old and new module: same export names, same kinds); the two `export { VEHICLE_… }` re-exports of shared patterns are kept. Because every other file still imports from `./db`, nothing outside `server/db*` changed, and the tests that mock `./db` are unaffected. **Checked:** `pnpm check`; all 1,587 unit tests; the old/new export comparison; and the Playwright smoke tests against the app actually running on the split code (sign in, create operation and sheet, add and certify a row, 17 pages) — the one thing the type check cannot show is a cycle between the new files breaking at load time, and the app starting and serving pages shows it does not. **Cycles:** the area files import each other (as the sections already called each other), which is fine because everything shared is a function; the generator listed every top-level constant whose value is computed from another file's names — only one (`intelEntityCache`, which uses a *type*), so nothing evaluates another file's code at load. **Keep it that way:** do not add a top-level `const x = someFunctionFromAnotherDbFile()`; compute it inside a function. **The generator was a throwaway script** (TypeScript AST: cut by section, assign sections to areas, add cross-file imports, `export` only what another file uses, TypeScript organise-imports to drop unused imports, Prettier); it is not kept in the repo — to split a file again, re-derive it from this description.

**Schema drift fixed: 9 columns no migration created (v2.17.16, migration 0128)** — found while building the scale-test database: a database built **only from the migrations** was missing nine columns that `drizzle/schema.ts` (and drizzle's own snapshot, `drizzle/meta/0127_snapshot.json`) already had — `associates.relationship`, `intel_pin_overrides.customLabel` and `.note`, `map_shapes.rotation`, and `targets.mdlStatus`, `.bailStatus`, `.bailConditions`, `.bailConditionsText`, `.specialProjects`. The live database has them (they were added outside the migration runner, the same way ops-notes.md describes for earlier columns), so nothing was broken in production, but any environment rebuilt from the migrations (a new server, a restore, staging, CI) would have errored on Target Registry, Associates, map shapes and pin notes. **The fix, `drizzle/0128_add_missing_schema_columns.sql`**, adds each column only if `information_schema` says it isn't there (a prepared `ALTER TABLE … ADD COLUMN` that is replaced by `SELECT 1` when the column exists), so it is a **no-op on the live database** and repairs a fresh one; it avoids `ADD COLUMN IF NOT EXISTS` because MySQL 8 doesn't support it. Checked both ways on MariaDB: a fresh database gets the columns, and re-running it on a database that already has them changes nothing and doesn't fail. (drizzle's snapshot already contained the columns, so `drizzle-kit generate` said "no changes" — a hand-written custom migration, `generate --custom`, was the right tool.) **To keep it from happening again:** `scripts/dev/check-schema-drift.ts` compares `schema.ts` with a database built from the migrations and exits 1 on any difference; `.github/workflows/e2e.yml` runs it after `drizzle-kit migrate`, so a column added to `schema.ts` without a migration now fails CI. **Rule: a schema change needs its migration in the same commit; never apply a schema change to a database with `drizzle-kit push` or by hand.**

**Missing database indexes added (v2.18.0, migration 0129)** — the scale test found that **the busiest tables had no indexes at all except their primary key** (`sheet_rows`, `row_members`, `certifications`, `row_attachments`, `running_sheets`, `operation_target_links`, `associates`, `audit_logs`, …), so every lookup by sheet, row or operation read the whole table and the cost grew with all the data ever recorded. Adding them changes **no results**, only how fast rows are found. Measured on the 5-year test data (390,000 rows): **opening a sheet 1.7 s → 0.05 s, Governance summary 35 s → 0.4 s**, Pattern of life 42 s → 1.8 s; the slow Intelligence work (Sheet Check, Intelligence Folder, the ~40 s stalls) is **not** helped, which is how the real cause (rebuilding the global entity list) was separated from the table scans. Twenty indexes were added (names end `_idx`; each is declared in `drizzle/schema.ts` next to its table and created by `drizzle/0129_add_missing_indexes.sql`): `sheet_rows (sheetId, rowNumber)`, `row_members (rowId)` and `(memberName)`, `certifications (rowId, memberId)`, `row_attachments (rowId)` and `(operationId, deletedAt)`, `attachment_entity_links (category, targetId)` and `(category, entityKey)`, `running_sheets (operationId, deletedAt)`, `(targetId)`, `(sheetDate)`, `operation_target_links (targetId)` and `(operationId)`, `associates (targetId, deletedAt)`, `audit_logs (sheetId)` and `(createdAt)`, `person_detections (attachmentId)`, `target_field_history (targetId)`, `sheet_summary_entries (sheetId)`. **The migration creates each index only if it is not already there** (an `information_schema` check around a prepared `CREATE INDEX`; `CREATE INDEX IF NOT EXISTS` is not available on MySQL 8), so it is safe on the live database whether or not someone added some of these by hand — checked on MariaDB for a fresh database, a database that already has all of them (changes nothing) and one with only some; MySQL 8 is checked by the e2e workflow. Building them on the 5-year test data took 4 s; on the live database today it will be much less. **`scripts/dev/check-schema-drift.ts` now also checks indexes**, so an index declared in `schema.ts` but never migrated fails CI. **Rule: a query that filters a large table by a column needs an index on that column — add it in `schema.ts` with its migration in the same commit.**

**Check Sheet is switched off by default (v2.18.0)** — the Check Sheet button on a running sheet (`CheckRunningSheetDialog` → `sheet.check` → `checkRunningSheet`, `server/sheetCheck.ts`) loads the **global** Intelligence entity list (`getAllIntelligenceEntities`, every operation) on every click and narrows it to one sheet; at 5 years of data that took ~44 s per click and, the server being single-threaded, held everyone else up too (it is the same size as the random ~40 s stalls). Rather than risk the Intelligence Folder and searches while that list is redesigned, it is now a **Command feature that starts off** (`sheetCheck` in `shared/commandFeatures.ts`; `DEFAULT_OFF_FEATURES` — a default-off feature is off unless the owner turns it on, **including for all-region admins**, who otherwise keep every feature). Off: the button and dialog are not shown (`useCommandFeature("sheetCheck")` in `SheetDetail.tsx`), and `sheet.check` / `sheet.dismissCheckFinding` answer FORBIDDEN (`featureForPath`). **Nothing was deleted**: the ~1,900 lines of rules (`server/sheetCheck.ts`), the dialog and the ~74 tests stay, and the owner can switch it back on per Command from the **Command features** card (it shows a caution that it can be slow on a large archive). The server rules that write new text (tidy-up, vehicle lists, street types) are unaffected — only the clean-up tool for already-saved rows is off. `commandFeatures.feature` is a `varchar`, so no migration was needed. **To bring it back properly:** adapt it to read only the sheet it checks (or the new per-operation entity store once the Intelligence list is redesigned), prove its findings are unchanged, then switch it on.

**Incomplete Sheets report rewritten (v2.18.1)** — `getIncompleteRunningSheets` (`server/db/reports.ts`, behind `reports.incompleteSheets`) used to load every sheet, row, member and certification ever recorded into memory and rescan them for every sheet; it took 30 s at one year of data and **failed at three** ("Maximum call stack size exceeded" from one enormous `IN (…)` list). It now asks the database for the work: one aggregate query counts the unsigned rows per sheet (a row is unsigned when it has no real member, or any real member lacks their OWN active certification — the same rule as `isRowSignedOff`, with an exact, case-sensitive `BINARY` test for the `__SPACE__` spacer name), the governance records of live sheets come from a join (not a giant `IN`), and the team and operation lookups are only done for the sheets that turn out to be incomplete. **The answer is unchanged:** `scripts/dev/compare-incomplete-sheets.ts` holds a verbatim copy of the original and compares the two field by field — identical on one year of realistic fake data (100 open sheets, both viewer modes) and on a 17-sheet edge-case database (closed sheet with an unlocked row, a row with no members, spacer-only rows, an inactive certification, no governance record, a deleted sheet, a missing operation, invalid `sheetCins` JSON, mixed teams, a lower-case `__space__` member). **Measured:** 1 year **31.9 s → 0.6 s**; 3 years error → about 2 s; 5 years error → about 3.5 s (5 s first call). It no longer fails, but it is **still linear in the number of rows** (the aggregate reads every row once; ~3 s at 5 years, so ~30 s at ten times that): a closed sheet can have an unsigned row (a member can unlock a row after the sheet closes — `guardActiveSheet` only checks the operation, not the sheet's `closedAt`), so a cheap "closed means signed" shortcut would change the answer. If it is ever slow again the next step is to keep a per-sheet "has an unsigned row" flag up to date when a certification changes, not to skip the check. Delete the comparison script once the new report has proved itself in use.

**Intelligence redesign plan (NOT started — decided 2026-10-22 to wait; early-warning tools added v2.18.2).** *Do not build any of this until the trigger below fires, unless the owner asks.*

**The problem.** `getAllIntelligenceEntities` (`server/db/reports.ts`, built by `buildAllIntelligenceEntities`, ~1,400 lines) rebuilds the whole list of people, vehicles and places from **every running sheet row of every operation** — per sheet, a Pass A finds each bracketed introduction ("Lawrence TAN (TAN)") and a Pass B finds later bare mentions; then one global step folds the results into entities using the Target Registry, aliases, merge decisions and identity links. A sheet's extraction depends only on that sheet's rows (plus a little registry data), yet every change rebuilds everything. Measured cost: **about 0.1 s per 1,000 rows on a development machine** (the droplet may be up to ~2× slower): ~1 s at 10,000 rows (~6 weeks of the expected growth of ~78,000 rows a year), ~2.7 s at 25,000, ~9–10 s at 78,000 (one year), ~40 s at 390,000 (five years). It runs on the server's single thread, so while it runs every other request waits (the random ~40 s stalls seen at 3–5 years). Users of the list: ~35 places in 18 files (Intelligence Folder, profiles, map, heat map, suggestions as you type, Region Search, cross-operation links, Check Sheet, attachment auto-linking, Target Logger, …). **Not yet measured:** whether the time is mostly the per-sheet reading or the final merge — measure first (time each section of `buildAllIntelligenceEntities`).

**The trigger — when to start.** The server writes a line after each rebuild: `pm2 logs runlog | grep "\[Intelligence\]"` (`server/intelBuildWatch.ts`). **Start Stage A when it prints WARNING** — a rebuild of **3 s or more**, or **20,000 running sheet rows or more**, whichever comes first (the row limit is reached at roughly month 3 of the expected growth; the warning is repeated at most every 30 minutes). Scheduled reminders also fire (a check-in around 2027-01-22 and a yearly scale re-test each October).

**The stages — each a separate release tested on `runlogtest`, each behind an owner on/off switch (like Check Sheet, `DEFAULT_OFF_FEATURES`) so rollback is instant, none deleting anything:**
- **Stage A — remember each sheet's extraction in memory** (no schema change). Keep Pass A/B results per sheet, keyed by that sheet's rows fingerprint (row count, newest id, newest `updatedAt`); a change redoes only that sheet, then the existing global merge runs over the cached per-sheet results. Same functions, so the output is identical by construction. Add single-flight (one rebuild at a time) and a background prewarm at server start so the first call after a restart does not wait. Risk: very low. Gives: most of the rebuild cost and the stalls. Still pays one full rebuild per restart (in the background) and holds the extraction in memory (~1 GB resident measured at 5 years).
- **Stage B — save the per-sheet extraction in the database** (new table, e.g. `sheet_entity_mentions` with an extraction-rules version): restarts are instant and memory stays small. A sheet is re-extracted when it changes; an `EXTRACTION_RULES_VERSION` constant marks stored results out of date when the text-reading rules change, and they are redone automatically (lazily per sheet, or by a backfill script) so they can never go stale. Mentions are stored as the **raw** extraction; the registry-dependent folding (aliases, targets, merges) stays a read-time step using the same pure functions. Estimated disk: ~1–2 million mentions at five years, perhaps 0.5 GB with indexes (count it in the photo/disk plan). Risk: medium.
- **Stage C — look up by operation, page the Folder** (indexed lookups on the stored mentions: `(operationId, type)`, `(type, entityKey)`, `(sheetId)`, `(rowId)`). Browsing screens (Folder, profiles, map, heat map) build from one operation's mentions; only Region Search and cross-operation links need everything, via an indexed key lookup. The Intelligence Folder loads a page at a time with server-side search over everything (175 MB → a page at a time at five years). Check Sheet can return (it only needs one sheet's entities plus key lookups). The only stage officers would see. Risk: highest — classify all ~35 call sites as "one operation" or "everything" first.
- Stop after any stage if it is enough.

**Safeguards for every stage.** (1) **Zero-difference proof:** `scripts/dev/intelligence-snapshot.ts` saves the current list in a canonical form (`server/intelCompare.ts`, tested) and compares a new build to it field by field, every occurrence — `snapshot before.json`, make the change, `compare before.json`; exits 1 on any difference. Run it on 1-, 3- and 5-year test data and on a small edge-case database (target aliases that look like other people, two operations sharing a vehicle, merged entities, identity-linked pairs). (2) **The current builder stays** as the reference until the new path has been in use and trusted. (3) **Same-moment accuracy:** a row saved by an officer appears in Intelligence straight away (re-extract that sheet in the save request, or on the next read), never "later". ## CI red from v2.50.0 to v2.57.0: a unit test could not build the Places export (fixed v2.57.1)

`check-and-test` failed on every push from v2.50.0 (the Places Report export drew its kind icons by rendering them into a page element, `document.createElement`), because `server/placesReportExport.test.ts` builds that export in Node where there is no `document`. It went unnoticed because the local test run was piped through `tail`, which hid the "Test Files … failed" line and the exit code. **When running the suite, read the "Test Files" line and the exit code (e.g. `pnpm vitest run > /tmp/vt.log; echo $?`), not just the tail.** `kindIconSvg` now returns no icon when there is no `document`, and the test also checks the card layout.
