**Running sheet export font (v1.199.1)** — the whole export is Roboto, served by RunLog itself: the files are in `client/public/fonts/` (Latin + Latin Extended, 400/500/700, Apache 2.0, licence alongside), declared by `robotoFontFaceCss()` in `lib/exportFonts.ts` with absolute URLs, and printing waits for them (`whenFontsReady`) so a PDF can never get a fallback font. The export no longer links to Google Fonts, so opening one makes no request to Google, and it works offline (woff2 is in the PWA precache). The Time column used `monospace`; it is now Roboto with `font-variant-numeric: tabular-nums`, so the digits still line up. (The app itself, `client/index.html`, still loads Inter and JetBrains Mono from Google Fonts.)

**Running sheet export header (v1.199.2)** — the header now matches the Supervisor Summary / Weekly Tasking exports: a centred dark-blue banner (brand dot, "RunLog", title) with the details in labelled cells in **two equal columns**, drawn like the log table under them — `Operation | Date`, `Target | Prepared by` (Target and Date were swapped in v1.199.4), then `Imagery taken` full width (built by `coverHeaderHtml` / `detailsHtml` in `exportToPDF`, `SheetDetail.tsx`; values are HTML-escaped). With no target, Prepared by takes the whole second row; with no author CIN, Target takes it. **Page 1 prints the full banner and pages 2+ print the compact one (v1.199.3):** the full header (`.first-page-header`) stays visible in print, and the compact one in the `<thead>` (which a `thead` repeats on every page *including the first*) is hidden on page 1 by pulling the full header down over it — a negative `margin-bottom` of the compact header's height (`--hc`, measured in the `beforeprint` script at the printed content width, A4 less 15mm margins = 180mm, minus 1px). It relies on the full header being opaque and taller than the compact one; paper other than A4 can differ by a pixel or two. The compact cell must not inherit `.log-table td:last-child{white-space:nowrap}` (it is the row's only cell) — `td.thead-meta-cell:last-child` overrides it so long names wrap; the details block drops its own blue side borders in the thead because the table's border already runs down both sides.

**Profile PDF layout (v1.200.5)** — all five profile exports (Target, Operation, Vehicle, Associate, Location) append `PDF_SECTION_LAYOUT_CSS` (`ProfileKit.tsx`) after their own CSS: the `.content` area has no side padding, so every section band is as wide as the header banner (what sits under a band is inset 10px to line up with the band's text), and only a section that is always short (its wrapper div holds a `.detail-grid` or `.ops-list` — Registered Details, Status, Operations) is kept whole (`break-inside: avoid`). **v1.200.9:** the first version kept *every* section whole, which left blank first pages on Operation profiles and big blank gaps on Target profiles (a section taller than the space left, or taller than a page, was pushed to a fresh page); anything that can be long (Background, associations, sheets, photoboards, imported documents) now flows across pages, and what never splits is a single row or tile (`.sheet-item`, `.pr`, `.pb-tile`, entity-list rows), with a title/label (`.section-title`, `.sub-title`, `.pb-label`) never left alone at a page bottom. A section wrapper is a div whose first child is a `.section-title`; a new always-short section needs a `.detail-grid`/`.ops-list` child to be kept whole. **Page border (v1.200.6):** `pdfPageFrameCss(colour)` (`ProfileKit.tsx`) draws a 2px border around the printable area of every printed page — a `position:fixed` `body::before` inside `@media print`, which the browser repeats per page (a border on the content block would only show at the very top and bottom of the document) — in the same light colour as the line under the stats row (`BLUE_MID` `#93c5fd`; light green `#6ee7b7` for Location) — v1.200.8, it was the dark header colour at first. Print only, so the on-screen preview has no frame. **Running sheet export photos are twice as big (v1.200.5)** — `attachmentImagesHtml` (`SheetDetail.tsx`): **v1.200.7: two photos per row** — each photo is half the observation cell less the gap (`calc(50% - 4px)`, max 320px; v1.200.5's 66% was too big and gave one per row), a third wraps to the next row, and a photo and its CIN caption never split across pages. The live sheet is unchanged.

**Profile export photos (v1.200.10)** — the photo tiles in every profile PDF export (`buildPhotoGridHtml`, `lib/attachmentBanner.ts`: Target "Target photos", Vehicle/Associate/Location "Photos", and each target's photos in the Operation export via `profileSection.ts`) are one size, `PROFILE_EXPORT_PHOTO_PX` = 180px (was 90px, and 95px in the Operation export), with the date/CIN label at 9px. Change that one constant to resize them all.

**Running sheet export text size (v1.200.11)** — the observation text and the Time column in the export are 12px Roboto (were 11px, which looked small printed); set inline on the three row variants in `exportToPDF` (`SheetDetail.tsx`: normal, team and full-team rows). Everything else keeps its size (page body 11px, CIN pills 10px, photo captions 9px, header values 12px), and the live sheet is unchanged.

**Export photo captions (v1.196.3)** — in the running sheet export only (`attachmentImagesHtml` in `SheetDetail.tsx`), each photo has a caption strip joined to its bottom edge, the same width as the photo (the `img` is `box-sizing:border-box` so the two match exactly): black "Taken by **CIN 484**" centred on light grey, several linked CINs as `CIN 484, 503`, and a photo with no CIN linked gets the same strip left blank so every photo in a row is the same height. It replaced the small green CIN pills in the export; the live sheet keeps its pills (`LinkedEntityPills`). The strip sets `print-color-adjust: exact` so the grey prints.

**App fonts are served by RunLog, not Google (v2.2.4)** — `client/index.html` no longer links Google Fonts (a render-blocking stylesheet plus two preconnects on every start, and it wouldn't load offline). JetBrains Mono (Latin + Latin Extended, the same variable woff2 files Google served, SIL OFL, `client/public/fonts/jetbrains-mono-*-variable.woff2` + `LICENSE-jetbrains-mono.txt`) is declared inline in `index.html` and used only by `code, pre, .font-mono`; the woff2 files are in the PWA precache (the `woff2` glob), so it works offline. **Inter was dropped, not hosted:** it was requested from Google but never applied to any visible text — body text is Tailwind's `font-sans` (`ui-sans-serif, system-ui…`), so the app has always shown in each device's own system font (checked on the Operations, Sheets, Intelligence, Profile and Login pages: every text element computed to `ui-sans-serif`; only `html`/`head`/`script` carried Inter), so the look is unchanged. The `:root` font is now plain `system-ui`. **If Inter is ever wanted as the app font**, it is a deliberate visual change: add its Latin/Latin Extended woff2 files, an `@font-face`, and set `--font-sans` in `index.css` — don't just re-add the Google link. The running sheet export still uses its own Roboto (v1.199.1).

## Places Report export looks like the page (v2.50.0)

The Places Report PDF (and the Places section of the Intelligence Package) used to print a plain table, then a list of visits. It now prints what the page shows: four summary tiles, then a card for each place with its kind icon and colour, kind / registered / source / "New this week" / "no departure" labels, visits by weekday, "Usually Mon · Thu around 21:47", and visits / time recorded / average stay, with that place's visits listed under it. Places nothing recognises come last under their own heading, as on the page. `buildPlacesBodyHtml` in `client/src/lib/placesReportExport.ts` carries its own styles so it looks the same in the standalone export and in the Package; the kind icons and colours for paper are in `client/src/lib/placeKindPrint.tsx` (the page's Tailwind colours written as hex). The source labels are shared (`PLACE_SOURCE_TEXT` in `shared/placesReport.ts`). Check: `e2e/screens.spec.ts` "Places Report lists where a target goes…".

## Places Report and Day Route exports: full width (v2.50.1)

The page body of these two exports had a 32px inset on each side while the navy cover band ran the full width of the page, so the cards looked narrower than the header. `.content` now has no side padding, so the cards, section bars and footer line up with the band's edges. Same fix in `dayRouteExport.ts`.

## Summary PDF: the Day Route replaces the Locations map (v2.51.0)

The Supervisor Summary PDF is now Summary, then **Day Route**, then Ego Network. The Day Route page takes the place of the old Locations map when the sheet has a target and places to plot; otherwise the Locations map is used exactly as before.

- It is about **this sheet only**: `routesForSheet` (`shared/dayRoute.ts`) keeps just the sheet's own visits, so another team's movements the same day never appear. A sheet that runs past midnight gets one page per day, with the date above each.
- It **says only what the rows say** (the "plain" version of `buildDayRouteBodyHtml`, `client/src/lib/dayRouteExport.ts`): the pin, the times the rows give and the place, in order, with the Google map picture and a red line between places. No stay lengths, no "No rows for 1 h 25 min" lines and no amber gap colour on the map (`staticMapInput(..., { plainLines: true })`). The Day Route report on the Intelligence page still shows those.
- The place name is shown once ("Terminal 4", not "Terminal 4, Terminal 4").
- Falls back to the Locations map when: the sheet has no target, the report is unavailable to the user, the sheet has no visits, or no place could be located. A day whose map cannot be made still prints its table.
- Check: `e2e/screens.spec.ts` "Summary PDF: the Day Route…" (made-up answers); `server/dayRoute.test.ts` for the rules.

`WeeklyActivityReportPage.tsx` (`exportWeeklyActivityToPDF`): the content is as wide as the navy header band (no side padding on `.content`); each **target is its own card** (navy border, solid navy header band with the target name and the operation's name at the right, so a target's page still says which operation it belongs to); the operation is a header strip above its targets rather than a box around them; **every target after the first in an operation starts a new page** (`.target-block + .target-block`), a new operation already starts one, and the very first target stays on the header page; all pills and chips are rectangles with a small radius (not 999px circles), and the image-card name pills wrap their text instead of clipping. ## Weekly Surveillance Report: overview at the top (v2.52.0)

For an executive reading the report: **each target, the days and times they were worked (start – finish), and their total hours**, per operation.

- **On the page:** at the top of each operation's dropdown ("Overview"): a line of totals (targets · days worked · hours) and a box for each target with its hours and a rectangular chip for each day worked ("Wed 21 Oct 07:00 – 14:00").
- **In the PDF:** the first page, under the header band, is the Overview: one navy-headed table for each operation (Target / Days and times worked / Hours). The operations' own pages then start on page 2, as before (each target still on its own page).
- **Where it comes from:** `WeeklyActivityTargetBlock.shifts` (`server/db/reports.ts`) — one entry per sheet worked, with the start and finish times from that sheet's Supervisor Summary, the same times `coverageHours` adds up. The rules and formatting are in `shared/weeklyOverview.ts` (`overviewOperation`, `shiftTimes`, `hoursText`; tests in `server/weeklyOverview.test.ts`). Sheets with no target show as "No target assigned".
- **Nothing is estimated.** A sheet with no times shows "times not recorded" and adds nothing to the hours; a missing finish shows "07:00 – (no finish time)". Known limit (unchanged from the coverage hours): a shift whose finish is earlier than its start (past midnight) is shown with its times but adds no hours.
- Check: `e2e/screens.spec.ts` "Weekly Surveillance Report PDF…".

## CTO Weekly Tasking: Export PDF replaces Print (v2.57.0)

The full view's **Print** button (a bare browser print of the live page) is now **Export PDF**, which works like every other export: it opens the shared export preview window (`client/src/lib/ctoTaskingExport.ts`, `buildCtoTaskingHtml`; navy cover band, PROTECTED header and the page number footer, the shared Close Preview / Print-Save PDF bar, pop-up-blocked alert) with Supervisors & Contacts (on-call, CTO Inspector, PTT, Team 1, Team 2 with phones), the Priority Board and the Weekly Tasking Calendar (a row for each team, a column for each day with its date; shift in the team's colour, RDO greyed, primary and secondary task). It is A4 **landscape** and built to fit one page. The coverage warnings (tasking issues) are not printed. The cell text (custom shift time, "Other" text) comes from `taskingCellText` (`shared/opManagerWeeks.ts`, tested), the same rule as the full view. Admin only, like the other buttons on that page. Check: `e2e/screens.spec.ts` "CTO Weekly Tasking…".
