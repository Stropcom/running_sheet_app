**Profile pages — one skeleton (v1.181.0)**: the Operation, Target, Vehicle and Location profiles share `components/ProfileKit.tsx` (sticky `JumpBar`, `Photoboard`, `ProfileCard`, `BackgroundCard`, `SheetsCard`, `PersonThumb`, plus the PDF-export helpers) and `components/PersonLinkRow.tsx` (photo + name + tag, opens the person in place). Order: header and stats, jump bar, photoboard (Operation/Target: the target first, then registered associates, each tile scrolling to that person's card; one row per target), Operations, Registered Details/Status, **Background**, Registered Associates, Operational Associations, Running Sheets (assigned, then "mentioned on other sheets"), Imported Documents. Vehicle/Location: Photos (empty state with Add photo), Operations, Registered Target(s)/Associate(s), Operational Associations, Running Sheets, then the Location map. Each profile's Export PDF builds the same order from the same data. **Background** is a single freeform plain-text field per target written in **Add Target to Registry** (`AddTargetBackgroundPanel`, directly under Associates; sent as `registryBackground` on `target.registry.create`/`createLinkedFromAssociate`, appended with `setBackground` mode `append` when the new target is merged into an existing one) and editable on the Target Registry card (`RegistryBackgroundPanel`, same position; `targets.registryBackground` + updated-at/by-CIN; `target.registry.setBackground` rejects Observers and writes a `target_background_updated` audit entry; text normalised by `shared/targetBackground.ts`). It shows on the Target profile and on every Operation profile the target is linked to. It is separate from `operation_target_links.background`, the read-only narrative imported verbatim from a document for one operation (shown under Imported Documents). **Document imports also feed it (v1.189.0):** the narrative is copied into the Background box in Add Target to Registry as "From <Operation> document:" + the text (`labelledImportedBackground` in `shared/targetBackground.ts`; re-labelled if the operation changes while the box is untouched), so it is editable before saving and, on a merge into an existing target, appended after what's there. The verbatim copy under Imported Documents is unchanged.

**Associations must come from a running sheet row that names both (v1.195.1, non-negotiable)** — Operational Associations on every profile (Target, Operation, Associate, Vehicle, Location), the Ego Network and the map all come from the same entity occurrences in `getAllIntelligenceEntities` (`server/db.ts`), narrowed by `attributedRowIds` (`server/entityAttribution.ts`) to rows where the entity is actually named. A false link is a legal problem, so the recognition errs towards *missing* a mention, never inventing one. Two leaks were closed: (1) a bare surname alias matched case-insensitively, so the target **PARK** was credited with every row that said "car park" and every other person in that row became their "association" (and they in turn got the target on their own profile) — an all-caps alias now only matches when written in capitals (`aliasSearchFlags` in `server/personAliasMatch.ts`; a surname typed in lower case is under-reported on purpose); (2) a mention that is exactly a *different registered person* sharing the target's surname ("Hana PARK" when the target is "Soo-Min Hana PARK") was folded into the target because the given name fitted — `mentionIsOtherRegisteredPerson` now stops that, using `registeredNamesByAlias` (every target and associate under their alias). Registry cards (`rowId` 0), assigned sheets and the sheet's assigned target never count as a sighting. **Rule for any new matching code: a bare word may only credit someone with a row if it cannot be an ordinary English word in that row; never match a surname alias case-insensitively; never fold a mention into a target when it exactly names another registered person.** Tests: `server/personAliasMatch.test.ts`.

**Operation profile target blocks (v1.195.2)** — the per-target drop-downs on the Operation profile (`OperationProfileContent.tsx`) start closed; whatever the officer last had open is remembered per operation on that device (`localStorage` key `runlog_op_profile_open_<operationId>`). Jumping from the Photoboard opens that target's block and that is remembered too.

**Heat Map circles stay visible (v1.196.2)** — the circles on the Intelligence Heat Map (`IntelligenceHeatMap.tsx`) used to be sized only in metres (120–550 m), so zoomed out to fit a region a one-visit place was a few pixels wide. Each circle now keeps a minimum on-screen size at every zoom (radius re-set on `zoom_changed`; busier places still larger; true real-world size once zoomed in far enough), is see-through (v1.206.5: 0.38 fill — it was 0.72 with a thick white outline, which made overlapping places nearly solid and let each outline cut across its neighbour — with a 2px edge in the circle's own colour, so two overlapping places read about 60% and the map shows through; the PDF export draws the same, `heatMapExport.ts`), and a numbered white disc at each place carries its rank — the same number as the Top Locations list. Places that overlap at a wide zoom have their discs nudged apart in pixel space with a thin line and small dot back to the true spot; zoomed in they sit on the true spot. The pure sizing/nudge rules are `shared/heatMapLayout.ts` (tested in `server/heatMapLayout.test.ts`). **Export (v1.197.0, branch `runlogheatmap`)** — the Heat Map PDF and the Intelligence Package's Heat Map section (`fetchHeatMapMapHtml` in `lib/heatMapSection.ts`, rules in `shared/heatMapExport.ts`, tests `server/heatMapExport.test.ts`) now draw the same circles and rank numbers as the screen over a **pin-free** Google Static Maps picture, plus a **zoomed inset** (A, B, C — at most three) for each cluster of places whose numbered discs overlap on the main picture, and the Top Locations table has matching rank badges (busiest first, ties in the order given — `rankLocations` / `buildHeatMapLocationsTableHtml` must stay in step). **How it lines up:** we choose the map's `center` and an **integer** `zoom` ourselves (Static Maps takes no fractional zoom; `chooseView`) and project each place with Web Mercator (`project`, `worldPoint` — pinned in the test against Google's published Chicago reference point); the picture's real size is read from the image itself (its pixels ÷ `scale=2`), not trusted from what was requested. Insets sit in the top corners then stacked beneath them, never over a place, never over each other, never at the bottom edge (Google's logo/copyright) — one that finds no free slot is left out; inset circles use the on-screen minimum size only (real-world size would fill the box). **Fallbacks, so the export never ends up without a map because of this:** any failure falls back to the old coloured-pin picture, then to the muted "No geocoded locations" note; an inset whose picture fails is dropped and the main map still prints. Not yet checked against live Google Static Maps (blocked in the dev sandbox) — compare the first real export against the on-screen map. Previously the export's static map was unchanged from pins.

**Intelligence entity set is remembered for a few seconds (v2.2.1)** — `getAllIntelligenceEntities` (`server/db.ts`) used to re-read and re-parse every running sheet row on every call (about 0.7–1.4 s at 2,400 rows, growing with the data), and the Intelligence folder, profiles, map and the "as you type" suggestions each made one. The unscoped build (`buildAllIntelligenceEntities`) is now kept by `FingerprintCache` (`server/intelCache.ts`, tested in `server/intelCache.test.ts`) and reused only while one cheap query says the source tables are unchanged: row count, newest id and newest `updatedAt` of `sheet_rows`, `running_sheets`, `targets`, `associates`, `operations`, plus count/newest id of `operation_target_links` and `entity_aliases` (`INTEL_SOURCE_TABLES` — **if the build starts reading another table, add it there**; the test checks the names and the `updatedAt` columns against the schema). Guards: a build is only remembered when the newest change is at least 2 s old (timestamps have 1 s resolution); nothing is reused for more than 60 s; callers each get their own `structuredClone` (about 8 ms), so a caller that edits its result in place can't affect anyone else; a failed fingerprint query means a fresh build and nothing remembered; `invalidateIntelligenceCache()` is called after the two in-place updates the fingerprint can't see (`operationTargetLinks.background`, `entityAliases`). Per-request scoping (`intelScope` → `scopeEntities`) still runs on every call, after the cache, so access rules are unchanged. Measured against the dev database (2,400 rows): folder list 1.4 s first call, ~150 ms after (the rest is sending 1.4 MB); vehicle suggestions ~60 ms; an edit to a row showed on the very next call. Deterministic: same data → same set.

**Operations page sort + phone Intelligence Folder (v1.198.2 / v1.199.0)** — the Operations page (`Home.tsx`) has the same **Sort: Most recent | A → Z** pills as the Intelligence Folder, under the search box (remembered per device in `localStorage` `runlog_ops_sort`; default Most recent = newest first; search results keep their match order under Most recent because they carry no real created date). On phones the Intelligence Folder operation rows/tiles no longer show the "N entities" pill or the entity list it opens (`max-sm:hidden` in `Intelligence.tsx`); tablet and laptop are unchanged.

**Operational Associations photos are twice as big (v1.200.12)** — the thumbnails under each associated person/vehicle/location on every profile are 112px on screen (`w-28 h-28` in `ProfileDropdown.tsx` and `IntelEntityWithPhotos`; was 56px) and 140px in the PDF exports (`buildEntityWithPhotosHtml`, `lib/attachmentBanner.ts`, `photoPx`; was 70px, label 8px). The Photos card / Target photos tiles are separate (`PROFILE_PHOTO_*`, `PROFILE_EXPORT_PHOTO_PX`).

**Profile photos are one size (v1.193.5)** — the Photos card on the Target, Vehicle, Associate and Location profiles (`EntityPhotosSection`) and a target's "Photos of …" card on the Operation profile (`IntelPhotoStrip size="medium"`) all use `PROFILE_PHOTO_GRID` / `PROFILE_PHOTO_TILE` from `lib/pageKit.ts`: square 11.25rem (180px) tiles from a tablet up (v1.200.10: 75% of the original 15rem / 240px), two equal columns on a phone, whatever the photo's own shape or how many there are. The Photoboard portraits are separate and unchanged, and the small inline thumbnails under entity chips keep their own size.

**Profiles: Registered Details has Addresses and Vehicles sub-headings; Status always shows Special Projects (v2.13.0)** — on the Target profile, each target's block on the Operation profile, the Associate profile, and every one of their PDF exports, **Registered Details** is split under two quieter sub-headings, **Addresses** (Home Address, Address 2…) and **Vehicles** (Vehicle 1…), each with its own count; a group with nothing in it is left out. The entries and the grouping are one pure module, `client/src/lib/registeredDetails.ts` (`targetDetailEntries` — moved out of `RegisteredDetailPanels.tsx`, each entry now carries `kind: "address" | "vehicle"` — and `groupDetailEntries`), used by `RegisteredDetailPanels` (the on-screen panels, `SectionHeading sub`), the Target PDF (`TargetProfileContent.tsx`), the Operation PDF block (`profileSection.ts`) and the Associate profile (screen and PDF, `registeredDetailRows` carries the same `kind`); the Target PDF keeps each field's change history under its Home Address / Vehicle 1. **Status** (Target and Operation profile, screen and PDF) is now **always shown** and always has a **Special Projects** row — the projects, or **"None"** when there are none (`specialProjectsOrNone`, `shared/targetStatus.ts`); MDL and Bail still appear only when answered. The status label column is `w-36` so "Special Projects" stays on one line. Existing data needs no change. Tests: `server/profileDetails.test.ts`. Checked in a browser against the dev database (Target profile at laptop and phone widths, its PDF export, and the Operation profile).

**Operational Associations rows are rounded rectangles (v2.13.1)** — the entity rows under Operational Associations on every profile (Target, Operation, Associate, Vehicle, Location) and in the SMEAC/UCO read-only views were fully rounded pills (`rounded-full`); they are now `rounded-lg`, the same corner as the panels, section bands and person rows around them. Both renderings changed together: `IntelEntityChip.tsx` (the plain row) and `IntelEntityDropdown` in `ProfileDropdown.tsx` (the row that opens its photos). Colours, padding and the entity tones are unchanged.

**Images folder: manually uploaded photos follow the Operation profile's order (v2.14.2)** — in an operation's Images folder (Operation view), the **Manually uploaded** group is now ordered like the Operation profile's Photoboard: the first target's photos, then that target's registered associates and residents (in profile order), then the next target and theirs. The pure rule is `orderPhotosLikeProfile` in `shared/photoOrder.ts` (tested in `server/photoOrder.test.ts`): a photo takes the place of the earliest person it is linked to (a target by `targetId`, an associate by name, case and spacing ignored); photos of the same person, and photos that can't be tied to anyone on the board (unlinked, vehicle / location / CIN links, or someone not registered on this operation), keep their arrival order (newest first) after the placed ones. The page reads the people from `intelligence.operationProfile` (the same query the profile uses); if it isn't available the old order stands. Only the Manually uploaded group is reordered — running-sheet groups and the Running Sheet view are unchanged. Checked: rule tests and the page loads clean; not looked at with real linked photos.

**Operational Associations rows are rounded rectangles in the PDF exports too (v2.14.1)** — `buildChipHtml` (`client/src/lib/attachmentBanner.ts`), the one builder behind the entity rows in all five profile exports (Target, Operation, Associate, Vehicle, Location), now uses `border-radius:8px` (it was `9999px`), matching the on-screen `rounded-lg` rows of v2.13.1. Other pills in the exports (INDICES tag, header type badge, SMEAC tags) are unchanged.

- **Ego Network on screen fills the room it has, on every device (v2.24.2)**: the live canvas used to cap its rings at a fixed size (165 / 290 px), so a big monitor left most of the canvas empty and the names ran over each other. `liveRingRadii` (`client/src/lib/egoNetworkLayout.ts`) now sizes the rings from the canvas: all the height there is (less room for a name past a node), and **stretched sideways** (`xStretch`, the rings become ellipses, limit 0.6–1.9) to use spare width, so a wide screen spreads the network out; a narrow phone squeezes it a little rather than running off the edge. With only one ring in use (1 hop, or 2 hops with nothing a second step away) ring 1 takes nearly all the room and the empty outer ring is no longer drawn. The canvas may grow taller than 760px on a tall screen (`max-h-[max(760px,100dvh-10rem)]`). The "1 hop" / "2 hops" names now sit in the widest gap between that ring's nodes (`widestGapAngle`), not at a fixed angle where they landed on a node. **The PDF export is untouched** (`computeEgoLayout`'s `xStretch` defaults to 1, `exportRingRadii` as before). Checked in a browser with a 15-node graph at 2000×1300, 1600×900, 1366×800, tablet and phone widths; tests: `server/egoNetworkLive.test.ts`. Limit: a phone with a dozen direct links is still tight — the names can touch near the bottom of the ring.

- **Ego Network on a phone / iPad: a circle, smaller names, pinch to zoom (v2.25.0)**: in the compact layout (`useCompactLayout`) the rings are a true circle (`xStretch` 1) that fits the smaller side of a now-square canvas (`liveRingRadii({ compact: true })`, margins `LIVE_COMPACT_MARGIN_*`), and the names are set at 10px (centre name 120px wide, ring 1 88px, ring 2 76px) instead of 12px. Two fingers pinch the picture up to 4× (`MAX_ZOOM`), one finger drags it once zoomed (before that one finger still scrolls the page; the canvas is `touch-action: pan-x pan-y` and the touch handlers are native, non-passive listeners so the browser does not zoom the whole page instead); +, − and Fit buttons do the same without a touch screen. The tap that ends a drag or pinch is swallowed so it does not also pick a node. A new focus or reach starts from the whole picture. Desktop is unchanged from v2.24.2. Checked with a simulated two-finger pinch (CDP touch events) in a browser; e2e: `screens.spec.ts` "Ego Network on a phone…" (uses a made-up graph through a route override, so it does not depend on the database). Limit: with a dozen direct links and two hops the names near the bottom of the small ring can still touch — pinch in to separate them.
