**Associations must come from a running sheet row that names both (v1.195.1, non-negotiable)** — Operational Associations on every profile (Target, Operation, Associate, Vehicle, Location), the Ego Network and the map all come from the same entity occurrences in `getAllIntelligenceEntities` (`server/db.ts`), narrowed by `attributedRowIds` (`server/entityAttribution.ts`) to rows where the entity is actually named. A false link is a legal problem, so the recognition errs towards *missing* a mention, never inventing one. Two leaks were closed: (1) a bare surname alias matched case-insensitively, so the target **PARK** was credited with every row that said "car park" and every other person in that row became their "association" (and they in turn got the target on their own profile) — an all-caps alias now only matches when written in capitals (`aliasSearchFlags` in `server/personAliasMatch.ts`; a surname typed in lower case is under-reported on purpose); (2) a mention that is exactly a *different registered person* sharing the target's surname ("Hana PARK" when the target is "Soo-Min Hana PARK") was folded into the target because the given name fitted — `mentionIsOtherRegisteredPerson` now stops that, using `registeredNamesByAlias` (every target and associate under their alias). Registry cards (`rowId` 0), assigned sheets and the sheet's assigned target never count as a sighting. **Rule for any new matching code: a bare word may only credit someone with a row if it cannot be an ordinary English word in that row; never match a surname alias case-insensitively; never fold a mention into a target when it exactly names another registered person.** Tests: `server/personAliasMatch.test.ts`.

## A suburb spelled like a surname is not that person (v2.46.3)

- **The bug.** The Advent Park pin popup listed **Elliot Marcus VALE** under Targets next to **Arman Reza DARYANI**, from a row that only named Daryani: "…arrived at Advent Park, 345 Kalamunda Road, MAIDA VALE WA". Surnames and suburbs are both written in capitals, so the bare-surname search (pass 3 of `getAllIntelligenceEntities`, `server/db/reports.ts`) matched the suburb's "VALE" and credited the registered person with the row. That list comes from which target entities occur in the same rows as the address (`observedTargets`, `server/db/mapping.ts`), so the same false credit reached the target's rows, Heat Map and associations — a link nobody wrote, which the Intelligence rules forbid.
- **The rule (`shared/suburbMention.ts`, `insideCapsSuburb`, tested in `server/suburbMention.test.ts`).** A capital word is part of a suburb, not a person, when the run of capital words it sits in (one space apart) **(a)** is followed, within the run, by a **state** ("MAIDA VALE **WA**", "SURRY HILLS NSW 2010"), or **(b)** comes straight after a **street type and a comma** and ends the address segment ("…Kalamunda Road, MAIDA VALE (Advent Park)", "…Road, MAIDA VALE."). Such a match is skipped. "Elliot VALE departed", "met VALE at the park", "Smith Street, VALE arrived" are still read as a person; on one row the surname and the suburb are told apart ("Elliot VALE departed 5 X Street, MAIDA VALE WA" still counts the person).
- **Applied in** the bare-surname search for persons (`reports.ts`) and in the Sheet Summary's alias-to-"TGT" replacement (`buildSummaryAbbreviatedText`, `server/db/governance.ts`), so a sheet for target VALE no longer shows "MAIDA TGT". The Target Logger's own matching takes names from movement phrases, not whole rows, so it was not affected; the bracket form "(VALE)" is explicit and unchanged.
- **Direction of error.** Under-report: a suburb written with no state and no street before it, or a surname written straight after "Road, " at the end of an address, is the only way this can miss a real mention. Nothing new can be credited.
- **Checked:** unit tests for the rule and the Summary; reproduced on a real server (two registered targets, the Advent Park row: before, both listed; after, only Daryani) and a row that genuinely says "VALE departed … walked to Advent Park" still lists him; `e2e/screens.spec.ts` ("A suburb spelled like a target's surname does not list that target at the address" — fails with the fix switched off, passes with it).
- **Not checked:** other places that might match a capital surname inside address text (none found in a search of `server/` and `shared/`); the pop-up on a live Google map.

## "Vehicle REGO (Vehicle REGO)": a clean vehicle in the Intelligence folder (v2.49.6)

**Why the bracket appears.** The space-bar trigger in the observation box
introduces a vehicle once with a bracket the first time its rego is typed
("1MEN83" → "1MEN83 (Vehicle 1MEN83)"). The Intelligence folder takes a vehicle in
from that bracket (later bare mentions are matched to it). The Target Logger's
chips write the vehicle plainly ("Vehicle 1MEN83, MENON driver…"), which is **not**
an introduction, so the first time an officer types the rego by hand — even right
after "walked towards Vehicle" — it still gets the bracket. That is by design for a rego typed after a description ("grey Toyota 1ABC123" →
"… 1ABC123 (Vehicle 1ABC123)"). **A rego typed straight after the word "Vehicle"
no longer gets a bracket at all** (`detectVehicleMentionTrigger`): "Vehicle 1MEN83" is
already the short form, the bracket added nothing, and it was what produced the
wrong entity below. Taking the bracket out of such a row, by hand, fixes the
vehicle the same way.

**The fault it exposed (server).** For a bracket that only repeats "Vehicle REGO"
written just before it ("…exited Crown Towers Perth and walked towards Vehicle
1MEN83 (Vehicle 1MEN83), in the valet parking…"), the vehicle's name was rebuilt from
the sentence in front of the rego, so the folder showed **"1MEN83 exited Crown
Towers Perth and walked towards Vehicle"** instead of 1MEN83. `extractEntitiesFromText`
(`server/db/intelligence.ts`) now treats "Vehicle REGO" straight before the bracket as
*no description* (a real description never ends in the word "Vehicle" before the
plate), so the entity is plain **1MEN83** and a real description ("a white Toyota
Landcruiser, bearing WA registration 1FBP509 (Vehicle 1FBP509)") is still kept.
**Rows already saved** keep the odd entity name until the entity is re-read: it is
rebuilt from the row text, so it corrects itself once this version is running (the
Intelligence folder re-reads the rows), and a Merge Entities / alias can tidy any left.

**The second bug (client).** `computeUsedVehicleRegos` only recognised a bare
"(1FCC987)" bracket, not the "(Vehicle 1FCC987)" the trigger itself writes, so a
vehicle already introduced that way was bracketed again each time its rego was typed
in a later row. It now counts both. Tests: `server/entityClassification.test.ts`.

## Day Route report (v2.50.0)

Intelligence → Reports → **Day Route** (between Places and Pattern of Life): pick an operation, a target and a day, and see where the target went that day, in order, with the time at each place and the stretches no row covers.

- **Rules** are in `shared/dayRoute.ts` (tests: `server/dayRoute.test.ts`): `buildDayRoute` takes the same visits the Places Report works out (`getIntelTargetPlaces` → `buildVisits`), keeps the chosen day, orders them by arrival (by departure for a stop that opens with the target leaving), joins two stops in a row at the same place (a hand-over between sheets) into one, and numbers the pins by first visit (1-9 then A-Z, the only single characters Google's static map accepts; past 35 a pin is unlabelled). A leg between stops is `travel`, a `gap` (no row for 60 minutes or more, `GAP_MINUTES`) or `unknown` (the earlier stop has no logged departure, so the time between is never guessed). `staticMapInput` builds the Google request: one pin per place that has a position, a red line for travel, an amber line for a gap or unknown leg (static maps cannot dash a line).
- **Positions**: `intelligence.getPlaceCoords` (`getIntelPlaceCoords` in `server/db/reports.ts`) geocodes each place by the fuller written address, cache-first, the same rule as the Heat Map (`resolvePlaceLatLng`). It only answers for places this target's own rows put them at on an operation the caller can reach, never an arbitrary label. A place that cannot be located is listed but has no pin.
- **Map picture**: `rsMapping.getStaticMapImage` gained an optional `paths` list (one colour per line). The page and the PDF use the same picture.
- **Page**: `client/src/pages/IntelligenceDayRoute.tsx`; **PDF**: `client/src/lib/dayRouteExport.ts` (same shell as the other report exports: cover band, PROTECTED header, map, stops table with gap rows).
- Reads uncertified rows too, like the Places Report. Nothing is filled in.
- Not built yet: clicking a stop to light its pin (needs the live map), and an interactive illustrative file. The static map is a picture, so the pins are not clickable.
- Check: `e2e/screens.spec.ts` "Day Route sits between Places and Pattern of Life…" (made-up answers; the Google picture is replaced). The real Google picture could not be fetched in the build sandbox, so look at it on the live site.

## Target drop-downs inside Operation, Location and Vehicle profiles (v2.76.11)

A registered Target listed in another profile's "Associated Persons" (on the Operation, Location and Vehicle profiles, and the Target profile's own associations) opened as "Profile not found". The server sent the target as `type: "target"` but with an id like `person::<name>` and no `targetId`; the drop-down (`IntelEntityDropdown`) only recognised a target when the id contained "target", so it fell back to the Associate profile, which looks the label up among people who are *not* targets and found nothing. (It only appeared to work when the target's bracket name happened to also create a separate person entity — a plain "Rowan SMITH" — and failed for the usual "Rowan Mark SMITH, born 1 May 1990 (SMITH)".) Now the server puts the target's `targetId` on those entries (`server/db/crossOperation.ts`, the four profile builders) and one pure rule, `profileLinkFor` (`shared/profileLink.ts`, tested in `profileLink.test.ts`), decides what a chip opens: a target opens the Target profile by id; vehicles, places and other people by label. Checked in a browser on the Operation, Vehicle and Location profiles with a target named the usual way: before, the drop-down called the associate profile (404); after, it calls the target profile (200) and opens.

**A shared surname no longer stops a sheet's own target collecting its rows (v2.79.14, urgent fix)** — since the v2.76.6 audit change ("a surname shared by more than one registered person can't be credited to any of them from a bare word"), a target whose TGT alias (the word the TGT chip writes into rows, e.g. "SANTOS", "PARK") was ALSO carried by anyone else on the registry — a relative recorded as an associate of another target, another target — got **no** credit for rows that only say the bare surname: the Intelligence folder showed the target as "Indices" (card only, never in a row), the Ego Network had 0 links and the Heat Map was empty, even though the sheet was full of rows about them. Common surnames (PARK, SANTOS) hit this straight away. Fixed in `getAllIntelligenceEntities` with one pure rule, `bareAliasOwner` (`shared/aliasSeeding.ts`, tests `server/aliasSeeding.test.ts`): a shared alias is still credited to nobody from a bare word **except on the sheet that was opened for one of them** — there the bare surname is that sheet's target (the TGT chip writes exactly that). The audit's safeguards stay: a person the sheet itself introduces under that surname ("Rosa Maria SANTOS (SANTOS)") still wins on that sheet; a shared surname on someone else's sheet, or a sheet with no target, is still credited to nobody; "never match a surname alias case-insensitively" and the other-registered-person check are untouched. Nothing is stored, so existing rows are re-read live and the folder corrects itself after the deploy. Checked on a scratch database with a SANTOS target + an associate "Rosa Maria SANTOS" on another target: the target had 0 real rows from v2.76.6 on and 2 before / after the fix (same rows, same text). **How it was missed:** the audit tests covered the pure alias rules but nothing built the whole entity set for a target whose surname is shared; the proof above is the scenario to keep (run `getAllIntelligenceEntities` over a target + a same-surname associate + rows that only say the surname).

**A registered vehicle or address named in plain text now counts (v2.79.16)** — the Intelligence folder credited a vehicle or place only when the SAME sheet bracketed it ("Vehicle 1EMB303 (1EMB303)"). Rows written by the TGT chip and the Target Logger ("Vehicle 1EMB303, SANTOS driver…", "departed 19 Jacaranda Drive and continued via:") name the plate or street plainly and never bracket it, because the target card is the introduction — so the target's own vehicle and home address showed as card-only "Indices" with no sightings. This was long-standing (it reads the same on code from before the v2.76.6 audit), not the v2.76.6 shared-surname break. One pure rule in `shared/registeredMentions.ts` (tests `server/registeredMentions.test.ts`), used by `getAllIntelligenceEntities` after each row's bracket pass: a **registered plate** counts when its exact registration is a whole word outside any bracket and is not a measurement ("30cm"); a **registered address** counts only when it is number-led, written exactly as the registry holds it (any case, street type in full), not part of a longer number ("119 …", "2/19 …"), and not followed by a different suburb ("19 Jacaranda Drive, BIBRA LAKE" is not the registered ATTADALE one; a surname after the comma — "…Drive, SANTOS driving" — is a person, not a suburb). A row the bracket path already credited is never counted twice. A vehicle or place nobody registered is unchanged. Checked on a scratch database (target with home address + two vehicles, rows written the way the chips write them): 1EMB303 went from 0 to 2 real rows and 19 Jacaranda Drive from 0 to 1; the second registered plate, which no row mentions, stays at 0 (nothing invented). Nothing is stored, so existing rows are re-read live after the deploy. Limit: a place with no number ("Garden City Shopping Centre") is still credited only when bracketed — a bare name is too often an ordinary word.

**A registered address with its suburb is credited from plain text (v2.83.11, fix)** — an address on a Target or Associate card is stored with its suburb and state ("19 Jacaranda Drive, ATTADALE WA"), but a running sheet row usually says just "departed 19 Jacaranda Drive". The builder (`server/db/intelBuild/registeredMentions.ts`) used to look for the whole card text in the row, so those rows were never credited and the address showed as card-only "Indices". It now looks for the street (`registeredStreet`) and checks the suburb beside it (`registeredSuburb`): a row naming the street with the registered suburb, or with no suburb, counts; a row naming it with a *different* suburb ("19 Jacaranda Drive, BIBRA LAKE") does not; "119 …", "2/19 …" and a name that is not number-led never match (`shared/registeredMentions.ts`, `server/registeredMentions.test.ts`). The rule stays narrow on purpose (err towards a missed mention). A row naming the street with no suburb is credited to the registered address — the same convention the plates use, and what "vicinity of 12 Smith Street" on the target's own sheet needs. Checked: unit tests (22); the Intelligence golden check (extra address mentions only, reference updated); old and new builders compared on four databases — mentions only added, none removed, nothing else changed.

## The profiles' "Jump to" bar stays pinned on an iPhone (v2.83.29)

On a phone the Jump to bar (Photoboard, one chip per target …) on the Operation, Target,
Vehicle and Location profiles scrolled away with the page instead of staying under the header.
Cause (`JumpBar` in `components/ProfileKit.tsx`): the bar was `position: sticky` **and** its own
horizontal scroller (`overflow-x: auto`, so the chips could slide sideways), plus a blur
filter — Safari on an iPhone does not pin an element that scrolls on its own, while Chromium
does (which is why it could not be reproduced in the sandbox). The running sheet's toolbar,
which is plain sticky with no overflow and a solid background, sticks fine. Now the bar is two
elements: an outer `sticky` wrapper with the border and a solid background and **no overflow**,
and the chip row inside it, which is what scrolls sideways on a phone and wraps on a laptop.
Nothing else about the look changed. The rule — *an element that is sticky must not have any
overflow set* — is checked in `e2e/profile-jump-bar.spec.ts` (390 px: the sticky element has no
overflow and stays pinned to the top of the scroll area after scrolling; it failed on the old
structure first). **Not tried on a real iPhone here — check after deploy:** open a profile
with several targets, scroll down, and the bar should stay under the header.
