**Add Target to Registry is four tabs (v1.190.0)** — Target, Residents, Associates, Background (`AddTargetDialog.tsx`; building blocks in `components/AddTargetKit.tsx`; the rules are pure functions in `lib/addTargetSteps.ts`, tested in `server/addTargetSteps.test.ts` — change the rules there, not in the JSX). A tab is done when every section on it is **filled in or has its "nothing to add" box ticked** (No known address / No known vehicles / No other residents / No associates / No background to add); tabs open in order (a later tab is locked with a padlock until the one before is done), Next is greyed with a red line saying what is missing, and Save Target only works when all four are done. Every section opens with its first form already showing and has a full-width "Add another address / vehicle" button at its bottom; Residents/Associates open with one blank person. A "none" box can only be ticked while the section is empty. Every person, vehicle and address has an Upload Image: vehicle/address photos are staged as `StagedImage.linkTo = { type: "item", category: "vehicle" | "location", ownerKey, itemKey }` and linked on save by the entry's full label (`composeVehicle`/`composeAddress` `.full`, `fromRegistry: true`). The Target tab adapts to the target type: a Person has identity + addresses + vehicles; a Vehicle target's vehicle is the identity (address optional/none); a Location target's address is the identity (vehicles optional/none). **Departure/Arrival were removed from this dialog** (the `dep`/`arr` columns stay and are saved as null). **v1.191.0:** MDL, Bail and Special Projects are all required (red asterisks; the Target tab won't finish until each is answered); Special Projects gained **None** (an answer, saved as no projects), **TRACKER** and **LD** — a target now carries seven projects (`TARGET_SPECIAL_PROJECTS` in `shared/targetStatus.ts`: TI, LBS, SEEK, CAD, Tracker, LD, Coyotes — with None that is eight equal boxes), all of which sync both ways with the Sheet Summary, with the Summary's hints (`SPECIAL_PROJECT_HINTS`). The "No known …" boxes are plain (a green tick when ticked, no dashed red outline), the step note is red/green text with an icon (no banner), and each section's border and header use its entity colour (person rose, addresses emerald, vehicles amber, resident sky, associate violet) like the Target Registry card.

**An identity-linked Target and Associate share their photos (v1.202.1)** — a registry Associate made a Target (or the reverse) is one person kept as two records (`targets.linkedAssociateId` / `associates.linkedTargetId`, the "Identical profile" banner), and the app combines intelligence across both, but a photo is linked to ONE record (a target by id, an associate by label key), so a photo on the associate never showed on the new target's profile or Photoboard ("No photo"). `getAttachmentsForEntity` (`attachment.byEntity`: Photos card, Photoboard, thumbnails) now also returns the linked counterpart's photos — a target gets its linked associate's, an associate gets its linked target's (`identityLinkedCounterparts` in `server/db.ts`; only linked records, never a same-name stranger) — and the Operation profile's batch lookup (`getAttachmentsForOperationEntities`) slots the associate's photos into the linked target's list. It is read-time, so it fixes existing pairs and later uploads to either record, with no migration or copying. The photo's `linkId` is the link on the record being viewed when there is one, else the other half's (so the unlink button still works). Checked against the dev database with a seeded pair, both directions and an unrelated same-name associate.

**Promoting an associate to a Target files the old target as its associate (v1.203.0)** — when an associate X of target A is made a Target B (`createTargetLinkedToAssociate`, the "same person — link and copy" route), A is also filed as an associate of B, in the same transaction (`addReciprocalAssociate` in `server/db.ts`): A's identity fields are copied (`LINKED_SYNC_FIELDS`), the relationship is always "associate", and the new row is identity-linked to A (`linkedTargetId`, `targets.linkedAssociateId`) unless A is already linked to another associate, in which case it is a plain row. It never duplicates — if B already has an associate for A (linked to A or the same name, live or soft-deleted) nothing is added, so a removed reciprocal stays removed — and is skipped when A is deleted. **No backfill:** pairs promoted before v1.203.0 are not touched (it would create records officers never saw); add the associate by hand. The reverse (`createAssociateLinkedToTarget`) is unchanged.

**Import Target no longer hangs on the on-device AI step (v2.2.5)** — a large document (e.g. a tactical profile PDF) took minutes and then showed "Unexpected token '<', "<html> <h"… is not valid JSON": that is **nginx's own 504 page** (nginx waits 60 s by default), not a RunLog error. The rules-based reader is fast (about 0.1–0.4 s for the fixtures; ~2 s cold); the slow part is the optional **on-device document AI pass** in `target.registry.parseDocument` (`documentImport/localDocumentAI.ts`: Qwen2.5-1.5B via transformers.js on the server CPU, up to `MAX_AI_CALLS` = 8 sequential greedy generations, and the first call loads ~1.5 GB of weights — minutes on a 2-vCPU droplet). It is additive and display-only (each suggestion is re-parsed by deterministic code, `documentAIVerify.ts`), so it is now **time-limited**: `AI_TIME_BUDGET_MS` = 15 s for the whole document (`documentImport/aiBudget.ts`, `withinBudget`, tests `server/aiBudget.test.ts`). When the budget runs out the remaining checks are skipped ("declined") and the rules' own reading is returned, exactly as when the model files aren't installed; a model call can't be cancelled, so while one is still running a new import **skips the AI pass** (`busy`) rather than queueing behind it, and a model error skips just that check. The first import after a restart will usually run out of time while the weights load (the load keeps going in the background, so later imports can use the model). **Each import now logs one line** — `[ImportTarget] <file> (<KB>): read N ms, AI model ready|missing|incomplete, N AI check(s) in N ms (stopped early: budget|busy|error), total N ms` — look at it (`pm2 logs`) before guessing why an import is slow. The dialog also words a non-JSON/HTML server reply as "The server took too long to read this document and stopped waiting…" (pointing at the **Parse & extract fields** switch — off attaches the file as-is) instead of showing the raw JSON error. **If imports still fail with a 504 even though the log says the work finished quickly or the file is huge, raise nginx's `proxy_read_timeout` (droplet-only `/etc/nginx/sites-available/runlog`).** Note for the Golden Rule: this AI pass is on-device (no network call) and was already in the app; it is the reason the AI budget exists, and switching it off entirely (remove the model files, or skip the `aiModelStatus === "ready"` block) is a supported option — the rules-based import does not depend on it.

**Document AI on/off switch for the owner (v2.3.0, migration 0127)** — **Access Management → Document AI — Import Target** (`components/admin/DocumentAiCard.tsx`, owner only like Command features / Zero data: `isFeatureOwner`, checked on the screen and again in every `documentAi.*` procedure in `server/routers.ts`) turns the on-device AI check in `target.registry.parseDocument` on or off, so the owner can compare imports with and without it. **Default ON** (no row = the behaviour before the switch); off skips the whole AI step (`aiModelStatus: "off"` in the response, the rules' own reading is returned, the log line says `AI model off`). It is a server-wide setting, not per Command (the model is one process), stored in the new **`app_settings`** table (`settingKey` / `settingValue` "true"/"false" / `updatedByCIN`; `server/appSettings.ts` `getBoolSetting`/`setBoolSetting`, 2 s cache; key `DOCUMENT_AI_SETTING` = `documentAiEnabled`) — a generic home for future owner switches that aren't about one Command; **it is in `KEEP_TABLES`** (Zero data keeps it). Each change writes a `document_ai_changed` audit entry (new `audit_logs.action` value, same migration). The card also shows whether the model is installed (`getDocumentAIModelStatus`: with no model files the switch has no effect and it says so) and a **tally since the server started** (`documentImport/aiStats.ts`, in memory, reset on restart or with **Start counts again**): imports with / without the AI step, imports that had anything for it to check, AI checks made, how many **agreed with the rules**, how many **offered a reading** (an AI answer the deterministic parser accepted — `documentAIVerify.ts` "confirmed" / "suggested"), imports that hit the time limit, and average import time with vs without the AI. **If "Offered a reading" stays 0 across real documents, the AI adds nothing and can be removed** (see v2.2.5 for the memory/time cost: ~3.6 GB resident, an OOM kill was seen on a 4 GB droplet). Tests: `server/aiStats.test.ts`. Checked against the dev database: switch off → `aiModelStatus: "off"`, on → `missing` (no model files in the sandbox, so the AI path itself can't be exercised here), another admin refused (403), audit rows written, card symmetric at laptop and phone widths with no sideways scroll.

**Import Target PDF hang fixed — an image repeated on every page (v2.3.1)** — the real cause of the "very slow, then `Unexpected token '<'` / server took too long" on a tactical profile PDF (AURORA …Tactical_Profile) was **not** the AI step: `extractPdfPageImages` (`documentImport/pdfTextReader.ts`) waited for each embedded image with `page.objs.get(id, cb)`, but pdf.js keeps an image used on more than one page (the template repeats an icon bar / legend on every page, see `imagePhotoFilter.ts`) in the **document-wide store `page.commonObjs`** under an id starting `g_`; the page's own `objs` never answers for it, so the promise never resolved, `readPdfText` never returned and nginx cut the request at 60 s. Reproduced with a 3-page PDF reusing one image (page 1 read fine, page 2 hung forever; a 40-page one never finished in 5 minutes) and fixed: `getPdfObject` picks the store by id (`g_` → `commonObjs`) **and** never waits longer than `PDF_IMAGE_WAIT_MS` (5 s) for any one image — a skipped image is a smaller result, never a hung import — and a shared (`g_`) image is read once per document, not once per page. The same 40-page, 120-image worst case now reads in ~9 s. Tests: `server/documentImport/pdfSharedImage.test.ts` (store choice, the timeout, and a real PDF built with pdf-lib that reuses one photo on 3 pages). **When an import hangs, suspect a promise that can never settle before blaming the model.** The v2.2.5 AI time limit and the v2.3.0 switch remain, but the AI was not what was slow here.

**Tactical Profile PDFs are read card by card, hyphenated given names, repeated photos (v2.3.2)** — an agency "Tactical Profile" imported as a **PDF** used to come out as one pile: the first target's name, every address (8) and vehicle (16) of every person in one list, 24 photos that all defaulted to "This target", and a "Who is this?" row full of junk names ("Tactical Profile AURORA", "Vehicles Mirela Ana DRAGOVIC", "Passport AUR"). The same document as Word was already read card by card (`tacticalProfileCards.ts` → `mapTacticalProfile`) but a PDF is flat paragraphs, not tables, so the card reader never fired. Three fixes, found by running the real AURORA PDF and DOCX (a real training profile, all content marked fictional; **not** committed — the tests use an invented document with the same layout): (1) **`documentImport/tacticalProfilePdf.ts`** (`tacticalTablesFromPdf`) finds the cards in the PDF's paragraph run (a "Target" paragraph + person name + TELCO line; an "Associate of Target" paragraph with the name/address above and the owner below) and rebuilds the SAME table shapes the Word reader sees, so one existing reader and mapper serves both — there is no second rulebook for what a card means. It copes with the PDF text layer's quirks: page furniture removed, a vehicle wrapped over several paragraphs rejoined, "Registered Vehicles Linked Vehicles" side-by-side headings read as the first column's, "STATUSACTIVE" glued, a telco value printed away from its label handed back to it, the "Target's and Associate's Vehicles" list rebuilt (it supplies a card's missing vehicles, as in Word), and DOBs the text layer lists apart from the associate cards matched in document order **only when the counts agree**. It fires only on the template's own signature (a stray "Target" heading isn't enough) so any other PDF is untouched. **Bail is left blank for a PDF** (the template's rotated BAIL label is lost from the text layer, so the answer can't be tied to its card; the officer answers it, nothing is guessed). (2) **A given name with a capital after a hyphen** ("Jean-Baptiste", "Mary-Anne") was not a person's name to the name patterns in `freeTextEntityScan.ts` / `targetProfileFieldMap.ts` (`[A-Z][a-z'-]+` can't contain a capital), which silently dropped Amadou Jean-Baptiste TRAORE's whole target card from the **Word** version too and blanked the owner on four associates; the given-name token is now `[A-Z][a-z'-]+(?:-[A-Z][a-z'-]+)*` in all four patterns. (3) **A photograph shown twice** (a photoboard thumbnail and again on the person's own card) is offered once: `imageDedupe.ts` (`dropRepeatedPhotos`, applied at the end of `readPdfText`) drops a repeat whose 16×16 greyscale fingerprint differs by at most 4 of 256 bits and has the same shape, keeping the copy with the person's caption. Measured on the real 24 photos: the twins matched exactly (0 bits) and the two closest DIFFERENT people differed by 13 — **never widen `MAX_DIFFERING_BITS` without re-measuring; a dropped real photo is worse than a duplicate.** Result for the real PDF now equals the Word version: **Target 1 of 3** (Mirela DRAGOVIC / Kieran DOYLE / Amadou Jean-Baptiste TRAORE), each with only their own addresses and vehicles, 9 associates each attributed to the right owner with their own address, vehicle and DOB, 12 captioned photos, no look-alike names. Tests: `server/documentImport/tacticalProfilePdf.test.ts`. Checked end to end in the real Import Target dialog against the dev database (review shows only the first target's own 3 photos, "9 more photos belong to the other targets", its 2 associates pre-selected). **Not covered:** the on-device AI check (no model files in the sandbox), and other agencies' PDF templates — a new one is a new recogniser plus a fixture, like this one.

**Surnames with a Mc / Mac prefix (v2.3.3)** — the RAVEN profile (4 targets, 14 associates, PDF and Word) exposed a second name-shape gap: **"Teagan Rose McLEOD"** — a surname written `McLEOD` / `MacDONALD` (lower-case prefix, then capitals) — was not a person's name to the name patterns (surname had to be all capitals, `O'BRIEN` allowed), so the **Word** reader silently dropped her card (13 of 14 associates) and the PDF reader mis-assigned two associates (she became a copy of her own owner, and the associate before her lost his owner and vehicle). The surname token is now `(?:[A-Z]'|Mc|Mac)?[A-Z]{2,}(?:-[A-Z]{2,})?` in `freeTextEntityScan.ts` and the two associate-line patterns in `targetProfileFieldMap.ts`, and `splitPersonName` accepts the prefix, so the name still splits into given names + surname. Result for the real RAVEN files: PDF = Word = 4 targets, 14 associates each with their own owner / address / vehicle / DOB, 18 captioned photos (the dialog shows "Target 1 of 4"; the first target's own 6 photos, 12 held for the others). **A card that fails the name check is dropped silently by the Word reader** (`readTacticalProfile`) — if an import is ever short of a person, check their name shape first (other prefixes — De, Di, Van, Le, La, D' — are not handled yet; add one with a test when a real document needs it). Test: `server/documentImport/tacticalProfilePdf.test.ts`.

**Import Target window is as wide as Add Target (v2.3.5)** — `ImportTargetDocumentDialog.tsx`'s `DialogContent` was `max-w-lg` (512 px) while Add Target to Registry is `sm:max-w-xl md:max-w-2xl lg:max-w-5xl`; the Import window now uses the same three width steps (576 / 672 / 1024 px at sm / md / lg), keeping its own `max-h-[90vh]` scroll. On a phone it stays the usual margin-from-the-edges dialog (Add Target goes full screen there; the review is a read-then-continue screen so it didn't need that). Checked with a real document at laptop (1024 px), tablet (672 px) and phone (358 px): no sideways scroll, and the "Who is this?" name chips now sit on one or two lines instead of six.

**An import never saves the same photo twice on one person (v2.3.6)** — an associate (Jared Koa WILLIAMS) ended up with three identical copies of the same photo on his profile after the same document was imported more than once. `saveStagedImages` (`AddTargetDialog.tsx`) already skipped a byte-identical photo for the **target** only (its own comment said associates weren't covered); the check is now general: before any staged photo is uploaded, the entity it will be linked to (the target by id; an associate, a vehicle or an address by its name / label — `attachment.byEntity`) is asked for the photos it already has, each is SHA-256 hashed (`sha256Hex`, cached per entity for the save) and an identical one is **skipped**, and every photo saved is added to that set so a repeat later in the same batch is caught too. Different photos of the same person are of course kept. The officer's own explicit "keep a second copy" on a target photo (`duplicateImageKeys`) still stands. Copies that were **already saved** are not removed (no backfill) — delete them from the profile's Photos card. Hashing needs the stored files, so it relies on the signed-in photo route of v2.2.3 (the browser sends the cookie) and fails open: if a photo can't be fetched or hashed it is treated as new, never dropped. Checked against the dev database with the real RAVEN PDF: one import left exactly one photo on each associate. **Not covered:** the same photograph saved through a different route (e.g. uploaded by hand from the Images folder) is only caught when it goes through this save.

**Imported narrative has its wrapped lines joined in the Background box (v2.3.7)** — a document typed or converted with a hard line break at the end of every visible line arrives as one paragraph per line, so the Background that Add Target seeds from an import ("From <Operation> document:" + narrative) showed a blank line after every line, even mid-sentence ("… CANNINGTON WA" / "6107 remains as a previous address."). `reflowWrappedLines` (`shared/targetBackground.ts`, applied inside `labelledImportedBackground`; tests in `server/targetBackground.test.ts`) joins two neighbouring lines with one space only when the first did not finish — no `. ! ? ;` at the end, not a short colon-ended label ("07 August 2026:"; a long line ending in a colon is a wrapped value and does join), not a heading (`isHeadingLine`) — **and** the second plainly carries it on (starts lower case or `@`) or the first is at least 70 characters (`WRAPPED_LINE_MIN_CHARS`, i.e. it was wrapped, not a short label). Short label lines ("Nadia Farah QURESHI", "Mobile: …"), headings and every break after a finished sentence stay exactly as they were; no word changes. Only the Background box is changed: the verbatim copy under Imported Documents (`operation_target_links.background`) and the review screen's own display reflow are as before, and Backgrounds already saved are not rewritten. A wrapped line that happens to be under 70 characters, ends without a full stop and is followed by a capitalised word is not joined (deliberate — it can't be told apart from a short label). **v2.4.0:** a Background already saved with the broken lines (imported before 2.3.7) can be tidied from the Target Registry card — the Background panel (`RegistryBackgroundPanel.tsx`) shows an outline **Join broken lines** button next to Save whenever `reflowWrappedLines` would change the text; it only rewrites the box (nothing is saved until **Save background**, and **Discard changes** puts it back), so the officer sees the result first. Nothing is rewritten automatically.

**A driven vehicle that isn't on the target's registry is added to it automatically (v2.15.0)** — when a row names the sheet's registered target as the **driver** of a vehicle whose rego isn't already on his registry (`targetVehicleRegos`: V1, legacy V2, every extra vehicle), the vehicle is filed on the registry as his **next vehicle** (an extra vehicle, i.e. V2, V3…; his V1 if he has none yet), filled in with what the row itself says about it — **colour, make, model and body type** ("A blue Mercedes Benz C200, sedan, bearing WA registration 1FAB007" → blue / Mercedes Benz / C200 / Sedan, state WA); a part the row doesn't state is left blank, nothing is guessed, and a rego the row only names bare takes its description from another row on the same sheet that brackets it. It composes the same wording Add Target does ("blue Mercedes Benz C200 Sedan, bearing WA registration 1FAB007 (Vehicle 1FAB007)"), so chips, the flag and exports treat it like any registered vehicle. **Deliberately quiet** (the user ruled out a toast, an "auto-added" note with a Remove, and an audit entry): nothing is shown or logged — the officer sees the new vehicle on the Target Registry card and edits or removes it there like any other. The pure rules are `server/vehicleAutoAdd.ts` (tested in `server/vehicleAutoAdd.test.ts`): `driverVehiclesInText` (a "Vehicle REGO" / "(Vehicle REGO)" mention followed by "NAME driver" in its own clause — a passenger, "unseen occupants", "male driver", "UM1 driver" never count), `driverIsTarget` (the sheet's target only; its surname written **in capitals** as a whole word — never case-insensitive — compatible given names via `aliasMentionCompatible`, and never a different registered person sharing the surname via `mentionIsOtherRegisteredPerson` against the target's associates), `describeVehicleInText` and `composeRegistryVehicle` (it reuses the document-import parser's colour, shade-word and body-type lists, now exported from `server/documentImport/vehicleLineParser.ts`; a make must be on `VEHICLE_MAKES_PATTERN` or a short extra list so narrative is never read as a make; "Mercedes Benz", "Land Rover"… are two-word makes). The database part is `autoRegisterDriverVehicles` (`server/db.ts`), called from `createSheetRow` and `updateSheetRow` after the row is saved, so it covers the sheet, RS Quick Entry and offline-draft sync alike; it **never throws** (a failure is logged and the row is still saved), goes through `updateTarget` (so an identity-linked associate stays in sync) and only acts on **person** targets that aren't deleted. **On an edit only a driver the old text didn't already name is considered**, so a vehicle an officer removed from the registry doesn't come back each time the row is touched; a copied sheet (`copySheet`) never triggers it. Not built: the "Add vehicle to registry" button for passengers or hand additions (the mock-up still exists), and Observers' rows aren't treated differently (an Observer can't add rows). Checked against the dev database with a temporary sheet on target ROCHA (then removed): a passenger row adds nothing; a driver row adds the Mercedes C200 with colour / make / model / type; a repeat and an already-registered rego add nothing; a bare mention picks up the description from the earlier row; editing a row to name him driver adds it.

**Face matches: no repeat questions once a person is confirmed or turned down (v2.17.7)** — after "Yes, same person" on DOYLE and **Confirm upload**, the app asked about two more photos of DOYLE and about PIKE; and after "No, different person" it kept showing other photos of the person just turned down. One pure rule, `shared/faceMatchTriage.ts` (`triageMatches`, `autoDecision`, `identityKey`; tests `server/faceMatchTriage.test.ts`), now decides what is still worth asking, and the early pop-up (`FaceMatchPreview`), the after-link pop-up (`PossibleMatchDialog`, which skips as it steps), the saving step (`settleMatches` in `LinkAttachmentDialog.tsx`) and the second picker (`FaceSelectPicker.tsx`) all use it: **(1) once the photo is confirmed as a named person** (a "same" answer on one of their photos, or picked in the Link-to list) **their other photos are not asked about**; **(2) once a person is answered "different", their other photos are not asked again** — each is recorded as "not a match" (`dismissFaceMatch`) so it is not offered next time either; **(3) once the photo is confirmed as a named person (target / associate), a face on file under a DIFFERENT name is not asked about unless it scores at least 50%** (`HIGH_CONFLICT_SIMILARITY` = 0.5; first set at 0.7, lowered to 0.5 at the user's request in v2.17.8 — a very close match under another name is still worth a look, since two registry records may be the same person); below 50% it is recorded as "not a match" without asking. Identity = a target by id, an associate by name; an **Unidentified Person** entry is its own record and is never skipped (one could be the confirmed person). The officer's own answer is never overridden: "different" stands, and a "same" that doesn't fit who the photo was finally linked to is asked again. The first search still uses `FACE_MATCH_THRESHOLD` 0.35 (`server/db.ts`) — the 50% bar only applies to names that conflict with a confirmed person. Not looked at in a browser (no face photos in the sandbox; the rule is covered by unit tests built from the four matches in the report: three DOYLE photos at 64 / 54 / 49% and PIKE at 36%).

## Face picker: matches for the tapped face, and only the strongest faces highlighted (v1.205.0, pop-up v1.206.1, question v1.206.3)

Face recognition is still fully on-device (RetinaFace + MobileFace via onnxruntime, no network) and still **never links anyone by itself** — the upload only counts faces (`runFaceDetectionForAttachment`) and the one-face-only suggestion (`previewFaceMatch`) is unchanged. New: **the moment the officer taps a face** in the link window (`TapSelectFace` in `LinkAttachmentDialog` — existing photo, or one being staged for upload), the app looks for similar faces on file and, when there are some, **opens the existing "Possible match" pop-up by itself** (`components/FaceMatchPreview.tsx` → `PossibleMatchDialog` with `onPreviewAnswer`): the same zoom (Small → Maximum), source photo, who it is filed as, operation / sheet and similarity %, with the tapped face **cropped** on the left (`FaceCrop`) and the question **"Is it the same person?"** with **"No — different person"** (next match; closes after the last) and green **"Yes — same person"** (closes and **selects that person** in the list — `handleMatchAnswer` stages the candidate's own target / associate, or a new Unidentified Person). The first (v1.206.1) version only had Previous / Next / Close; the question was restored at the user's request. Nothing is linked until Confirm upload / Save; the answers are remembered per tapped face and matched link (`faceAnswers`) and **applied when the link is made** (`settleMatches`): "different" is dismissed (`dismissFaceMatch`), "same" on an Unidentified Person merges the identities (`confirmFaceMatch`), "same" on a target / associate that was chosen needs nothing more — so the after-link Same person / Not a match pop-up (unchanged) only asks about matches that were not already answered. A status line under the photo says "Checking…", "N similar faces on file." with a **View** button (reopens the unanswered ones), "All N … answered." or "No similar faces on file."; the pop-up opens once per tapped face. `attachment.faceMatches` (existing photo) / `attachment.faceMatchesFromBytes` (staged photo) embed **only the tapped face** and return the closest few (up to 5, similarity ≥ `FACE_MATCH_THRESHOLD` 0.35) from operations the person can reach (`filterByOperationAccess` on `sourceOperationId`, in `faceMatchesFor`, `server/routers.ts`). **Only the strongest 4 faces are highlighted** (`shared/faceRank.ts`: strength = detector confidence × face area, `STRONG_FACE_LIMIT` = 4, tested in `server/faceRank.test.ts`); `detectFaces` / `detectFacesFromBytes` return every face with `rank` and `strong`, the picker numbers the strong ones 1–4 and the rest sit behind a **"Show N more faces"** link (dashed grey boxes, tappable by hand; a selected face is always shown). `index` is still the face's position in the detector's output — every confirm/compare call relies on that, so ranking never reorders. Detection no longer embeds every face: `detectFaceBoxes` (boxes only, cached per photo for 10 minutes, 8 photos) serves the upload count and the boxes, and `embedFaceAt` embeds just the face asked for; `detectAndEmbedFaces` remains for the confirm/compare paths. ## Compare Faces: bigger window, photos no longer pile up (v2.49.1)

The Compare Faces picker (`components/CompareFacesDialog.tsx`, Images page) had two
faults. **Small window:** the base dialog caps itself at `sm:max-w-lg`, which beat
the `max-w-2xl` the dialog asked for, so it was always about 512 px wide. It now
sets `sm:max-w-5xl` (and `max-h-[92vh]`), so two photos sit side by side with room
to compare faces. **Photos on top of each other:** the photo grid was itself the
height-limited scroll box (`grid max-h-48 overflow-y-auto`); in some browsers a
grid whose own height is capped squeezes its rows to fit, so the tiles overlapped.
The scroll box (`max-h-[55vh]`, was 192 px) is now a plain block with the grid
inside it (`auto-rows-max`, 3 columns, 4 from `sm`), so the limit can never squeeze
the rows. **Rule:** don't put `overflow` and a height limit on a grid you also
want the rows of to stay full height — scroll an outer block instead. Checked in a
headless browser with mock photos at laptop and phone width (the overlap itself
only shows in some browsers, so the same-browser overlap was not reproduced here).
