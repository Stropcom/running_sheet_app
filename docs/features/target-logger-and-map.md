**Heat Map on the Map page (v1.198.0)** — a **Heat Map** switch in the Map Settings pane (below Nearby Location; not shown to map-only Investigator accounts, whose role can't call the report's data). Off by default; on, it shows **Operation**, **Target** (All targets or one) and **Transparency** (0–80%, default 30), and nothing else — no When picker, it is always **all time** (`getHeatMapLocations` with `when: { mode: "all" }`), no counts, one look: a **soft fade** (a radial gradient per place, colour from the same cool→hot ramp as the report). It is drawn by `components/MapHeatOverlay.tsx` as a `google.maps.OverlayView` in the map's **`overlayLayer` pane** — under the marker pane, `pointer-events: none` — so every pin stays on top and clickable (the `OverlayView` subclass is built inside the effect, never at module scope, same rule as `divIconOverlay.ts`). Size is `heatFadeRadiusPx` in `shared/heatMapLayout.ts` (tested): a minimum on-screen radius (34 px + up to 30 for the busiest) at any zoom, the real-world area ×1.5 once zoomed in, capped at 320 px so it never floods the map. **Defaults follow the top of the pane (v1.198.1):** the Operation and Target selects each start on **"Current — …"** (`heatOpChoice` / `heatTargetChoice` = `"auto"`): the operation is the running sheet's (`rsSelectedOpId`), else the map's first selected operation (`selectedOpIds[0]`), else the first reachable; the target is the running sheet's target (`rsTargetData.id`, only when the heat operation is the running sheet's), else a single selected target (`selectedTargetIds`), else all — and a default target is used only if it belongs to the heat operation (`heatTargets`), the request waiting for that list so the first call already has it. Picking anything in the Heat Map section overrides it (`"all"` / a target id / an operation id); changing the operation resets the target to Current. These choices (`heatOn`, `heatOpChoice`, `heatTargetChoice`, `heatTransparency`) are remembered per device in `runlog_map_settings`. **Key (v1.198.1):** an "Observation density" key (same ramp as the report) shows **bottom-left of the map while the heat map is on** — above Google's logo/copyright strip, hidden while a Fly-mode card uses that corner. An operation the person can't read the report for shows "The heat map isn't available for this operation." instead of drawing.

**Fly + Nearmap split view (v1.201.0, Swap removed and Follow added v1.202.0)** — in Fly, a square **NM** button under the compass / 0° buttons (same look as the flat map's NM; `IntelligenceMapping.tsx`) shows a small **Nearmap window** on top of the 3D map: a flat top-down Google map with the Nearmap layer (`components/NearmapPip.tsx`, tiles from `/api/nearmap/tile`). The window is `components/SplitViewFrame.tsx` — drag the title bar to move, the grip in the bottom right corner to resize, a **Follow** button, ✕ — and starts top left under the Centre on me / Follow me buttons. **Follow** (on by default, and back on every time the window is reopened or Fly is left; `splitFollow`, not remembered) makes the window look where the 3D camera looks: `NearmapPip` polls `getLastFlyCamera()` every 400 ms and moves only when the camera has; with Follow off a pan/zoom in the window stays, and turning Follow back on snaps it to Fly. (There is no Swap any more — it was built in v1.201.0 and removed at the user's request.) The window's box lives in CSS variables on the map container (`SPLIT_VARS`, `splitBoxStyle`) so dragging never re-renders the Map page; it is reported once on drop. **Remembered per device** in `runlog_map_settings` (`nmSplitOn`, `nmSplitBox`, parsed by `parseSplitSettings`). **Offered only** in Fly, not on a phone (`useIsMobile` / `narrowScreen`), and only when the server has a key — `intelligence.nearmapAvailable` (also on the Investigator allow-list in `server/_core/trpc.ts`; the key itself never leaves the server). Pure rules (default / clamped box, availability, zoom for a camera range) are in `shared/splitView.ts`, tested in `server/splitView.test.ts`. Not checked against live Google 3D / Nearmap (blocked in the dev sandbox).

**Nearmap photo date (v1.202.0)** — wherever Nearmap is showing, a label says when the photos were taken and how old they are: on the flat map a white chip bottom-left (`NearmapAgeLabel variant="map"`, above Google's logo and above the Heat Map key when that is on; only while the NM layer is on and Fly is not open), in Fly a dark strip along the bottom edge of the small window (`variant="window"`, "14 Mar 2026 · 7 mo"). A coloured dot gives the age: green under 6 months, amber 6–12, red over 12 (`describeNearmapAge` in `shared/nearmapAge.ts`, tested in `server/nearmapAge.test.ts`; calendar months). The date comes from `intelligence.nearmapCaptureDate` (also on the Investigator allow-list) → `fetchNearmapCaptureDate` in `server/nearmapProxy.ts`, which asks Nearmap's **Coverage service** (`https://api.nearmap.com/coverage/v2/point/{lng},{lat}`, same key, server only) and takes the newest `captureDate` (`latestCaptureDate`); answers are cached per ~500 m (`nearmapSpot`) for an hour, a failed lookup for five minutes. **If the lookup fails — no key, no Coverage access on the key, an error — the label is simply not shown** (the failure is logged server-side with the upstream status and the start of the body). The exact Coverage query parameters (`limit`, `sort=-captureDate`, `resources=tiles:Vert`; it retries with none if Nearmap refuses them) could not be checked from the dev sandbox, so check the first real label against Nearmap's own viewer, and look at the server log if none appears. The date describes the centre of the view; Nearmap's latest map can join surveys of different dates across the screen.

Rose was too alarming across seven buttons; amber stays for "needs attention" and red for problems.

**Map marker entity count (v1.193.4)** — the number on a house marker is the count of distinct people and vehicles its popup lists, from one pure function, `markerEntityCount` in `shared/markerEntityCount.ts` (tested in `server/markerEntityCount.test.ts`), written to mirror `entityBlocksHtml`: the people registered at the address (target / other resident / associate) with every vehicle on their registry record, plus what running sheets *observed* there (people seen, vehicles seen — a person only *seen* at a place no longer brings in every vehicle they own), plus every address the pin absorbed within 20 m (`secondaryLocs`), each person and each vehicle once (people by short name, vehicles by rego). If the popup's lists change, change this function with it.

**NEARBY LOCATION (Map page, right-hand pane, v1.184.0)**: one switch under Target Logger, off by default (remembered per device in `runlog_map_settings` as `nearbyOn`), nothing shown beneath it. On: the page runs its own GPS watch (independent of Show & Share), loads every location the person can reach (`intelligence.mappingLocations` with **every reachable operation id** — an empty `operationIds` returns nothing, it does not mean "all"), geocodes them with the same Geocoder + localStorage cache the normal pins use (manually-moved positions from `intelPinOverrides` win), and draws the ones within 500 m as diamonds (fill = type, ring and distance pill = 100 m / 250 m / 500 m band, a red pulse at 100 m or less) plus a translucent non-clickable 500 m circle. They are **in addition to** the normal pins (z-index -1, under them) and open the same `buildInfoWindowContent` popup; Edit/Move work on the diamond too. Pure rules (distance, bands, 500 m filter, 20 m fold into a target address) are in `shared/nearbyLocations.ts`; the drawing is the "NEARBY LOCATION" block in `IntelligenceMapping.tsx`.

## Target Logger: a vehicle seen on the move names who is in it (v1.204.4)

A departure with unseen occupants ("Vehicle 1FAT001, unseen occupant/s, departed 27 Olding Way and continued via:") is often followed by a row that identifies the target in the vehicle ("Vehicle 1FAT001, HOGAN driver and sole occupant, travelled on Leach Highway, FREMANTLE and continued via:"). That shape — `VEHICLE_SIGHTING_PATTERN` / `matchVehicleSighting` in `shared/vehicleEventPatterns.ts`: "Vehicle REGO", the occupants, a comma, then `travelled|travelling|driving|drove` + `on|along|down|up|via|through` + the route, and **no** departure or arrival verb (those keep their own rules) — is now read as a move: (1) `computePendingVehicleDepartures` (`server/db.ts`) gives that pending departure the identified occupants (when the row names someone; "unseen" is kept when it doesn't) and `via` / `viaRowId` (where it is now); (2) `scanWalkEvents` places those people **in the vehicle** (`ScannedPlacement.via`) and takes them out of the place they were last logged inside, so the "Inside 27 Olding Way" card goes; (3) `isReadAsMovement` is true for it, so the tracker no longer warns that a later row "wasn't read as a move". On the sheet's Target Logger and the RS Quick Entry card the departed vehicle now shows the person (HOGAN · In 1FAT001) and "Travelling on Leach Highway, FREMANTLE · 10:55 AM — from 27 Olding Way · 10:50 AM", and its "Vehicle arriving" chip carries the identified occupants. It ends, as before, when the vehicle arrives. `extractOccupantNames` moved to `shared/occupantNames.ts` (still re-exported from `lib/mentionAutocomplete.ts`) so the server rules can use it. Tests: `server/vehicleSighting.test.ts`. Not yet looked at in a browser against a real sheet.

**Target Logger: a sighting row keeps the place they entered (v1.206.4)** — "HOGAN and CORNELL inside Flight Club Fremantle playing darts and drinking beers." used to be read as being inside **"Flight Club Fremantle playing darts"** — a different place from the one they had entered, so the logger moved them there and the map's target flag (which needs a place it can locate) disappeared. `presencePlace` in `shared/walkEventPatterns.ts` now runs the text after "inside" through `cutAtDescription`: a place name is written in capitals / digits, so it keeps the leading run of name words and stops at the first lower-case word that isn't a name connector (`PLACE_NAME_CONNECTOR_RE`: and, of, the, de, la, le, du, del, von, van, on, at, in, by, near, upon — kept only when a capitalised word follows, so "Melville Fish and Chips", "Hotel de Ville" and "Kinky Lizard Cafe on Mews" stay whole while "Gino's at the bar", "Bull Creek Tavern for lunch" and "… playing darts" are cut). The existing cuts (with / while / who / as / when, "and" + lower case) still apply first. Tests: `server/walkScan.test.ts` ("a presence row's place stops where the description starts"). Only the "inside <Place>" sighting rows are changed; other walk-in phrasings are as before.

**Target Logger: a departure that names its occupants moves them out of "inside" (v1.206.6)** — "HOGAN and CORNELL entered DRIVO Carpark…" followed by "Vehicle 1FAT001, HOGAN driver, CORNELL front passenger, departed DRIVO Carpark and continued via:" used to show both "Inside DRIVO Carpark" and the departed vehicle (and the map's "inside" flag). A person can only be in one place and the latest row wins, so `scanWalkEvents` now treats a `VEHICLE_DEPART_PATTERN` row that names occupants like the v1.204.4 sighting: they are placed in that vehicle, taken out of every place they were inside, and no longer heading anywhere. Unseen and "unidentified …" occupants name nobody registered and change nothing (an unseen-occupant departure still leaves the walk-in). A later row placing them elsewhere overrides as before. Tests: `server/vehicleSighting.test.ts`.

**Target Logger: boats and vessels (v1.207.0)** — a row where someone gets onto a boat puts them **on a vessel** until a later row puts them somewhere else (latest row wins, same as everything else in the logger). The pure rules are `shared/vesselPatterns.ts` (`matchVesselBoarding`, `matchVesselDisembark`; tests in `server/vessel.test.ts`): boarding = boarded / embarked (on, onto) / entered / climbed or stepped or got aboard, onto, into / went aboard / jumped aboard + a craft ("a vessel", "the white yacht", "a 10 metre catamaran" — vessel, boat, yacht, ship, ferry, dinghy, jet ski, catamaran, cruiser, speedboat, sailboat, trawler, tinny, skiff, houseboat, runabout, kayak, canoe); leaving = disembarked (from) / alighted / got off / stepped off / climbed off / jumped off / exited / left / walked off + a craft, or "disembarked" / "alighted" alone. A craft word that is part of a place ("boat ramp", "boat shed", "Fremantle Boat Pens", "marina", "jetty", "dock") is never read as a vessel, and "Vehicle <rego>" sentences are never boardings. `scanWalkEvents` places the people with `placements[].vessel` (rego `""`, so they are not in a vehicle), takes them out of any place they were inside and stops them heading anywhere; a boarding row returns early (so "entered a vessel" is no longer read as being *inside* "a vessel"), a leaving row puts them back on foot and the rest of the sentence ("… and walked along the jetty") is still read. `locateTarget` gives the new state `vessel` (flag emoji 🛥️, label "on a vessel", `TARGET_EMOJI`), placed at where they were last logged, else at the newest vehicle arrival that named them, always marked `placeIsEstimate` — the row says where the boat is only in words ("at the end of the jetty"), which can't be geocoded. Both the running sheet panel (`SheetDetail.tsx`) and RS Quick Entry (`IntelligenceMapping.tsx`) show an **On a vessel** card (key `vsl-…`) with a **Disembarked** chip ("HOGAN disembarked from a vessel and walked [route] towards [location]."), and `isReadAsMovement` counts boarding / leaving so the "wasn't read as a move" warning stays quiet. **Not built:** tracking the vessel itself as an entity (a named boat, its own profile, a boat target) or a "vessel departing" chip; vessels are only where the people are. Not yet looked at in a browser.

**Target flag: when several markers share an address (v2.0.1)** — a parked car and a boat can both resolve to "15 Riverside Road", and the flag used to go on whichever matching marker came first (the boat), so "HOGAN · departed on foot" sat on the boat instead of the car he got out of. The pure rule is `shared/flagMarker.ts` (`chooseFlagMarker`, `markerKind`; tests `server/flagMarker.test.ts`) — **the flag goes on the most specific marker the sheet points at:** (1) **the marker of the vehicle he got out of / is in** (label holds the rego, `findVehicleMarker`; a rego marker of another operation is never used) — a "departed on foot" position now carries that vehicle's `rego` (`locateTarget`'s walking branch, from the newest arrival that named him) and the map uses its marker wherever its address is; (2) **a boat marker when he is on a vessel**; (3) otherwise a marker of the right *kind* for the state — vehicle marker for vehicle / moving / out of sight, place marker (house, point of interest) for inside / on foot, boat for vessel (`markerKind` reads the icon: boat / vessel / yacht / ship / ferry… = boat; sedan / car / police / motorbike / truck / van… = vehicle; a rego-only label with no icon is a vehicle; anything else is a place); (4) still more than one of that kind → the **newest** (markers arrive newest first), and the Target location status line says "N markers share this address, so the flag is on the newest <kind> marker" instead of picking silently. Only custom markers that *carry* the place (own address, linked intel label, or a merged location) are weighed; a single carrier is used as before. **To stop it recurring: label a vehicle's marker with its rego** — that is the only thing that ties a marker to a specific vehicle; boats have no equivalent tie yet (a boat marker is found by its icon, so two boats at one address fall to rule 4). Wired in the flag effect in `IntelligenceMapping.tsx` (`findPin`).

**Target Logger: "last seen at" follows arrivals and departures (v2.0.2)** — the logger's "last place logged" for a person (`lastAt` in `scanWalkEvents`, shown as "Last seen at …" on the On-a-vessel and in-vehicle cards and used as the place for the boat flag and for a vehicle with no arrival row) was only updated by walk-in / walk-out rows, so after "Vehicle 1FAT001, HOGAN driver, arrived at 15 Riverside Road…" it still said **DRIVO Carpark** from several rows earlier, and the boat flag was drawn there ("HOGAN · on the boat" on a car park). It is now also set by **a vehicle arrival with named occupants** (the arrival address, short form) and by **a departure with named occupants** (the address they left from), in row order, so the newest logged place wins. Unseen occupants set nothing. Tests: `server/vessel.test.ts` ("where the vessel is: the latest place logged, not an older one").

**Getting off a boat reads short (v2.0.3)** — "HOGAN disembarked from the boat and walked [route] towards [location]." used to make the on-foot card and flag read "HOGAN disembarked from the boat and · departed on foot" (the whole front of the sentence was taken as the walker's name). `scanWalkEvents` now cuts the getting-off clause out of the row text (`stripVesselLeave`, `shared/vesselPatterns.ts`: "disembarked (from) / got off / stepped off / exited … the boat (and)", or a bare "disembarked / alighted (and)") before the walking rules read it, so the walker is just **HOGAN**. The heading it produces carries `fromVessel` ("the boat", or "the vessel" when the row only says "disembarked") — `ScannedHeadingTo` / `PendingHeadingTo.fromVessel`, set per row from `disembarkRows` — and **the flag reads "HOGAN · disembarked, on foot"** (`locateTarget`, label `disembarked, on foot`) while the Target Logger card (sheet and RS Quick Entry) shows the pill **Disembarked**, "On foot", "Left the boat · since …". A boat is never a place someone is "inside", and a getting-off row without a walk still just puts them back on foot. Tests: `server/vessel.test.ts` ("getting off a boat and walking: short wording").

**Walked to the car and got in (v2.0.4)** — "HOGAN disembarked from the boat and walked along the jetty to Vehicle 1FAT001 (Vehicle 1FAT001), and entered via the driver's door." was read as only walking *towards* the car (flag "HOGAN · to 1FAT001"), because only "entered Vehicle X" counted as getting in. `GOT_IN_AFTER_VEHICLE` (`shared/walkEventPatterns.ts`) now also counts a getting-in clause after the vehicle in the same sentence — entered it / the vehicle / the car (not "the car park") / via / through / by / the driver's, passenger, front, rear or back door or seat; got / climbed / jumped in or into; sat in; seated — so he is **in** 1FAT001 (`inside: true`) and the flag reads **"HOGAN · in 1FAT001"** at the car's marker (state `vehicle`, place = where it is parked). Walking to the car with no getting-in clause is still "to 1FAT001". **The flag also never lands on an unfit marker** (`markerFitsState`, `shared/flagMarker.ts`): a boat marker is never where someone in, or walking to, a car is, and a car marker is never where someone on a boat is — even when it is the only marker carrying the address (the map skips it and falls back to the address pin, or says no marker matches). Tests: `server/vessel.test.ts` ("walked to the car and got in"), `server/flagMarker.test.ts` (`markerFitsState`).

**Active RS lights up as soon as a running sheet is picked on the Map (v2.4.1)** — the header's Active RS button (`DashboardLayout.tsx`, `activeRsId`) reads `rsSelectedSheetId` from `runlog_map_settings`, but it only re-read it on a page change or window focus: the browser's `storage` event fires in *other* tabs, never the one that wrote the value, so choosing a sheet in Map Settings → RS Selection left the button greyed until the officer went to another page and back. The Map page's settings-save effect (`IntelligenceMapping.tsx`) now dispatches `runlog-map-settings-changed` on `window` after every write and the layout listens for it, so the button updates immediately (and again if the selection is cleared with the X). Any other code that writes `runlog_map_settings` and wants the header to follow should dispatch the same event.

**"Entered here" from a map click — a shop inside the centre he is in (v2.5.0, wording v2.5.1)** — a person logged inside a place with many parts (a shopping centre) has only the vehicle-style options on the card (Walked to Vehicle / Left address / Vehicle Depart), so there was nothing to log him going into one shop when the officer clicked that shop on the map for an RS Quick Entry. The pure rule is `enterNearbyOffers` in `shared/enterNearby.ts` (tested in `server/enterNearby.test.ts`); **the click is the trigger** — nothing is ever added to the cards without one, so a target inside a house gets no extra button. When the RS Quick Entry is opened from a place on the map (POI tap, tap-and-hold chooser, a marker's RS Quick Entry, an intel pin — `mapQeLatLng` is set by each opener and cleared when the entry closes) and someone is logged inside a different place within `ENTER_NEARBY_METRES` (400 m) of the click, an **Inside** card with one **Entered here** chip is shown. **v2.5.1 — the sentence is written like any other first mention of a place:** the **full address with its bracket short form the first time** (`arriveAddr`: "ROCHA entered JB Hi-Fi Rockingham City, 1 Council Avenue, ROCKINGHAM WA (JB Hi-Fi Rockingham City) and continued out of sight." — the bracket is what registers the location, so the shop gets its pin and the target flag), the short form once the sheet has mentioned it. (v2.5.0 wrote the short form and appended ", Rockingham Centre", so no pin or flag was made.) The centre needs no naming: nobody exited it, so the scan keeps its walk-in ("Rockingham Centre", older row) next to the shop's (newest row, which is the placement the flag follows), and Walked to Vehicle / Left address on the centre's vehicle card keep working. One offer per person, from the place he was last logged going into (the newest walk-in). Never offered: for the place he is already inside (or one that holds it), when either position is unknown (`placePosition` — a pin or marker titled that place, else the geocoder's cached position; nothing is guessed), when the click is far away, or from the **target's own registered home address** (`hbf` / `hb`) — so a click on a neighbour's house or a strata block while he is at home offers nothing. Only the map's RS Quick Entry has it; the running sheet's own Target Logger is unchanged. Not looked at in a browser (Google Maps is blocked in the dev sandbox).

**The Target Logger and the flag end by themselves when every member has ceased (v2.6.0)** — until now nothing in the logger read "Surveillance ceased", so the last card and the flag stayed on the last known place for ever. Individual officers cease and commence during a deployment, so one person's "ceased" must not end it, and **no timer is used** (a deployment can sit for hours with nothing logged and always finishes with a ceased). The pure rule is `surveillanceState` in `shared/surveillanceState.ts` (tested in `server/surveillanceState.test.ts`): every CIN on the sheet — its team roster (`runningSheets.sheetCins`) **plus** anyone who appears on a row — is on or off, starting on. A row whose text starts a line with "Surveillance ceased" puts every CIN on that row **off**; one starting "Surveillance commenced" puts them back **on**; **ordinary rows change nothing**, so a late debrief row can't revive a ceased CIN. The surveillance has **ended** when every CIN is off, and goes live again the moment any CIN commences. A team member who never writes a row must still cease (they hold it open until a ceased row has their CIN on it — take them off the sheet's roster if they weren't there); a ceased row with no CINs on it changes nothing. It reads the saved rows only (`getSurveillanceState` in `server/db.ts`, `row.surveillanceState`, polled with the other pending lists and invalidated after a row is added). **When it has ended**: the Target Logger (the sheet's and the RS Quick Entry's) shows **one grey card** — "Ceased", "Surveillance ceased 3:40 PM", "Last seen inside Rockingham Centre" (`endedContinuityCard`, `client/src/lib/surveillanceCard.ts`; `ContinuityCardData.ended` greys the pill and the header dot) — in place of the live cards, with no movement chips and one **Surveillance commenced** chip ("Surveillance commenced at [location]."); and the **target flag** turns grey and dashed reading **"ROCHA · ceased at 3:40 PM"** (⏹; v2.6.1 — it said "last seen" at first) at the last known place, in Fly too. The grey Target Logger card still says "Last seen inside …" for where he was. The time is the row that made the last CIN cease. Not looked at in a browser (Google Maps is blocked in the dev sandbox).

**Hand-over between running sheets — the second team's Target Logger resumes by itself (v2.7.0)** — one team ceases and the next takes over on a *separate* running sheet for the same target and place. The pure rule is `isHandover` (`shared/surveillanceHandover.ts`, tested in `server/surveillanceHandover.test.ts`); **all of these must match, or nothing is carried over**: (1) the same **operation**; (2) the same **target** (`targetKeyOfSheet`); (3) the first sheet has **ended** (every CIN ceased, v2.6.0); (4) the second sheet's first "Surveillance commenced at <place>" row is at the **same time or within 1 minute** (`HANDOVER_MINUTES`) of the row that ended the first sheet — so a short overlap works, a gap of 2 minutes does not; (5) the **place** matches (`samePlace`) the place on the ceased row or the target's last-known place. When it matches, `getRowsForLogger` (`server/db.ts`) puts the first sheet's rows in front of the second's for the Logger only (the six pending/walk lists and `getSurveillanceState`): carried rows get negative ascending ids so they compare older than the sheet's own rows, nothing is copied or saved, and chains A→B→C work (depth ≤ 5, cycles excluded; 5-second in-memory cache in `findHandoverSource`). **A place picked from the address suggestions also gets its sign from Google's type (v2.17.6)** — v2.17.5 fixed the sign for a place **tapped on the map**; this does the same for one **picked from the "as you type" suggestions** (running sheet and RS Quick Entry), which carry Google's types but only wrote the address into the observation. `useAddressSuggestions` now puts `placeSign` (`placeSignFromTypes` on the prediction's types) on a Google place item, and `addressSuggestInsertText` (`AddressSuggestDropdown.tsx` — the one function both consumers build the inserted text with) fires `intelligence.savePlaceSign` with the inserted address and the sign (fire-and-forget; offline or an Observer simply means no sign beyond what the name says). **A business with a tenancy code and a centre name before the street keeps its name (v2.17.9)** — a tapped "Westpac Branch Booragoon" was written "Westpac Branch Booragoon, T5004, Westfield, 125 Riseley Street, BOORAGOON WA (Westpac Branch Booragoon)" and the map's location came out as just **"125 Riseley Street, BOORAGOON"**: the business name was dropped, so it got no Bank sign, no pin of its own at the branch (it sat on the centre's street address) and the Target Logger place had no name to match. **Two people entering the same place one after the other are both inside (v2.17.10)** — PARK walked into Westpac Branch Booragoon from the car, then DOYLE (who had waited in the car) got out and entered the same branch; the Target Logger and the flag **swapped** them ("PARK in the vehicle", "DOYLE Inside") instead of showing both inside and the car empty. `scanWalkEvents` keeps one walk-in entry per place (`lastWalkIn`, keyed by the place) and `record` overwrote it with only the person who had just walked in, dropping whoever was already there. `record` (`shared/walkEventPatterns.ts`) now carries over the earlier people at that place — the place holds "PARK and DOYLE" — but only those still logged **on foot at that very place** (not since put in a vehicle, on a vessel or a bus, walked out — `leavePlace` / `leaveAllPlaces` already trim — or entered somewhere else), nobody is named twice, and a place everyone has walked out of starts fresh. Tests: `server/walkInMerge.test.ts`. Rows already saved read correctly from now on (computed live).

**Airport terminals: a numbered terminal gets the plane sign and is its own place (v2.19.3).** Perth Airport has Terminals 1 to 4, and a running sheet row such as "arrived at Terminal 4, Perth Airport WA 6105, Australia (Terminal 4)" used to get the house pin, because a bare "Terminal N" is deliberately not read as an airport (it could be a port or bus terminal — see v2.17.0 above). Two rules now, both pure functions in `shared/` with tests: **(1) the sign** — `placeSignOfName` (`shared/placeSigns.ts`) gives `place_airport` to a name that is exactly "Terminal N" (optionally "… Domestic / International / Regional"), **only when a later part of the label ends in the airport's name** (the locality as Google writes it: "Perth Airport WA 6105"; at most a state and postcode after it). So "Terminal 1, Fremantle Port", "Terminal 2, Perth Bus Station", a bare "Terminal 1", a car park ("Terminal 4 Car Park, Perth Airport") and a street ("Terminal 4, Airport Drive") stay as they were. An officer's own icon still wins, and a tapped place whose Google type is airport already got the plane. **(2) the place** — `samePlace` (`shared/targetPosition.ts`) treats each numbered terminal as a place of its own: "Terminal 3" never matches "Terminal 4" (it already didn't, the number is a word), and **a label that names no terminal never matches one that does**, in either order, so a vague "Perth Airport" row cannot fold every terminal into one place (the shorter-inside-the-longer rule would otherwise have matched them). It errs towards two places rather than wrongly merging them, as the Intelligence rules do. The row text itself is unchanged (Google's address, with its "Perth Airport" suburb, is the real address). Tests: `server/placeSigns.test.ts`, `server/targetPosition.test.ts`. **Not done:** a bare "T4" / "Gate 12" style name is not read.

**Supermarket sign (v2.20.0)** — an eleventh square sign in the **Places** group (`place_supermarket`, a shopping trolley; the shopping centre keeps its bag), same rules as the other place signs (`shared/placeSigns.ts`, picker label "Supermarket Sign", drawn by `placeSign` in `client/src/lib/markerSvgs.ts`; an officer's own icon always wins). **By wording** (the place's own name, the first part of the label): the word "supermarket(s)", or Woolworths, Coles, ALDI, IGA, Foodland, FoodWorks, Spudshed, Harris Farm. **By Google's type** at a tap: `supermarket`, `grocery_store`, `grocery_or_supermarket` (a mall that also holds one is still the shopping centre, as before). **Never guessed:** a chain's petrol station, liquor store, pharmacy, car park, depot, warehouse or head office is not the supermarket ("Coles Express", "Woolworths Petrol", "BWS", "Dan Murphy's", "Woolworths Distribution Centre"); a street ("Coles Road") and the Tasmanian town "Coles Bay" are not a shop; "Karrinyup Shopping Centre" stays the centre. Order in the name rules: pub / hotel, post office, bank, gym, shopping centre, **supermarket**, cafe, fast food, restaurant, airport. Costco and other wholesale or independent grocers are not read by name (Google's type still catches them). Tests: `server/placeSigns.test.ts`. A map pin shows it once a supermarket place is picked or tapped; existing pins that already have a saved icon are not changed.
