# UI conventions (full text)

Detailed per-feature notes moved out of `CLAUDE.md` (text unchanged, original order). `CLAUDE.md` keeps only the standing rules; add a new note for a change **here**, in the file for its area.

## Contents


---

- **Resolved — `AdvancedMarkerElement` positioning drift, migrated to `OverlayView`**: `google.maps.marker.AdvancedMarkerElement` had a confirmed, reproducible positioning-drift bug — its on-screen position visibly separated from its true lat/lng the further the map was zoomed from wherever it was last drawn, correcting back to accurate near that original zoom level. Confirmed present under both a real vector Map ID and a real raster Map ID (see `components/Map.tsx`'s `MAP_ID_VECTOR`/`MAP_ID_RASTER`), so it wasn't a rendering-mode/Map-ID issue. Not fixable from outside the class: forcing a fresh `.position` assignment, or even a full detach/reattach (`.map = null` then `.map = map`) on the map's `idle` event, didn't stop it — `AdvancedMarkerElement` recalculates its position continuously as part of the map's own render loop during a gesture, not once at the end, so any one-shot correction got overwritten by the very next frame. **Fixed** by migrating all five overlay call sites (custom map markers, shape note-labels, live team member pins, intel pins, and the address search pin) in `IntelligenceMapping.tsx` to a shared `DivIconOverlay` class (`lib/divIconOverlay.ts`), built on `google.maps.OverlayView` — the same overlay mechanism `Circle`/`Rectangle`/`Polygon`/`Polyline` shapes use, which is why shapes never drifted. It recomputes its pixel position from the map's live projection on every redraw instead of trusting cached internal state. `DivIconOverlay` mirrors `AdvancedMarkerElement`'s API shape closely (`.map`/`.position`/`.content`/`.zIndex`/`.title`/`.gmpDraggable` get/set properties, `.addListener(...)` inherited from `google.maps.MVCObject` — do not replace it with a custom shim) and hand-rolls the two behaviours `OverlayView` doesn't provide natively: drag-to-move (via pointer events + `projection.fromDivPixelToLatLng`) and an `anchor: "center" | "none"` option (`"none"` for shape note-labels, whose pill content sets its own offset transform directly rather than being centred on its anchor point). The previous `AdvancedMarkerElement` implementation stays intact in git history (see the commits migrating each overlay type, prior to this note being updated), so reverting to it is a reasonable option to revisit if it's ever needed (e.g. a future Google Maps JS API release changing this trade-off) — not a rewrite from scratch.

- **Design preference — symmetry (non-negotiable, check on every UI change)**: the user cares about layouts reading as neat and symmetrical (equal-sized buttons/pills in a row, balanced spacing, aligned icons) — when building or touching UI, actively check for lopsided sizing/spacing rather than leaving whatever falls out of default flex/grid behavior. This isn't just for new components: adding a tab, button, or item to an existing row/group means re-checking that the whole row still reads as symmetrical (e.g. equal-width tabs via `grid grid-cols-N`, not one trigger sized to its own text while others aren't — see the Operation page's 3-tab bar in `OperationDetail.tsx` for the pattern). This app is used on laptop, tablet, and phone; mentally (or actually, via Playwright) check how a change looks at each of those widths, not just desktop, before considering it done.

- **Form kit — one look for forms, dialogs and titled panels (non-negotiable, extend it rather than inventing a new style)**: `lib/formKit.ts` is the single source. Controls (`Input`, `Select`, `Textarea`, the Operation picker) get a white fill and a visible border from the base components in `components/ui` (light-theme `--input` is deliberately a clearly visible grey, and placeholders are `text-muted-foreground/80`); field labels are `FORM_LABEL` (12px semibold uppercase `text-foreground/80`). Panels use `FORM_TONES[tone].panel` + `.band` — a solid white card with a full-strength border and a tinted **titled header band** (the band pulls to the card edge with `-mx-3 -mt-3`, so the panel needs `p-3`). The tone is the entity colour the Intelligence chips already use: target/person = rose, address = emerald, vehicle = amber, associate = violet, resident = sky, photo = cyan, other = slate. **Colour key (v1.190.5, app-wide):** a registered **target is rose** (same family as the Target Registry), an **other-home-address resident is sky**, an associate is violet, a person mined from observation text is **navy** (`blue-900`, `INTEL_CHIP_CLASSES.person` / `TYPE_COLORS.person`; targets use `TARGET_COLOR` in `Intelligence.tsx`), and **Images/photos are cyan** (the Images section, camera counts, photo panels). The PDF exports (`ProfileKit.tsx`, `OperationProfileContent.tsx`, the map's location popup in `IntelligenceMapping.tsx`) use the same hexes written out — `#e11d48` target, `#0284c7` resident — so change them together. Colour marks what a panel *is*, never tints the fields themselves; nest panels at most two levels (`FORM_NESTED_PANEL`). Don't reintroduce translucent tinted bodies or `border-l-4` rails. Applied so far: Target Registry (card, Add/Import/Merge dialogs, Imported Documents), Add/Edit User; `LinkAttachmentDialog` and the remaining pages are still to convert (the page-by-page readability pass).

- **Page kit — one look for read-only pages (non-negotiable, extend it rather than inventing a new style)**: the companion to the Form kit, for pages that *display* records. `lib/pageKit.ts` holds the shared classes: `SECTION_CARD` (solid white `bg-card`, full-strength `border-border`, `shadow-sm`, `p-4`), `SECTION_BAND`/`SECTION_TITLE`/`SECTION_COUNT` (a grey titled header band that bleeds to the card edge via `-mx-4 -mt-4`, so it must be the card's first child; 13px bold uppercase title; count pill), `ROW_ITEM`, `FIELD_LABEL`/`FIELD_VALUE`. The five Intelligence profile pages share `components/ProfileSectionHeading.tsx` (`SectionHeading`, with `sub` for a quieter heading inside a banded card). Rules: no `border-border/NN` or translucent `bg-card/NN` on cards (they wash out on the light page), no text under 12px, labels are uppercase semibold `text-foreground/70`, values are `text-sm`. Collapsible panels on the Running Sheet (Team — Certify, Target, Target Logger) use the same grey band as their header. Applied so far: Intelligence Folder and all five profiles, Running Sheet panels, Summary, Governance, and the three To-Do pages (shared `components/TodoKit.tsx`: operation card with grey band, each sheet its own bordered row, red/amber/blue tone, dark `-700` text on the light theme). Reports (Outstanding Actions, Weekly Activity) are done too, and so are the Intelligence **Ego Network** and **Heat Map** reports (v1.188.3: one titled card each — filters in equal columns, Export/Refresh in the band, canvas or map beside a ranked list, canvas colours from theme tokens; the canvas is no longer a fixed near-black panel, and the parent no longer fixes their height). The Running Sheet table is a card per row below 768px (`.running-sheet-cards` in `index.css`, CINs wrap as chips in `CinCertifyCell`; tap certifies, press-and-hold a chip removes it; iPad and laptop keep the table). Court wizards, SMEAC/UCO forms, Intel Export, Operations pages, Profile, Audit Log (cards on phones), Images, Calendar, Shortcuts, Recycle Bin, Help and Draft are done too; the base table rule no longer draws near-black row lines on the light theme. Still to convert: Op Manager/CTO Roster (incl. the Weekly Tasking Report) and the Mapping/RS Mapping side panels (need a live map to check).

- **Colour themes and the light header / side panel (v2.24.0)**: Appearance (`MyProfilePage.tsx`) has two saved choices per officer. (1) **Colour theme** (`users.colorPalette`, `COLOR_PALETTES` in `shared/const.ts`): Steel Blue (default), Harbour Teal, Monochrome, Phosphor, Amber Console, Case File. **Federal Navy and Graphite were removed** (too close to Steel Blue — three blues); a saved removed id reads as the default through `normalizeColorPalette`, and migration `0131` moves those accounts to `steel-blue` too. A new palette is a light and a dark block in `index.css` plus an entry in `COLOR_PALETTES` and `PALETTE_SWATCHES` (`server/appearance.test.ts` checks every id has both blocks). (2) **Header and left side panel** (`users.chromeStyle`, `CHROME_STYLES`, applied as `data-chrome` on `<html>` by `AppearanceApplier`): `dark` (default, as before — a dark rail in both modes) or `light` (the palette's own light colours). It only shows in Light mode; Dark mode is always dark. The `[data-chrome="light"]` rule in `index.css` is written in terms of the palette's own tokens (`--sidebar: var(--card)` …) and **must stay after every palette block** (same specificity, later wins). **The deeper folder colours are automatic, no switch**: inside `header.app-chrome` (the desktop header carries that class) and `[data-sidebar="sidebar"]` (desktop rail and the phone menu sheet) the Tailwind `--color-<hue>-400` variables are redefined one step deeper (`-600`; purple/red `-500` → `-700`), so every existing class — icon, outline, tint — follows without being edited and the page content is untouched. New folder colours therefore need their hue added to that rule. Pages already use their own deeper light-mode shades, so the folder's tile on its page matches the side panel. Checked in a browser at laptop, tablet and phone widths for Steel Blue, Harbour Teal and Monochrome (e2e: `screens.spec.ts` "Appearance"). Not covered: the Map page's own panels.

- **My Profile sections are drop-downs, closed by default, with memory (v2.24.1)**: every titled card on My Profile (Shared with you, Profile Information, Intelligence Entity Scan, Missed-Entity Scan, Appearance, My devices, Change Password) is a button-headed drop-down (`components/ProfileSection.tsx`; `PasskeyDevicesCard` uses the same `useRememberedOpen` hook and `SectionChevron`). Closed the first time; after that it stays the way the officer left it, remembered **per section in this browser** (`localStorage` key `runlog_profile_sections`, wrapped in try/catch — a convenience, not an account setting, so it does not follow them to another device). The body stays mounted while closed (`hidden`), so a half-typed password or a scan result is not lost by closing. A new Profile card should use `ProfileSection` with a new `id`. e2e: `screens.spec.ts` "My Profile sections…"; the Appearance e2e test opens its section first.

- **Governance folder and the sheet "RS Governance" page use the Certify look (v2.25.1)**: the Governance list (`GovernanceList.tsx`) is built from the To-Do kit (`components/TodoKit.tsx`) — `TodoHeader`, a `TodoGroup` card per operation (grey titled band with the operation name, a status pill — "All complete" / "N to review", rose if anything is overdue — and the sheet count), and a `TodoRow` per running sheet with a completion pill, date and OVERDUE flag; tile view is a `TodoTile` per operation with a progress bar. The kit gained a **`purple` tone** (the Governance folder's colour; the To-Do → RS Governance list stays blue), `TodoHeader`'s optional `right` slot (used for the sheet's percentage) and `TodoGroup`'s `badge`; `TodoTile` is only clickable when given `onClick`. The sheet page (`Governance.tsx`) has the same header, and its sections (Sheet details, Team Leader, Operative — Running Sheet, Operative — Imagery, Notes, Overall completion) are white cards with a grey titled band (`components/GovernanceSection.tsx`, which also holds `percentTextClass`: emerald done / sky part way / rose not started). Behaviour is unchanged (the three check sections still start closed, same checks, same data). Checked at laptop and phone widths, list and tile view.
